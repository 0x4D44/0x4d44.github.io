Architecture deep-dive · clean-room compiler

Recompiling Turbo Pascal
for the modern era.

mdtpw is a clean-room reimplementation of Borland Turbo Pascal for Windows 1.5. It takes legacy 16-bit Object Pascal source and compiles it to a native PE32 or PE32+ executable that runs on modern 64-bit Windows — no 16-bit emulation, no NE output, no DOS box.

01 · The problem

A 30-year-old app, recompiled — and it just runs.

The deliverable that matters: "a representative TPW app, recompiled, runs correctly on modern Windows." Bug-for-bug machine-code fidelity with Borland's compiler is explicitly not a goal. Behavioural fidelity of the language and its libraries is.

The input

TP7-era Object Pascal

The object model (not Delphi class), 16-bit Integer, length-prefixed strings, sets, variant records, units, typed constants, absolute, inline asm — and a faithful OWL 1.0 + BWCC GUI stack.

The output

A flat native PE image

The produced binary is an ordinary 32- or 64-bit Windows executable. The modern loader treats it like any other EXE — no thunking, no DPMI, no compatibility shim, no virtual machine.

The method

Re-author, don't emulate

No Borland binaries are consumed. The .TPL runtime and the whole OWL library are re-written from source in Pascal and compiled by mdtpw itself — the most faithful path and the best end-to-end test.

Grounded in the original media The design was built on the authentic TPW 1.5 distribution, extracted to a 164-file source corpus, cross-checked line-by-line against Borland's own SYSTEM.INT, WOBJECTS.INT, WINTYPES.PAS and the STEP01..STEP10 tutorial demos. The compiler's tests run that unmodified corpus.
02 · Mental model

Three things, holdable in one head.

The architecture is deliberately small. It is a conventional Pascal front-end that emits LLVM IR, a thin native runtime in Rust, and the TPW libraries re-authored in Pascal and compiled by mdtpw. Read top to bottom: each plane sits on the one below it.

① Front-end  ·  Rustsrc/ — lexer → parser → sema → emit

A by-the-book recursive-descent Pascal-7 compiler. The only genuinely novel work is the type/layout engine, the typed-constant evaluator, and DDVT dispatch.

lexer · tokens parser · AST sema · types + layout consteval emit · textual LLVM IR
② LLVM backend  ·  off-the-shelfbundled clang + lld-link

Textual .ll is fed to bundled LLVM tools — optimise, codegen to COFF, link to PE. Solved problems stay solved; mdtpw writes none of this.

clang · opt + x86/x64 lld-link · PE32/PE32+ llvm-rc · resources llvm-dlltool · import libs
③ Native floor  ·  Rust #![no_std]mdtpw_rt/ — i686 + x86_64 staticlibs

The smallest possible native surface — only the symbols LLVM/clang cannot synthesise. Everything else lives one plane up, in Pascal.

__mdtpw_start · PE entry StdWndProc trampoline __tpw_* helpers __tpw_ddvt_lookup
④ TPW libraries  ·  Pascal, compiled by mdtpwruntime_pas/ — 20 re-authored units

The bulk of the Windows surface is ordinary Pascal that mdtpw recompiles. The library being the object model is exactly why re-authoring is the best compiler test.

WObjects · OWL 1.0 WinTypes / WinProcs StdDlgs · StdWnds BWCC WinDos
The one-line model "Pascal-7 front-end → LLVM. Everything Windows-specific is Pascal we recompile, sitting on a thin Rust floor."

04 · Locked decisions

Nine choices that shaped everything.

These are settled, not up for relitigation. Each trades scope for fidelity or simplicity. Expand any card for the rationale.

D1AST → LLVM IR directly — no custom middle IR›

The emitter lowers the typed AST straight to textual LLVM IR. There is no hand-rolled intermediate representation between them.

Why: LLVM is the typed IR. A bespoke middle IR would duplicate it for zero optimizer payoff.
D2Re-author OWL / Objects / StdDlgs / BWCC in Pascal›

The entire OWL library is re-written in TPW Pascal and compiled by mdtpw itself, rather than reimplemented natively or consumed as binary.

Why: the library is the object model and the DDVT. Re-authoring is the most faithful path and the single best end-to-end compiler test. The native floor stays tiny.
D4Two-plane type model — language widths frozen, API widths widened›

Pascal language types keep their TPW widths (Integer = 16-bit). Only Pointer/PChar widen to flat 32-bit. The re-declared API units re-type handles and messages at true Win32 width.

Why: legacy code touches handles only by name through compiler-supplied units — so recompiling is both source-compatible and ABI-correct. This is the make-or-break decision (see §05).
D5stdcall everywhere›

Every Pascal routine and every Win32 import uses stdcall (LLVM x86_stdcallcc).

Why: Win16 Pascal/FAR is callee-cleans-stack; stdcall is the only Win32 convention that is callee-cleans and exactly what kernel32/user32/gdi32 export — so API calls and callbacks need no shim.
D6Real → IEEE f64›

Borland's 6-byte software Real maps to IEEE f64; Single→f32, Extended→f64, Comp→i64. Serialized or absolute Real is rejected with a diagnostic (size 6→8).

Why: f64 strictly dominates the 48-bit real; the corpus uses bare Real, never {$N+}. A bit-faithful 48-bit real is a large runtime for less accuracy.
D7Segment / port / interrupt / overlay / BASM → reject with a diagnostic›

16-bit-isms with no flat-32 meaning are a hard compile error carrying a precise, actionable message.

Why: a survey of ~150 demos shows application code never uses them — only the RTL does, and the RTL is replaced. Rejecting is faithful and simplest (see §09).
D8Reuse a modern resource compiler›

.RC scripts compile through bundled llvm-rc; resources embed via the linker's .rsrc. mdtpw writes no RC compiler.

Why: resource compilation is a solved problem; writing one is pure scope.
D9No env vars, no feature flags›

The target is a single CLI argument resolved into one immutable Target record, threaded through codegen and ABI. There is exactly one behavioural code path.

Why: reproducible, testable, holdable in the head. Win64 becomes a data change in that record — not scattered string switches.
05 · The two-plane type model

How 16-bit code stays correct on a 32/64-bit machine.

This is the load-bearing idea (decision D4). There are two representation planes. The language plane freezes Pascal types at their original TPW widths for source fidelity. The API plane re-declares the handle and message types at their true modern Win32 widths — and legacy code only ever touches those by name.

Why it works A legacy program declares var W: HWnd; and passes it to SendMessage. It never writes the width down — it just uses the name. Because mdtpw supplies HWnd from its own re-declared WinTypes, recompiling silently upgrades every handle from 16 to 32/64 bits, ABI-correct, with zero source edits. The escape hatch — code that absolute-overlays or serializes a width-changed struct — is rejected rather than silently corrupted.
06 · Message dispatch — the heart of OWL

DDVT: a second vtable, keyed by Windows message.

OWL methods declared virtual wm_First + wm_Size don't go in the ordinary VMT. They go in a separate Dynamic Method Table (DMT), keyed by the message id, with inheritance fallback. Every object type therefore carries two dispatch tables. Step through a live message arriving from Windows:

1
Windows posts a message
WM_SIZE arrives at the one exported StdWndProc trampoline (in the native floor).
2
Recover the OWL object
GetObjectPtr(HWND) looks up the Pascal object for this window in a side table.
3
Repack to a Win16 TMessage
The Win32 args are reshaped into the canonical Win16 TMessage layout user code expects.
4
Lookup by message id
__tpw_ddvt_lookup(obj, 5) walks the DMT. wm_Size = index 5 → found in TMyWin.
5
Dispatch the handler
User's WMSize(var Msg) runs verbatim — it reads Msg.LParamLo/Hi assuming Win16 shape.
6
Unhandled? Fall through
A miss walks DefWndProc → DefCommandProc / DefChildProc → ultimately Win32 DefWindowProc.

The highest-risk contract The Win16⇄Win32 WM_COMMAND repack is where every menu and button silently lives or dies — Win16 puts the control id in wParam; Win32 splits id/notify into wParam and the hwnd into lParam. That reshape happens in exactly one place, the trampoline, so thousands of lines of user handlers never have to know.
07 · The runtime split

Mostly Pascal, with a thin Rust floor.

The runtime is split deliberately to keep native code minimal. Almost everything is Pascal that mdtpw recompiles; the Rust floor exists only for the handful of symbols that LLVM and the linker genuinely cannot synthesise.

One walker, no second copy The DDVT walk lives in src/ddvt_walk.rs. It is a module of the compiler crate — so cargo test runs its unit oracle — and it is #[path]-included into the runtime floor, where __tpw_ddvt_lookup forwards to the exact same code. There is no duplicate implementation to drift apart. The ABI it depends on — symbol name, (ptr, i16) → ptr signature, and the { parent, count, [count × {i16, ptr}] } memory layout — is frozen.
08 · Self-standing backend

Ships as a single EXE. Needs nothing installed.

cargo build --release produces one mdtpw.exe that embeds both the runtime assets and the entire LLVM backend. A fresh Windows host needs no LLVM, no MSVC, and no Windows SDK to compile a supported program.

; the backend payload, embedded in mdtpw.exe, extracted on first use to: %LOCALAPPDATA%\mdtpw\backend\<content-hash>\ clang.exe ; .ll → .obj (LLVM 21.1.8, x86 + x64 backends) lld-link.exe ; .obj → PE32 / PE32+ llvm-rc.exe ; .rc → .res (resources) llvm-dlltool.exe ; generate Win32 import libs from actual imports ; the cache is content-addressed: a new build extracts a new <hash> dir, ; so versions never collide and re-extraction is a no-op once warm.
Targets

win32 & win64

--target win32 (default) emits i686 PE32 with stdcall. --target win64 emits x86_64 PE32+ with the MS x64 ABI, native-width handles, and native callback boundaries — the same source, a data change in Target.

Build config

mdtpw.toml

Invoked with no .pas, mdtpw walks up for an mdtpw.toml (cargo-style). An explicit .pas bypasses it entirely — the backward-compatibility lock keeps every test invocation byte-identical.

Resources

Win16 .RES → COFF

A dedicated reconstructor (res16) rebuilds 16-bit .RES resources — bitmaps, icons, dialogs — into modern COFF resources the linker can bind, recovering assets the original binary tooling left behind.

09 · 16-bit-ism policy

Lower it, emulate it, or reject it.

Every 16-bit construct gets one of three verdicts. The policy is justifiable precisely because the corpus survey shows application code never touches the reject set — only the runtime library did, and the runtime library is replaced.

ConstructVerdictRationale
Pointer / PChar / ^T, @, AddrlowerFlat 32 — the only sane representation
MakeProcInstance / FreeProcInstancelowerIdentity / no-op — thunks meaningless when flat
export, far / near procs, {$F}lowerOne convention: stdcall, flat (D5)
ExitProc chain, unit init orderemulateObservable program behaviour — reproduce faithfully
Real arithmeticemulateAs f64 (D6) — dominates 48-bit, simpler
Seg / Ofs / Ptr, Mem, Port, PrefixSegrejectNo flat-32 meaning; absent from app corpus
inline asm … end, inline($..)reject16-bit machine code; only the (replaced) RTL used it
interrupt, MsDos / Intr, overlaysrejectDOS / 16-bit only — not Windows practice
Serialized / absolute width-changed structsrejectSizeOf changed (6→8, 16→32) — silent corruption otherwise

Rejections aren't silent — each is a precise, actionable diagnostic naming the construct and why it has no flat-32 meaning. Out-of-scope units (OLE, DDE, MMSystem, PenWindows, Paradox) still parse as a front-end safety net but carry no behavioural gate.

11 · The oracle ladder

The project lives or dies by its tests.

Every capability gates on a tiered oracle, written before the implementation. The gates harden as you climb — golden stdout for console programs, then real linkage, then a real headless Win32 message pump for GUI apps. Goldens are derived from TP 1.5 semantics, never captured from current behaviour.

What "headless GUI test" means assert_owl_headless_exit drives a real Win32 message pump with no display. The OWL program runs a deterministic self-script — InvalidateRect + PostMessage + a wm_Close terminator — so WM_PAINT and WM_COMMAND traverse the genuine pump, sentinel writes prove handler dispatch, and a clean exit code 0 proves the whole stack. M7 proved OWL dispatches end-to-end this way. There is no #[ignore] escape valve: an ignored test names a gap and the stage that owns it — ignored is never "closed".
