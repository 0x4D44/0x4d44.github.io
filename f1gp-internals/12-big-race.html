Inside Formula One Grand Prix Part II — The port

Chapter 12

What Big Race adds

The original runtime is the engine. Big Race is the car built around it: a native app that drops into an existing install, fits the 1991 picture to a modern window, and adds a few things the original never had. Every addition obeys one rule: it may read the game's state, but it never changes the race behind the game's back.

The one rule

Everything in this chapter is a host-side feature. The architecture guide states the contract plainly: each is a Big Race addition around the source runtime, and none writes source memory mid-race. The enhanced renderer reads state and redraws it. The window presenter scales finished frames. The recorder copies pixels and audio. Even the vehicle sets, which do change how cars drive, make their one change at startup, before the race begins, and then let the original simulation run unaided.

That rule is what keeps the oracle work of chapter 10 meaningful. If the original option is selected everywhere, the game you play is the game the tests compare against.

Native launch and drop-in behaviour

Big Race is one Rust binary, big-race. It is meant to be dropped into a player's existing game folder and started like the original.

  • No arguments means play. A drop-in replacement must not print usage when double-clicked. With no command, the binary runs play; with no path, it looks for the owned game files beside itself.
  • Case does not matter. DOS filenames were case-insensitive. The data inventory in src/native_game_data.rs finds files whatever case the install uses.
  • The packed executable wins. The original ships as an EXEPACK-compressed GP.EXE. Big Race unpacks it itself with a native decoder in src/native_exepack.rs. If an unpacked GP_UNPACKED.EXE also exists, the packed file is authoritative, because mod folders can hold stale unpacked copies that change the roster and the random number history.
  • The game's C: drive is the game folder. The original's file dialogs think in DOS drive letters. Big Race maps its virtual C: root to the drop-in game directory, never to the host's root.
  • Missing data fails loudly. Optional menu art is loaded before the window opens, and present-but-malformed data is an error with a message, not a silent fallback.

Two direct commands skip the menus: original-quick-race <path> starts a preset Quick Race, and jev-race <path> starts one with the experimental AI driver described below. Settings live in a per-user application directory. When the product was renamed from its working name to Big Race, the settings code gained new write paths plus read fallbacks for the old ones, so nobody lost their preferences.

Release builds are the way to play. Debug builds keep extra runtime checks and are much more CPU-hungry. During a race, the original's own D (lower detail) and T (track texture shading off) keys still trade visuals for speed.

The original-style menu

A normal launch opens the original menus, rebuilt from the player's own files rather than drawn from scratch. Labels, hit boxes and navigation come from records inside GP.EXE, parsed after EXEPACK decoding; if an owned record is missing, the menu fails closed. Backdrops come from the game's BACKDROP.DAT, text from the executable's own glyphs. Chapter 7 covers how those menus work.

The menu offers Quick Race, Practice, Qualifying, Non-Championship Race, Championship Season, Load/Save Game, setup, options, help and exit. Menu music plays the original ADLIB.CAT catalogue through Big Race's own OPL2 synthesiser model. When a session starts, the original sound interrupt takes over, and the menu music resumes on return.

Big Race owns exactly one slot in the original menus: the first control of the Options menu, whose label in the game's resource is already the product-owned "About Big Race". The original Options menu is defined by a resource and parsed against exact rectangles, so adding a new row would mean inventing original UI. Taking over the About slot does not.

Saves extend the original's. Pressing S during a session writes a complete native checkpoint, BIGRACE.STATE.SAV, and a 26,736-byte raw sidecar, BIGRACE.SAV, that the original GP.EXE itself accepts through its Load Game route. Championship checkpoints (BIGRACE.CSE) are written automatically after each round.

The Big Race options page

Options → About Big Race opens a page that holds the choices the original never had. It is drawn in the original's style, in the same 320x200 coordinate space, at 2x like every other options page.

Up and Down move focus, wrapping. Enter or Space cycles the focused setting. Pressing a row with the mouse focuses it, as on every other options page; hovering does not, because hover-focus would fight the keyboard. Each change is saved at once to a small companion file beside the main settings file:

The display settings are deliberately kept out of the structure that the original Options save writes, so they can never leak into the original's save format. A malformed companion file is reported on the console and ignored, and is not rewritten until the player changes a setting.

Window presentation

The original drew a 320x200 picture for a 4:3 CRT. VGA mode 13h pixels were not square: 200 rows filled the same height as 240 square pixels would. A modern window has square pixels and any shape. Big Race's presenter, src/native_window.rs, is the single owner of that last step. Nothing outside it hands a frame to the window library.

Always 4:3

Every screen reaches the window as a 4:3 picture, centred, with nearest-neighbour sampling. Screens are presented at the height they were composed: menus as 640x400, races as 320x200. The presenter alone performs the "tall pixel" stretch to 4:3. That replaced an older arrangement in which menus were stretched from 400 to 480 rows during composition and then scaled again by the window library, which quantised rows twice. At a 2x window a source row came out 4 or 6 pixels tall instead of 4 or 5.

Rows still cannot all be the same height. At 1280x960, 640x400 maps rows in a repeating 3, 2, 3, 2, 2 pattern (a 12:5 ratio). That is inherent to 200 rows on a 4:3 screen, and it is how the original hardware displayed them too. What integer placement buys is uniform columns.

Choosing the rectangle

The Scaling setting decides how big the 4:3 picture is:

  • Fit always takes the largest 4:3 rectangle that fits the window.
  • Integer takes the largest whole multiple of 640x480 that fits, falling back to Fit only if not even 1x fits.
  • Auto, the default, takes the whole multiple only when its width is at least two thirds of the Fit width. Otherwise it takes the Fit.

Pure integer scaling would show a 640x480 picture on a common 1440x900 laptop screen. The two-thirds rule avoids that while still preferring crisp integer steps when they are close.

The placement is keyed on a fixed 640x480 base, not on the width of the frame being shown, so the picture does not change size between the 640-wide menu and the 320-wide race. The cost, recorded in the design: when the Fit wins, as at 1200x900, race pixels are 3.75 points wide, so the integer-step promise holds for the 640-wide base rather than for every frame.

Scanlines

Scanlines darken one line per source row. The pass works in logical source rows (logical(y) = y × 200 / rect_height) and dims the last output row of each source row's run by a quarter, per channel v − v/4. That gives exactly one line per source row at any scale, and the same picture for a 320x200 race frame and its 640x400 menu doubling. A simpler "every odd row" pass was rejected because it beats visibly at the 12:5 menu ratio. Scanlines only appear when the picture has at least two output rows per source row; below that they would dim half the picture. They never reach recordings.

Mouse, fullscreen and macOS quirks

Alt+Enter toggles fullscreen. The presenter inverts its own mapping for the mouse, so a click lands on the source pixel under the pointer at any size, and a click in the border returns nothing. Getting that right exposed several quirks of the minifb window library on macOS:

  • Its reported window size updates only at the end of a live drag-resize. After a fullscreen toggle it is stale. Big Race reads the live content-view bounds itself.
  • It flips the mouse y using a frame calculation that assumes a title bar. In fullscreen there is no title bar, so every y was short by the title-bar height. A correction adds it back.
  • The existing fullscreen toggle called the Objective-C runtime through a variadic declaration. On Apple Silicon that passes the nil sender on the stack; it had only worked because AppKit ignores that argument. The declaration is now typed per message.
  • Before the rework, two mouse sites applied a 480-to-400 inverse to content that had never been stretched, so the Season Complete control responded about 40 rows below where it was drawn.

Hold loops, which wait on a static screen, now re-present on a size change, so a fullscreen toggle during a ceremony frame does not leave a stale, distorted picture.

The enhanced renderer

The original draws its 3D scene into a 320x164 canvas. Scaled up to a large window, polygon edges become staircases. The enhanced renderer, chosen with the Renderer row, redraws the whole race scene (sky and horizon, road, verges, kerbs, strips, trackside objects, cars, trees and signs) at the window's own resolution, with sharp straight edges. Original remains the default, and it is the only renderer that is a source oracle.

Why it cannot just render bigger

Three facts forced the design.

  1. The exact frame must always be drawn. The original renderer reads and writes game memory during a frame: it marks cars on road records, publishes scene state, uses bitmap scratch, and its pit-crew overlay consumes the shared random number generator. Skip or reorder any of that and the race desynchronises.
  2. The exact pipeline is fixed at 320x164. Its scan-line arena, edge rings and every rounding step assume that size. It cannot be handed a bigger canvas.
  3. Camera-space geometry is not recoverable in one place. The first design tried to tap road points before projection. Four independent reviews found that unworkable: projection receives track-space coordinates, two of its eighteen slots are derived rather than projected, near points keep the previous frame's screen words, and a fill's edge endpoints are carried across entries.

So the enhanced renderer does not re-project anything. It records what the exact renderer painted, in screen space, and paints it again bigger.

Recording the paint

The exact renderer accepts an optional SceneSink. When one is attached, every terminal drawing site, in parent and nested pit scenes alike, records one command in the order it paints. Coordinates stay in the original's 320x164 integer space.

The ordering claim was checked against the code: every writer in the exact pipeline is an opaque overwrite into one layer, in back-to-front order, with no coverage test. Replaying the sequence is therefore correct without a depth buffer. With no sink attached, the exact path pays one Option check per command and nothing else.

Painting it again

The rasteriser in src/enhanced_scene.rs maps each coordinate as x' = x × w / 320 and y' = y × h / 164, horizontally and vertically independent, and fills polygons with a scanline fill on floating-point edges. Per-pixel patterns, such as the sky dither and the road texture, sample the pattern at the corresponding source pixel, so they look as they did, only larger. Bitmaps use the original's own row-walk scaling rule with the geometry multiplied up, sampled nearest-neighbour, so sprites stay blocky and sharp. Output is palette indices, not colours, so palette fades apply once at the end and a palette-only change is a lookup rather than a re-render.

Composition

After the 3D scene is published, the original paints more on top of it: the map, cockpit strips, the pit crew, HUD, messages and pause text. None of those later passes updates the scene's publication mask. So the composer keeps a byte copy of the published scene and, for each pixel, uses the enhanced index only when the page byte still equals that copy, the mask marks it, the pixel lies inside the scene rows, and it is outside the two 48x22 mirror rectangles. Anything the original drew later wins. The cockpit, HUD and mirrors stay as the original draws them, nearest-scaled.

Two further details keep scene and page in step. The canvas sits at row 0 in the cockpit view and 16 rows down in external views, and that offset is captured at draw time because the original zeroes it before presenting. And the enhanced buffer is promoted from "pending" to "displayed" only when the original copies its page to video, so a palette update in between never mixes a new scene with an old page.

The enhanced width is capped at 1,280 pixels. Measured in a release build at 1280x960, a full composition plus a cached palette-only one took 1.7 ms, and sixty frames of simulation, exact render, replay and composition ran in about a quarter of a second.

How we know

With a sink attached, the in-repo Suzuka road fixture test passes unchanged, and an owned-asset race of sixty idle frames with the renderer on and off leaves byte-identical game memory while the composed frames differ. Replayed at the original 320x164 size, the recorded Suzuka scene has 0.21% "neighbourhood strangers" (pixels whose colour appears nowhere in the 3x3 neighbourhood of the exact frame), and every colour's pixel count is within three percent, with a 64-pixel floor for two thin horizon slivers.

The review found three real bugs, each fixed with a test made to fail once: the mask was indexed in page rows, so external views were sixteen rows off; a bitmap folded the vertical scale into the column step; and a pattern fill could paint the raw 0x1b sentinel colour where nothing had been recorded. The first live run composed nothing at all: the lower race buffer was the whole 64 KiB video segment rather than the 64,000-byte page, and a size check refused it.

What the milestone deliberately leaves out: integer vertices only (sub-pixel positions are a planned extension of the same commands), no smoothing or lighting, no high-resolution cockpit or mirrors, and recordings stay at 640x480. At the time of the journal the live-window look had not yet been checked by eye.

Vehicle sets

The Vehicles row picks who is on the grid: Original, Bangers or Monster Trucks. A set changes how every car drives, the player's and every AI car's, and swaps the car body the renderer draws up close. Original is the default and runs no code from src/vehicle_sets.rs at all. Everything a set adds lives in that module and its data, so the feature can be switched off by the setting or removed by deleting the module.

One seam: the decoded driving block

Each circuit file carries a 38-byte block of driving parameters. At every startup the loader decodes it into DS:0204..0229, and then grid initialisation, the driver ratings and the corner-speed calibration read it. It holds four scalars that reach every car, including the player's:

WordMeaning
DS:0216engine scale; thrust is fixed(fixed(fixed(0x16C9, torque), DS:0216), rating)
DS:020Etyre grip scale
DS:0218wing scale
DS:0222performance spread

The same block holds the AI cars' shared setup record: front and rear wing, six gear ratios, tyre compound and brake balance. A set is a DrivingOverlay applied to this block right after it is decoded and before anything reads it. Nothing touches game memory during the race; the original simulation drives the new cars with its own code.

Bounds from the original's arithmetic

The original multiplies in fixed point: fixed(a, b) = a × b / 0x4000, so 0x4000 is 1.0. The overlay type refuses to be built outside a set of bounds drawn from that arithmetic. Engine scale stays at or below 1.0, because the design review found that a scaled word at or above 0x4000 wraps negative. Grip scale stays at or above 0.6, because the AI corner solver divides by grip in a 32/16-bit divide whose overflow is swallowed and reads as "no corner limit". The code is candid that the grip floor is a heuristic, not a proven invariant: it is where a 9,000-frame Suzuka measurement found zero faults, not where the arithmetic is known to break. The other scales are capped at 2.0, and the AI setup record is validated (wings 0..64, non-zero gear ratios 16..80, compound 0..5).

Tuning the field

The first guesses were wrong in instructive ways. Bangers started with tall gears: the field crawled off the line into each other and up to five cars retired where the original loses one. Raising banger grip to 0.8 made it worse, so grip was not the cause; short gears fixed it. Monster trucks started at full engine. With the wing cut, drag went too, and at 9,000 frames the trucks outran the Formula One field. Pace is now measured as the computer field's laps completed rather than peak speed, because one spin makes peak speed noise. The final runs had no retirements and no corner-solver faults. The player's truck still tops the F1 car by about five percent on the straight, which the journal calls "the joke".

New bodies, old billboards

Each set also brings a polygon car body, a boxy saloon for bangers and a cab on a tall chassis for trucks, encoded in the original's shape format and checked by parsing it back. The shape cannot replace the original in place: the renderer re-copies the whole 0x8800-byte shape segment from live memory every frame, and shape 0 is already the longest with about 252 bytes of headroom. So the new body is appended past the segment and the table entry for shape 0 is re-pointed after every copy. The body's last detail record is the original's own far billboard, copied from the player's shape 0, so distant cars and mirror reflections still show the Formula One sprite. That is an accepted oddity until new sprites exist.

Where a set does not apply

  • Linked races always run Original. Both machines must simulate the same grid, and the peer carries no set. The race says so once on the console.
  • Saves record the set. A native session save made under a set is refused under another, with a message naming both. The original's own SAVE GAME file carries no set and loads only under Original. An Original save keeps its old layout byte for byte; only a set writes the newer version.
  • Championships. Until 2026-09-23 a Championship season ran Original throughout, because its checkpoint had no place to record a set. A change on that date records the Vehicles setting in the season checkpoint when the season starts, races every weekend with it, and refuses to resume under a different set, by name. An Original season still writes the old checkpoint layout byte for byte. The README's description still reflects the earlier behaviour.

Recording

Pass --record to capture everything the window shows, menus and races, with audio, as a Matroska file with VP9 video and Opus audio. It works with the menu route and with original-quick-race. The file goes to the user's Videos folder (Movies on macOS) as YYYY.MM.DD - big-race.mkv; an existing name gets a numbered suffix.

Recordings are 640x480, sampled from the composed frame by the same nearest-neighbour sampler as the window, with 48 kHz stereo audio. Scanlines never reach them. The encoder itself lives in a shared crate from the emulator project; Big Race owns the clock, the frame sizing and a non-blocking tap on the menu music, so the game loop never waits for encoding.

Modem multiplayer

Big Race runs the original's own linked protocol between two machines, through two virtual modems that exchange 16 kHz modem audio over TCP. Game packets never cross the socket; only modem sound does. On a local network, Wait For Call advertises a session on UDP port 47771 and Dial finds and claims it, with no address typed in. With sound on you hear the original dial, answer, training, carrier and hang-up audio. The original runtime owns packet framing, retries and Link Options; sockets and threads never enter the game's memory, and saving is refused during a live linked session. Chapter 8 tells the whole story.

The experimental Jev driver

One addition is openly an experiment: handing the steering to an external AI model, TypeSafe's Jev, while the race stays visible and runs at normal speed. It starts with jev-race <path> for a direct Quick Race, or --jev to keep the normal menus. It needs the user's own access to that service, which stays inside the process and is never passed on a command line.

The integration holds the throttle and enables the original game's Auto Brakes aid for that session only, leaving the saved driver-aid preference untouched. It sends compact telemetry read from the runtime, not screenshots: the car's signed distance from the ideal line as a percentage of track half-width, its angle to that line in degrees, and a preview of the driving line whose range and point count grow with speed. Jev chooses, at a slower rate, between the ideal line and a temporary 25-percent left or right avoidance target. A local controller blends toward that target and turns the line geometry into proportional digital steering pulses every frame, as ordinary key make and break edges. The window title shows each accepted decision, the local steering, the latency and the confidence.

The game loop never waits for the model. While a request is in flight it keeps the last control, replaces queued telemetry with the newest frame, and rejects replies older than two seconds. The player's own steering keys are ignored while Jev drives; Escape still leaves the race normally. Two small lessons came out of it: the racing line's heading word can flip by 180°, so it is folded to ±90° before steering, and the HTTPS client is native Rust, so the feature needs no Python runtime.

Authored circuits

Big Race adds two circuits the original never had: Bahrain and Madrid, entries 17 and 18 in the extended catalogue. They run on the original Quick Race runtime with their own track data. Their lifecycle (startup, driving, pit, retirement, finish, escape and relaunch) is tested separately from the evidence for the original sixteen circuits.

They are built by a second binary, track-author, which compiles a frozen source package into a complete original-format track file offline. It fits the main and pit section streams, emits the racing line, named car parameters and loader tail, and adds authored shapes, scenery settings and placement commands. It has no network access and reads no game assets. Accuracy has explicit bounds: the main path's ordered error must be at most 2.5 m at the 95th percentile and 5 m at worst, and the pit path's 2.5 m and 6 m. A track record in this format is 4.8768 m long.

Bahrain's centreline comes from OpenStreetMap, under the Open Database License, with the request, date and snapshot hash recorded. Madrid's comes from the city's geoportal snapshot through a separate, explicit fetch script that builds never run. Elevation, width and corner landmarks are the project's own estimates, kept apart from the source data and labelled as assumptions. The authored preview palette is used only in the track picker; the race itself uses the original executable's palette.

Authoring taught its own lessons about the original's track format, several of which are in chapter 11's spirit:

  • Polygon colours are shade-row indices, not palette bytes; flat objects have sixteen entries, and Bahrain's first shapes vanished because their colours indexed past that row.
  • An object distance of 256 is one road half-width, not a world unit. World-unit offsets put Bahrain's scenery 12 to 48 half-widths away and out of view.
  • Packed track curvature is scaled by π/2: the previous record receives (boundary_delta × 0x6488) >> 14, not a heading increment.
  • A racing line with zero radius skips the corner-speed setup entirely. Bahrain passed its path checks with every corner-speed word still at its seed value.
  • Pit entry needs section mode bits, entry, through and exit as 1, 3 and 2; pointers alone do not enable a route. And the pit service window must contain its line patch: a 96/128 window skipped Bahrain's whole 87–98 service patch.
