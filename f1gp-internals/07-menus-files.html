Inside Formula One Grand Prix Part I — The original

Chapter 07

Menus, files and saves

Before the race there are menus, and around it there are files. The game keeps every menu as a small data record inside its own executable, paints it over a backdrop from a picture archive, and writes its own fonts. Its save files carry no names or headers: the game knows them by exact length and a four-byte checksum. This chapter takes each piece apart, and shows how the port rebuilt the menus pixel for pixel by reading them straight out of the player's copy of the game.

Menus are data inside GP.EXE

F1GP does not draw its menus with hand-written code for each screen. Each screen is a resource: a block of bytes inside GP.EXE that describes a panel, a title and a list of controls. One general routine draws any resource and runs its keyboard and mouse input. The Main Menu, the Options pages, Driver Select, the file selector and the rest are all this one shape with different numbers in it.

The executable on disk is packed with Microsoft's EXEPACK. The port has its own EXEPACK decoder (src/native_exepack.rs). On the owned copy it rebuilds the 600,848-byte unpacked image byte for byte: the raw image prefix, the backward literal and fill runs, all 1,306 relocations, the ordinary MZ header and its checksum. The unpacked image lives only in memory; nothing is written back to the install.

The shape of a menu resource

Take the Main Menu as the example. Its resource is laid out like this:

  • An 18-byte header. After a leading word, it holds the control count (9), a zero word, the panel's left, top, right and bottom edges, and two more words.
  • A 5-byte descriptor giving the title's screen position.
  • The title string, zero-terminated.
  • Nine 24-byte control records, one per row.
  • The row labels as consecutive zero-terminated strings, which the control records point at.

The neighbour bytes are the menu's navigation graph. Each arrow key follows one link, and 0xFF means "nowhere". Because the links are stored per control, a menu can have any shape: a single column, a grid, or two buttons side by side at the bottom of a column.

Finding a menu without an address

The port never hard-codes where a menu lives in the executable. Each parser, one per screen in src/native_original_*.rs, searches for the screen's title string. It requires exactly one match, walks back over the descriptor and header, and then validates everything: the header words, every rectangle, every label pointer, every metadata word and every neighbour link. Zero matches is "not found". Two is "ambiguous". Anything malformed is an error, and the app refuses to start rather than draw a menu it cannot vouch for.

This strictness pays off in odd places. RACE OPTIONS also appears inside QUICK RACE OPTIONS, so its parser has to validate candidate structure rather than trust the string. And because the parser reads what is actually there, it works on modified copies of the game. A season pack called GP1998 changes the roster; parsing its packed GP.EXE in memory turned up team slots with more car numbers than names. The port's first rule had rejected that. The rule was the port's own assumption, not something the original enforces, so it was relaxed.

The trap

The header's four panel values look like x, y, width and height. They are left, top, right and bottom. The Options menu header reads 0x20, 0x08, 0x120, 0xC0. Treated as sizes, the panel ran to the screen edges. Read as edges, it is a 256 × 184 panel at (32, 8), and the frame then matched the original exactly. The Main Menu and the Load-Save menu share one panel: left 48, top 4, 224 wide and 192 tall.

How we know

Every recreated page is checked against a capture from the original game running in the mdpc emulator. The port renders the page at the original 320 × 200, converts it through the palette, and hashes all the RGB pixels. The only pixel excluded is the parked mouse cursor in the bottom-right corner — 63,999 of 64,000 pixels must match. Each test was first run against a deliberately wrong digest to watch it fail, and direct pixel comparison was used to find what differed. That is how the port learned, for example, that the Race Options page defaults Opposition Standard to Rookie, not the assumed Ace.

Focus, choice and navigation

The first thing a new player sees is a language dialog with three flags: English, Français and Deutsch, and an O.K. button. It is a small screen with an idea that the port got wrong at first: the focused control and the chosen language are separate things.

The graph comes from the executable's neighbour links. Left and Right move among the flags; Down from French reaches O.K.; Up from O.K. returns to French. Activating a flag chooses that language. Activating O.K. accepts it. So English can stay drawn as the pressed blue choice while French, or O.K., carries the red focus highlight. The original frames for "French focused, English chosen" and "O.K. focused, English chosen" each have their own digest, and the port matches both.

The flags hold a subtlety too. Their images have transparent pixels, but the dialog first clears each 39 × 28 rectangle to palette index 0 (black) and only then skips the transparent pixels. Compositing them straight over the blue panel looks almost right and is wrong: the black flag borders and Germany's black stripe depend on that clear.

After the language dialog comes a two-row Startup menu — Quick Race above Main Menu, with Quick Race focused — and then the nine-row Main Menu. None of these menus wrap: the executable's graph has no link from the last row back to the first.

Backdrops and pictures

Behind every menu is a full-screen picture. They come from BACKDROP.DAT, which holds 36 records arranged as 18 pairs. In each pair the first record is a 256-colour palette and the second is a 320 × 200 screen. A menu screen always uses its pair's palette, not the race's, which is why result pages drawn over a race still show the menu's colours.

The trap

The port's first menu backdrop used records 6 and 7 — pair 3 — on every page. It looked like a plausible title picture. It is the language screen's backdrop. The fix came from an oracle, not an opinion: with the original running, the uncovered 32-pixel strips at either side of each menu were compared against all 18 decoded pairs. The language screen matched only pair 3. Startup and Main matched only pair 15, with no error at all. Setup Options was later caught the same way: it too is pair 15, not pair 3.

Circuit previews and other archives

TRACKPIX.DAT works the same way with 17 palette-and-screen pairs. Pairs 0 to 15 map directly onto the sixteen circuit files F1CT01.DAT to F1CT16.DAT, and are the previews shown when a circuit is chosen. The seventeenth pair is not a circuit. It is the fixed landscape behind the Select Circuit grid. An earlier note in the project had concluded that the exposed background there was not from TRACKPIX at all; a later full-frame comparison matched pair 17 at all 11,296 exposed pixels, and the port now keeps that pair instead of discarding it.

Other archives in the same container format include FLAGS.DAT (six records; the first three are the language flags), HELMETS.DAT (39 helmet pictures used on the Driver Select detail pages), and the two ceremony animations, CHAMP.DAT (23 records) and TROPHY.DAT (17 records). Across the nine archives in the owned install, the port validated 34, 36, 6, 39, 23, 31, 29, 33 and 17 records, every one with a gap-free layout and no trailing bytes.

The f1pcanim container

All those picture files share one container. It starts with the eight ASCII bytes f1pcanim and a u16 record count. A directory of 14-byte entries follows. Each entry gives a record type, a u32 payload offset, a u32 payload length, and the image's width and height. The payloads follow the directory with no gaps: the first begins where the directory ends, each next one where the last ended, and the last ends at the end of the file. The port's parser, src/pc_animation.rs, rejects any gap, overlap or leftover byte.

Palettes

A 0x06f0 record is exactly 768 bytes: 256 red, green and blue values in the VGA DAC's six-bit range, uploaded by BIOS call AX=1017h. The port rejects any component above 63. To show a six-bit value on a modern screen it expands it to eight bits as (v << 2) | (v >> 4), which maps 0 to 0 and 63 to 255.

Byte runs

Types 0x06e8 and 0x06ee share one run-length codec. Read a control byte c:

  • 0x00–0x7F: copy the next c + 1 bytes literally.
  • 0x81–0xFF: repeat the next byte 257 − c times (from 128 down to 2).
  • 0x80: never seen; the port treats it as an error.

The expansion must come to exactly width × height bytes. On the owned install, the port expanded all 166 byte-run records this way — 121 screens, 39 helmets and six flags — and every one ended exactly.

The trap

Each 0x06e8 record expands to a full 64,000 bytes, so it looks like a complete picture. It is not. The original XORs every expanded byte over the existing screen. A zero therefore means "leave this pixel alone" — it is the identity of XOR, not a transparency colour. An animation is a keyframe followed by a chain of XOR deltas. The Championship ceremony in CHAMP.DAT is two such chains: records 1 to 7 are the podium scene, and records 9 to 22 are the champagne. The winner's sequence shows records 1 to 7 seven times, then record 1 again, then the champagne frames.

The LZW-style screen codec

Type 0x06e9 is the keyframe codec, and it was the last to be understood. It is a dictionary coder in the LZW family, with a twist: the dictionary does not hold strings, it holds places in the output already decoded.

Tokens are 12 bits, packed two to every three bytes. The first token takes the first byte plus the low four bits of the second; the second token takes the high four bits of the second byte plus the third byte.

Decoding runs like this. The first token must be a literal byte. The dictionary's entry 0 is then set to "offset 0, length 2". For each further token, a value below 0x100 emits one literal byte; a larger value looks up entry token − 0x100 and copies that many bytes from that earlier position in the output. Either way, a new entry is written: the position where this step's output started, with a length one greater than what was just emitted. That is the classic LZW rule — "what I just said, plus the next byte" — expressed as a pointer back into the image. The entry index wraps round at 3,840, which is exactly the number of 12-bit codes left once the 256 literals are taken.

The copy runs forwards one byte at a time. When the source and destination overlap, the copy repeats bytes it has only just written, which is how a long run of one colour compresses. The port copies in the same order on purpose. It validates the whole stream before it touches the output: an uninitialised dictionary entry, a reference to output that does not exist yet, or leftover tokens are all errors.

Fonts and icons from the executable

The menu text uses the game's own fonts, and they live in GP.EXE, not in a data file. The port bundles none of them. It finds them at launch by their structure, in src/native_original_font.rs:

  • The proportional font is 96 glyphs, one for each ASCII character from space upwards, eight rows each with the most significant bit on the left, plus a 96-byte table of advances. The finder looks for an advance table whose first entry (the space) is 4 and whose others are all between 3 and 9, then searches up to 4,096 bytes before it for a glyph bank whose shapes fit those widths. The match must be unique.
  • Beyond the ASCII range the same bank holds icons. Glyphs 0x8A and 0x8B are increase and decrease arrows, 0x8C and 0x8D previous and next, 0x8E and 0x8F page up and page down. All six have an advance of 8. Glyph 0x9D is a degree sign, and ten small digits start at 0x91.
  • The title font is a separate object: 27 descriptors for A to Z and the hyphen, each giving a width, a height of 12 and an offset to row-major pixel bytes. Zero is transparent; other bytes are already-shaded palette indices, so the bevelled look is baked into the font.
  • A separate fixed-width digit bank, ten digits of eight rows, draws numbers on some pages. The proportional font's digits look visibly different.

Drawing uses simple palette tricks. A normal row label is drawn three times: in index 4 one pixel up and left, in index 8 one pixel down and right, and in index 15 at its true place. The selected row uses indices 19, 21 and 15. Main Menu labels sit at y = 33 + 18n. The title MAIN MENU sits at (116, 12); drawn glyphs advance by their width plus one, and a space by four. Replaying that draw gave 636 non-transparent pixels, and every one matched the original screenshot.

From the port

Before the fonts were found, the port drew menus with its own 3 × 5 pixel font, and it still does if GP.EXE is missing. The first check that the real font had been found was a measurement: the label Driver/Team Selection is 162 source pixels wide in the proportional font, which is exactly what its x = 79 position on screen requires. The icons had a similar moment. The Select Circuit arrows look like drawn triangles; they are font glyphs 0x8C and 0x8D.

The Startup Files page shows how the executable and the preferences file line up. It offers three files to load at start-up — driver names, setups and circuit records — each with a Yes/No and a filename. The three filename buffers are 32 bytes apart, both in the executable's initialisers and in F1PREFS.DAT, which suggests 31 characters plus a terminating zero. The port treats that input limit as an inference, because no available trace shows anyone typing into the field.

Credits

The original's About entry opens two Credits pages, and those too are resources in GP.EXE: twelve text records per page, each with its text, position and palette colour, plus button labels, rectangles and neighbour links. The panel is 256 × 200 at (32, 0) over backdrop pair 15. The port recreated both pages exactly on 2026-09-01. On 2026-09-19 it replaced that route with its own About page, to keep the original credit text out of release builds, and on 2026-09-22 the same slot became the Big Race options page (scaling, scanlines, renderer and vehicles). The Options resource is untouched; the port only re-routes the one row it owns.

Driver and team selection

Driver Select is the most intricate menu. Its resource has 19 controls: nine rows of two team columns, an O.K. button and a driver-number pane. It is drawn over backdrop pair 5 with the separate fixed-width digit bank for the car numbers. The team names on the list come from an 18-entry, 13-byte alias table in the executable.

Behind the list sits the roster, also resident in the executable: 40 car numbers, 40 driver names of 24 bytes each, and 20 team text slots of 13 bytes. Only 18 teams are real; the last two slots read "Not Used". The same data area holds per-team performance words and a driver ranking that the race uses to seed and cut the field — see Chapter 03.

Choosing a team opens a detail page with helmet pictures from HELMETS.DAT. From there the player can select or deselect drivers, and edit driver, team and engine names. A few rules are exact:

  • The selection is a set of zero, one or several drivers, not a single car.
  • The first typed character overwrites the whole field. Driver names cap at 19 characters and accept only the original character set. Enter commits; Escape cancels in place.
  • An active field shows a 2 × 8 caret just after the measured text, alternating black and white.
  • Escape is a page stack: detail and confirmation go back to the list, the edit page goes back to detail, and Escape on the list leaves without committing anything. Only the confirmation action writes the staged names into the live roster.

F1GPDATA and F1GPDATB

The race's object pictures — trees, signs, marshals and the like — live in a pair of files that act as one bank. F1GPDATA.DAT starts with a directory of little-endian u32 entries. The first entry is both the offset of the first record and the byte length of the directory; on the owned install it is 0x398, which means 230 entries. Bit 31 of each entry picks the bank: clear means the record is in F1GPDATA.DAT, set means it is in F1GPDATB.DAT, and the remaining 31 bits are the offset. IDs 0 to 136 use the first file and IDs 137 to 229 the second. How those bitmaps are drawn belongs to Chapter 05.

The file selector

The Load-Save menu lists seven operations: Load Game, Load and Save Track Records, Load and Save Names, Load and Save Car Setups. There is no Save Game row in the menu the player can reach — more on that below. Every operation opens one shared file-selector resource, with the operation's title supplied by the caller.

The selector lists regular files from the game's GPSAVES directory, sorted without regard to case, twelve to a page. It pages with the 0x8E and 0x8F icons, and because paging counts in pairs, an even number of files stops one row earlier than you might expect. Focus starts on Cancel. Clicking a file fills it red and copies its name into the Filename field. The Parent, Root and drive buttons A: to D: move between directories.

Two details reveal how the original thinks about files:

  • Filenames are arbitrary. There are no fixed extensions. A Names file can be called anything.
  • Filter works on contents, not names. With Filter on, the selector lists only files whose length and checksum fit the operation. With No Filter it lists everything.
How it works

A DOS game can see the whole disk; a port should not show the player's entire computer. The port maps the virtual C: drive and its root to the game directory, not the host's root. A:, B: and D: stay on screen with their original DOS paths but list nothing when no drive is mapped. Parent from GPSAVES still reaches the game directory, so files kept beside the game remain loadable.

Save files: length plus checksum

Three kinds of file are simple copies of a block of the game's memory with four bytes added. The game recognises them by exact total length and a valid trailer, and by nothing else. It does not check names, circuit numbers, setup values or padding.

The checksum is two 16-bit words. The first is a plain wrapping sum of the body bytes. The second starts at zero and, for each byte, rotates itself left by three bits and then adds the byte. The rotation makes the second word sensitive to byte order, which a plain sum is not. The same two-word checksum protects F1PREFS.DAT, whose body is 0x48A bytes.

The trap

It is tempting to make a loader "safer" by checking that names are printable or circuit numbers are in range. For these files that would be wrong. The original accepts any body with the right length and trailer, so a stricter port rejects files the original accepts. The port's classifier checks exactly what the original checks and no more. Its Names decoder does the same kindly: it bounds each string to its slot, ignores bytes after the first zero, and substitutes unsupported display bytes rather than failing.

Track Records

The lap-record table holds 16 circuit records of 90 bytes. Each starts with a u16 circuit ID, then two 44-byte lap records, one for qualifying and one for the race. A lap record is a 24-byte driver name, a 14-byte team name, a u32 lap time in milliseconds and a u16 date, counted in days from 1978. Saving copies the 1,440-byte table from 2914:2312.

Loading does not replace the table; it merges it. For each circuit ID in the file, the game finds the first matching live circuit and compares the qualifying and race times separately as unsigned 32-bit numbers. Only a strictly smaller time wins, and then the whole 44-byte lap record is copied, name and date included. Equal or slower times leave the live record alone. So loading a friend's records file can only improve your table.

Names and Car Setups

A Names file is the three name tables back to back: 40 driver names of 24 bytes, then 20 team names of 13 bytes, then 20 engine names of 13 bytes. Loading replaces the live tables. The port has one extra obligation here: any in-progress edits from the Driver/Team pages must be committed to the live roster before Save Names serialises it.

Car Setups is a 322-byte image of live memory at 2914:1416: a two-byte header followed by 32 ten-byte setup records. The port keeps it as an opaque block and preserves every byte, including ones it does not understand. The port's own simple setup model, used by early clean-room races, could never have represented it.

The shared save writer has its own small rules. If a file of the expected size already exists, it offers Replace without first checking that file's checksum. If a file of another size is in the way, it refuses with SAVE ABORTED. Result dialogs size themselves from their text: the width is (max_width / 2 + 15) & ~7, doubled and centred on x = 160. TRACK RECORDS LOADED produces a 256-pixel panel; CAR SETUPS SAVED a 192-pixel one.

SAVE GAME: a snapshot of the race

Saving a race in progress is a different kind of file. It is not a fixed table. It is a snapshot assembled from three separate memory ranges, written into a temporary buffer at 381C:4C38, with the same four-byte checksum added:

The body is 0x686C = 26,732 bytes: the stack range (3,574 bytes), the data range (8,228) and the scene range (14,930) in that order. The file is 26,736 bytes with its trailer. The front of the body is a scene header. It records the circuit, race distance, weather and linked-mode flag as little-endian words. The word at offset 0x16 is not the player's car number, as it first appeared; it is an operation selector. The SAVE GAME route writes 1, and the Championship's own "continue the race" path writes 2 and restores the same three ranges.

Loading is different from the three fixed types. The original Load Game routine does not have one fixed size. It derives two accepted lengths at run time from SS:04BE and SS:04C0, allows two-byte variants of each, and hands the data to a separate Load Game subsystem. That is why the port first deferred it rather than treat it as "one more fixed-size file". A checksum-valid buffer is not the same as a restorable game.

The trap

The port's first raw-save writer copied the three ranges in the right order and computed a correct checksum. The original game's Load Game said GAME LOADED — and then LOAD FAILED / Invalid Data. The team swapped pieces between a known-good original save and the port's save, range by range and in combination; every swap reproduced the failure, while mutating header words did not. That separated "the file is well-formed" from "the state inside it is right". The missing step, found in the writer at 15F2:C5E0, was two stores made before the copy: DS:096B = 0x4813 and DS:096D = 0x381C. In the port's first files those four bytes were zero. With the seeds in place, the original GP.EXE loaded the port's file and reached the restored race frame.

There is one more surprise. In the Load-Save menu the player can actually reach, there is no Save Game row. The port offers saving through a key instead (below), and still writes the original format so the original game can read it.

The port's own files

The port adds files of its own, all kept separate from the original formats so that neither is ever mistaken for the other.

FileWhat it holds

Magic MDF1GPS and a version word; the session mode and vehicle set; grid position, circuit, car number, distance, weather and linked flag; a checksum of the resident image before live start-up; then the full canonical memory image, the lower-screen image and the XSOUND image, and a two-word checksum.

Load Game in the port accepts all three kinds of save file. It tries the port's session checkpoint first, then the Championship checkpoint, then the original SAVE GAME format with its scene header, operation selector and checksum. A malformed or incompatible file is rejected before the live game is touched.

The version numbers carry a small courtesy. When vehicle sets arrived, the session checkpoint spent a pad byte that was already zero on the set, and the Championship checkpoint appended one byte. In both, a save made with the Original cars is still written in the older version, byte for byte, and still loads in a build that predates vehicle sets. Only a Bangers or Monster Trucks save uses the new version number.

Preferences follow the same "original first" rule. At the first Escape hand-off from the menu, the port reads F1PREFS.DAT, checks its body against the two-word checksum, and applies the driver-aid byte at body offset 0x478. A missing or invalid file leaves the executable's built-in default in place, and an explicit setting in the port's own file still wins.
