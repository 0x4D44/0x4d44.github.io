Inside Formula One Grand Prix Part II — The port

Chapter 11

Field notes

The project kept a running file of lessons: every time a wrong belief cost real time, the correction was written down with the code it touched. This chapter retells forty-one of them as short stories: the trap, what we believed, what settled it, and the rule we kept.

How to read these notes

The lessons file, lessons_learnt.md, is written newest first. Each entry has a one-line nugget, which is injected into every new working session, and optional detail below it. It held 308 entries before a prune on 2026-09-23 cut it to 259. That prune dropped entries whose code had been deleted and merged near-duplicates, including a handful of entries headed "WRONG" or "SUPERSEDED": corrections to earlier lessons. Several of the stories below come from those removed entries, recovered from the file's history.

Addresses follow the conventions in chapter 10. 15F2:XXXX is the graphics segment as the disassembly listing names it; 0752:XXXX is the main code segment; 19ED:XXXX is the track expander overlay; bare hex such as 0x90a94 is a file offset in the unpacked executable.

The notes are grouped under five themes. Most notes could sit under two.

Reading the binary

Disassembly is a map drawn by someone who has never visited. These notes are about the places where the map and the territory disagreed.

1. The writer you cannot find

The trap. We needed to know which code writes the track expander's scene tables. Static scans of the disassembly for stores to those offsets found a small set of candidate sites.

What we believed. A lesson was written: "expander scene-data writers are only 5 sites".

What settled it. Fourteen breakpoints on the candidate sites never fired. The real builder of the wall table at scene 0xb6 writes through an ES register loaded long before the store, which no "segment switch" signature catches. Absolute, BP-relative, SS-prefixed and immediate-load scans had all failed the same way: F1GP sets its data structures through pointers it computes at run time, so static scans find the readers and never the writer. The lesson was marked WRONG and withdrawn.

The rule. Static scans find readers. To find a writer, arm a write watchpoint on the byte and let the game tell you.

2. The instruction the disassembler never showed

The trap. A whole-file disassembly is convenient. It is also misaligned wherever code sits next to data, because the disassembler cannot tell where an instruction starts.

What we believed. Nothing wrote track record byte +0x1f, the wall flags. The disassembly had no such store.

What settled it. Disassembling again from a known instruction start revealed or [es:bx+0x1f],1 at file offset 0x90a94. The "nothing writes it" conclusion had come from reading garbage decoded out of phase.

The rule. Disassemble from a known instruction boundary, and treat "nothing writes it" from a whole-file listing as unproven.

3. Same offset, different segment

The trap. In 16-bit code, [0x1c0] means offset 0x1c0 in whichever segment DS holds at that moment. Most routines use the frame's data segment. Some do not.

What we believed. The polygon fill's tables were "unidentified": a full working session dumped the game data segment 25B3 and found nothing that made sense. Separately, a dump for the mirror code returned plausible, non-zero words.

What settled it. The fill runs with DS = 381C, the scene data segment. The mirror code does mov ds,[ss:X] part-way through and switches to 25B3, so its plausible words came from the wrong table. The sharpest example: routine 3043 reads [0x1c0] in scene data, where it holds 0x20, while routine A749 writes game-data 25B3:0x1c0. Same offset, two unrelated variables.

The rule. Confirm which segment a routine runs under before reading its globals. Read the [ss:X] it loads from before you dump anything.

4. Find callers by arithmetic

The trap. We needed the code that finishes drawing a polygon after clipping. Reading about 3 KB of surrounding disassembly had not found it.

What we believed. Understanding the code around the clipper was the way in.

What settled it. A near call is E8 followed by a 16-bit displacement equal to target − (site + 3). The segment base cancels out of that sum, so you can scan the file for every call to a routine without knowing where it loads. Scanning for calls to the clipper at 15F2:0E59 gave one hit, inside the element drawer, and located the polygon tail in one step. Later a scan missed the mirror blit, because that is a far call into the 19ED overlay from inside the sky stage. A related trick found the track expander itself: one scan of the 600 KB file for the unique pair CWD; IDIV landed at file 0x90a5c.

The rule. Scan for call sites, near and far, before reading. Search by a unique opcode signature rather than trusting a cited address.

5. A file offset is not an instruction pointer

The trap. Comments in the port cited addresses in mixed spaces, and some labels for "unported" routines were plain file offsets.

What we believed. That a label such as 1469F named the routine at 0752:469F.

What settled it. Checking the caller's actual call bytes. File 1469F is not runtime 0752:469F, and file 1228E is not 0752:228E. Other citations failed a simpler test: the camera comments cited 8C53, which is the middle of an instruction, and 8D6A, which is aligned but turned out to be buffer zeroing, not trigonometry.

The rule. Resolve the code bank and inspect the caller's bytes before porting a named boundary. Check a citation lands on an instruction boundary before you trust it.

6. A latch is not a reprogramming

The trap. The PC's programmable interval timer is controlled through port 0x43. Writing 0x00 there latches the counter for reading; writing 0x36 programs a new mode and rate.

What we believed. Looking only at the latch sites, that the game never reprograms the timer, so the tick rate was the BIOS default.

What settled it. Reading every write to port 0x43 and decoding its control byte. The game programs divisor 3977, found at file 0x6D3B3, which gives 300.02 Hz. The main game tick runs on every sixth interrupt: exactly 50 Hz.

The rule. Decode the control byte of every port write. A read path and a write path through the same port are different stories.

7. Control flow that reads one way and runs another

The trap. Two small pieces of the track expander looked obvious. A loop ending near a ret looked finished. A sub after a call looked like a step backwards.

What we believed. That the loop returned, and that the sub moved the marker back one place.

What settled it. The loop at 19ED:57D0 falls into a trailing walk that clears forward until byte +0x22 has a bit set; skipping it left about 13 records dirty. And the routine called just before the sub, at 19ED:577C, contains an add of the same amount, so the pair nets to zero and the next mark reuses the value.

The rule. Follow a loop to its real exit, and read a callee's side effects before interpreting the arithmetic at its call site.

8. One eighth of the accesses

The trap. To find every access of the form [reg+disp16], a scan searched for ModRM bytes 0x84 to 0x87.

What we believed. That those four bytes covered the addressing form.

What settled it. Those are only the forms whose register field is zero. The full set is 0x80 | (reg << 3) | rm, so the scan found about an eighth of the accesses.

The rule. When scanning machine code, derive the byte set from the encoding, not from the first example you saw.

Measuring versus believing

The second theme is the gap between a plausible explanation and a measured one. Most of these cost an entire working iteration before a single measurement ended them.

9. Stop looking at crops

The trap. Comparing the port's cockpit frame with the original by zooming into 4x crops of the two images.

What we believed. Two diagnoses, both from eyeballing: "the icons have a palette swap" and "the text has shifted one column". Two more iterations of colour histograms and per-row analysis produced a third wrong cause.

What settled it. Rendering the whole frame with the real palette and counting pixels by colour pair killed both diagnoses. Viewing the two full images side by side named the real cause in one step. A difference map (red where pixels differ, the original dimmed elsewhere) then ranked the residual as separate items: crowd, gantry, barrier, car outlines, mirrors and HUD text.

The rule. Render the whole frame with the real palette, diff it, and measure before naming a cause.

10. Count that the new code runs

The trap. The port had two polygon walkers. New work kept going into one of them.

What we believed. That the walker being improved was the one the renderer used.

What settled it. Counting calls. Two iterations had gone into the walker the renderer never called. Worse, the port's faithful polygon fill refused any polygon whose lowest point was a single vertex, so a fallback painter was doing most of the drawing and nothing said so.

The rule. Count that new code runs before debugging why it does nothing. A silent fallback hides how little of a port is live.

11. A number that does not move

The trap. To measure how much the trackside objects contributed, a test rendered the frame without the track table.

What we believed. That the difference, 40,524 pixels, was the objects' contribution.

What settled it. The whole road stage is gated on the track table, so removing the table removed the road, not the objects. Holding the road constant and blanking only the object class gave the true figure: 1,446 pixels.

The rule. A score that does not move is not proof a stage is inert, and a score that moves is not proof it measured what you meant. Hold the other stages constant and diff pixels.

12. A worse score is evidence

The trap. A change made the oracle score drop. The natural reaction is to explain the drop away.

What we believed. For a whole iteration, that a large polygon flooding the frame was "the grandstand", drawn a little wrong.

What settled it. Dumping its outline. One vertex was 17,648 pixels off screen. It was garbage geometry, not a grandstand.

The rule. A change that lowers the oracle score is evidence, not a cost to explain away.

13. A better score can be wrong too

The trap. A change to the polygon fill's edge pairing gained 79 matching pixels.

What we believed. That the gain showed the pairing was right.

What settled it. The pairing chose ring neighbours in a compacted array, where the neighbour of an edge is an unrelated edge. The mechanism was wrong by construction; it happened to help in a few cases.

The rule. Restrict a change to the cases it is valid for before believing its number.

14. Fit the rule to whole runs

The trap. Deriving the rule for routed verge-strip weights from a window of eight consecutive track records.

What we believed. That the weight byte +0x28 followed 2L − i.

What settled it. The eight records were half of a sixteen-record run. Reading complete runs gave the real rule: over a run of length L, the weight is i + 1 on even positions and L − i on odd ones, so each pair sums to L.

The rule. Fit a rule to whole runs, never a window.

15. Check what the renderer can already do

The trap. Renderer progress stalled on a single trackside polygon, and seven iterations went into it.

What we believed. That the next gain lay in pushing deeper down that thread.

What settled it. Stepping back to ask what the renderer could already do. Car drawing was fully ported. It had simply never been given a car.

The rule. Before deepening a stalled thread, check what the code can already do and what it is being handed.

16. Count call sites before reaching for the emulator

The trap. Working out where the mirror image is drawn. The obvious move was a long emulator session.

What we believed. That the mirror path needed live tracing.

What settled it. A caller count. The edge builder at 15F2:5682 has exactly two callers, and one is not the main scene. That second caller is the mirror render.

The rule. Count call sites first. One caller rules a path out; two is a lead.

17. Deterministic garbage

The trap. A stack slot held the same value on two separate cold loads of the game.

What we believed. That a repeated value meant the slot was written on purpose.

What settled it. The emulator is deterministic. It replays identical stack garbage on every cold load, so repetition proves nothing about intent.

The rule. In a deterministic emulator, "same value on two cold loads" never proves a slot was written deliberately.

Oracles that lie

An oracle is only as honest as the question you ask it. These notes are about measurements that were correct and still misleading.

18. The NOP differential needs a poison step

The trap. A cheap way to ask "does routine X draw anything?" is to suppress the call and compare the frame with and without it. If nothing changes, the routine is inert.

What we believed. That routine 15F2:A675 made no difference to the frame. The zero-diff was taken as a refutation.

What settled it. The suppressed call left the backing buffer holding stale pixels from the previous frame, which happened to be the same pixels the routine would have drawn. The zero-diff was a false negative. Filling the destination with a sentinel value before the frame exposes it: with the call suppressed, sentinel pixels survive.

The rule. A suppress-and-compare test needs a poison step. Fill the destination with a sentinel first.

19. One sample, one branch

The trap. The polygon fill's selection logic forks at 15F2:1495. A capture confirmed the port's handling of it.

What we believed. That the selection was verified, because the port matched the original on the captured sample.

What settled it. The sample had taken the path where status bit 0x40 is set. Three iterations then went into wiring the bit-clear path, which every real polygon takes and no capture had covered. A breakpoint census over a whole frame found the fork is three-way, and that 3 of 12 polygons took code the port had never seen. Because the arms produce symmetric output, only the value of BX at the deciding test [bx],0x40 tells them apart.

The rule. Record which branch a capture exercised and the value that decided it. A census over real data finds paths that reading misses.

20. Three agreeing measurements

The trap. The camera's eye height and pitch constants were checked against several captures from the running game, and every capture agreed.

What we believed. That agreement across captures proved the constants.

What settled it. Every capture had landed on the same track record, 1191. The pit-lane state had never been measured. A live pit-lane capture disagreed. The constants were not wrong; they were conditional. F1GP has two camera views, entered at 0752:E985 and 0752:E9BC, and the hard-coded eye height and pitch were View B's. View A frames came out off by exactly the difference between the two.

The rule. Agreeing measurements are not proof. Check they sampled different states, and that the state that matters is among them.

21. A matching value is not an identification

The trap. Hunting for the variable behind a behaviour, a cited address held the expected value.

What we believed. That [0x233f] was the variable, because it read 0xa0 exactly when it should.

What settled it. The same value appeared in four states that needed two different terms. A single coincident value had passed for identification.

The rule. A cited address plus a matching value is a lead, not a proof. Find a state where the candidate must differ, and check that it does.

22. The file shows you where a table started

The trap. Reading a data table from the executable file is quick and needs no emulator.

What we believed. That the cockpit mask table at 25B3:6364 could be ported from its file contents. It was non-zero and looked complete.

What settled it. A live read. The game overwrites the table at run time for every row it actually uses. The file held a stale initialiser that only looked portable. The same limit once produced a retracted claim that two wall routines "could not work if called"; both of their tables are rewritten after load (see chapter 10).

The rule. A file read gives the value at load. For anything a routine branches on, read the live value.

23. Contradicting measurements with different subjects

The trap. Two investigations of the polygon fill's chooser disagreed: one said the original's branch mattered, the other showed it was a no-op on the port's data.

What we believed. That one of the two measurements had to be wrong.

What settled it. Naming what each one keyed on. The original's chooser keys on lower_y, the first word of the edge stream. The port's shipped heuristic keyed on an x coordinate, the third word. Both statements were true, about different things.

The rule. When measurements contradict, name the subject of each before choosing between them.

24. A sticky flag hides repeated faults

The trap. The game hooks the CPU's divide-error interrupt so a faulting DIV sets a flag and carries on. A test compared the final value of that flag with the original's.

What we believed. That a matching final flag meant matching fault handling.

What settled it. The flag is sticky. The zero-divisor case in the pit annotation code faults 415 times in one original call. A port that dropped every exception but the last, or skipped square-root steps, would leave the same final flag.

The rule. Pair each divide with its handler invocation, and count them.

Porting faithfully, and wrongly

Faithful does not mean literal. These notes are about the places where copying the original exactly would have been wrong, or where the "obvious" meaning of a field was not its meaning.

25. A faithful port can be the wrong port

The trap. Routine 15F2:B1A7 blind-clears part of a track record after drawing. Porting it exactly seemed like the faithful choice.

What we believed. That any deviation from the original's cleanup was a fidelity loss.

What settled it. Asking what regenerates the record. The original rebuilds that table, so its blind clear is harmless there. In the port at the time, the table persisted, so copying the clear would have stripped section flags for a whole lap. The deviation was the correct port. A related detail came out of the same work: the un-mark is a mask, not a restore. It sets +0x1e to zero and clears bit 7 of +0x2b even though the mark never set that bit.

The rule. Before copying destructive cleanup, ask what regenerates it in your architecture. If nothing does, the literal copy is the bug.

26. One table, two representations

The trap. The port marked competitor cars into the runtime track record bytes, as the original does. The painter, however, read each car's class from decoded Rust structs.

What we believed. That the cars were marked, so they would draw.

What settled it. Competitors were queued and drew nothing. The marks went into one copy and the painter read the other.

The rule. Keep one source of truth. A table held in two representations invites a silent half-update. This lesson is one of the roots of the single canonical memory image described in chapter 10.

27. The patch that did nothing

The trap. The first design for Big Race's vehicle sets patched the driving parameters in the executable image and swapped the car shape in a host-side copy of the shape table.

What we believed. That patching the image changes how every car drives, and that a swapped shape stays swapped.

What settled it. Independent design reviews read the loader. The 38-byte per-circuit driving block at DS:0204..0229 is decoded from the track file at every startup, overwriting whatever the image held. And the renderer re-copies the shape segment from live memory every frame, which erases a host-side swap. Both mechanisms would have been no-ops.

The rule. Find where the game rebuilds a value before deciding where to change it. The shipped design overlays the block after the loader decodes it, and re-applies the shape override after each copy (chapter 12).

28. A field's name is a hypothesis

The trap. Early investigations named fields by what they seemed to do.

What we believed. Three names in particular. That car record +0x84, written by routine AFA3, is a "detail level". That [0x2225] is the entrant count. That the table at 25B3:0C65 is the race order.

What settled it. Reading every consumer. Both readers of +0x84 negate it: it is a per-car draw-order bias, base 1 or 2 plus one per occupied scene slot skipped. [0x2225] is a frame-rate draw budget clamped to 12..23, which is why AFA3 always runs. And 0C65 is the spatial order around the lap, sorted on record +0x26; the race classification lives in +0xAA and is sorted separately. The first name stuck in places: the capture toolchain's own notes still describe +0x84 as a detail level.

The rule. Name a field after you have read all of its readers, and fix the name everywhere when it changes.

29. Twice a place, not an index

The trap. Each frame, race control marks the track records near visible cars with a class byte. The natural guess is 0x80 | car_index.

What we believed. That the low bits indexed the car list directly.

What settled it. The consumers' bound check. They compare against 0xb4, which is 0x80 | (2 × 26). The class is 0x80 | (2 × place), resolved through the order table, as the car placement routine at 15F2:AAED does, never a direct car-list index.

The rule. Let a guard's constant tell you the encoding. cmp cx,0xb4 was the whole answer.

30. Clipped geometry is supposed to leave the screen

The trap. A projector that returns "no screen position" for a point behind the near plane seems safe.

What we believed. That dropping polygons with a near vertex was a reasonable approximation.

What settled it. Half a grandstand disappeared, and a provisional rasteriser flooded the frame with a polygon whose vertex lay thousands of pixels away. The original assigns Cohen–Sutherland outcodes so near geometry is clipped, and the clipped result lands far outside the frame by design; only a clipping fill may rasterise it. Along the way, a mysterious x << 5 in the near clip turned out to be the general projection (x << 8) / depth evaluated at the near-plane depth of 8.

The rule. A shift that looks arbitrary is often the general formula at a special value. And "no screen position" is half a port; the other half is the clip.

31. When no rule can pass both tests, an input is missing

The trap. Two tests of the polygon fill wanted opposite left/right edge assignments from what looked like identical input.

What we believed. That the assignment rule was subtle and needed more cases.

What settled it. No choice of assignment converged. Printing the descriptors each stage was handed settled it in one run: the original's decision uses status bit 0x40, which the port was not passing in. A related check paid off in the same code: the fill tests its corner bits once, on an accumulator at [0x640], not per descriptor, and that input already existed in the port.

The rule. If identical input must give opposite outputs to pass two tests, the input is incomplete. Print what the stage is handed before adding another piece.

32. A guard that only holds for the code it guards

The trap. The port's fill rejected any edge ring whose two descriptors differed in lower_y, and the rejection never fired on real data.

What we believed. That the guard was a safe invariant of the original.

What settled it. Swapping in the original's selection rule. The guard had held only because of the port's own invented selection; with the real rule it rejected valid rings. A cousin of this trap: the fill appeared to "tolerate" stream-less descriptors, but in fact its caller only ever handed it a window between two cursors. Tolerating a case and excluding it look identical from outside.

The rule. A guard co-designed with the code it guards is only valid for that code. Recheck it whenever the rule changes, and check how a caller narrows input before copying its success.

33. Port the marks before the renderer they gate

The trap. The wall-drawing routines looked like dead code: no circuit set any wall flag in track record +0x1f.

What we believed. A lesson recorded that both wall routes were dead. A later one recorded that the road units were blocked on tables built outside the expander.

What settled it. Both were marked SUPERSEDED or WRONG. The wall marks come from track commands 0x8a (lateral) and 0x8b (longitudinal), with ten argument bytes each, handled in the expander's second pass. The wall-width table is built inside the expander too. Once the port ran those commands, about 74 records per circuit carried wall bits and drew. A capture of the live +0x1f bytes, built before the port, rejected a first wall pass written from a partial reading of the loop, before any wrong geometry shipped.

The rule. Port the loader marks before the renderer they gate, or the renderer is unreachable and unverifiable. Build the oracle before the port.

34. Do not relax the finish; drive better

The trap. Automated full-race runs on wet circuits sometimes never finished. The player car, held on straight throttle, could get stranded.

What we believed. It was tempting to treat this as a harness problem and loosen the finish check.

What settled it. The car was valid; the input was not. Held throttle can also be limited by the game itself: with the owned slip inputs, the original reduces a requested 16,384 to 15,074. A "source driver" that steers corners with real keyboard make and break edges, derived from live track geometry, finished every run naturally.

The rule. Keep the terminal predicate strict. Never force a retirement or relax a finish flag; fix the input.

Testing that proves nothing

The last theme is the most humbling: tests that were green, and meant nothing.

35. assert_ne! cannot see an inversion

The trap. A near-clip test checked that two outputs differed, with assert_ne!(a, b).

What we believed. That the test pinned the branch.

What settled it. A mutation that swapped the two outputs. They were still unequal, so the "both objects near" test passed the mutant.

The rule. Name both expected values. Inequality cannot tell a correct branch from an inverted one.

36. 738 green tests and no wall drawing

The trap. The wall-drawing body was covered by a large, green suite.

What we believed. That the suite exercised it.

What settled it. Every wall call site in the tests passed walls: None. The whole draw body could be deleted and all 738 tests stayed green. Worse, no frame-level differential test covered walls at all: the four frozen Suzuka frames contain no wall record, so they passed with walls both declining and drawing.

The rule. An oracle only covers the path its test takes. Break a new path deliberately before citing any suite as evidence for it.

37. The mutation that could not fail

The trap. A mutation survived, which normally means the test is weak.

What we believed. In one case, that a cast chain needed a stronger test. In another, that the wall build index was untested.

What settled it. Working out why each survived. The cast chain as u8 as i8 as u8 as i8 is the identity, so the "mutant" was the original code. And flipping the low bit of the wall build index only swaps within a command's own pair, which changes nothing on Suzuka because its commands share a divisor.

The rule. An inert mutation reads exactly like a weak test. Explain a survivor before believing either verdict.

38. The test that skipped the interesting return

The trap. Lap counting was tested by calling race_lap_state directly.

What we believed. That the lap display was covered.

What settled it. A car that has already finished skips the lap increment and returns early; later crossings only redraw. The direct call never went through that return. Reproducing through the timing-line latch, and checking the actual digit pixels, did.

The rule. Test through the path play takes. A direct call to the inner routine skips the branches the caller adds.

39. Exit code zero, nothing ran

The trap. Capture scripts were run as inline Python heredocs under a timeout wrapper.

What we believed. That a zero exit status meant the capture and its test had run.

What settled it. Two separate sessions observed the same thing: the heredoc executed nothing and exited 0. A shared Cargo target directory produced a similar ghost: a clean tree "passed" with a neighbouring worktree's test binary, reporting that tree's temporary mutant warning and test count without compiling anything.

The rule. Run scripts from files, give every worktree its own build target, and read the real test output rather than the exit code.

40. The mutation that damaged the original

The trap. A mutation self-test for captured metadata created its mutant files as hard links to save time.

What we believed. That the genuine capture was safe, because the mutation wrote to a "copy".

What settled it. A hard link is the same file. The JSON mutation altered a genuine capture.

The rule. Mutation fixtures copy, never link, and verify the source hashes after every run.

41. Lessons go stale too

The trap. Measurement lessons ("this routine does not run in a practice frame", "no circuit sets this flag") are true when written.

What we believed. That a verified lesson stays verified.

What settled it. Six lessons outlived their truth after the thing they measured was ported. Because every new session was fed the lessons' first lines, those six were repeated as fact until someone noticed.

The rule. A measurement lesson goes stale the moment you port what it measured. Prune or rewrite it then. These notes are a snapshot of a file that keeps moving.
