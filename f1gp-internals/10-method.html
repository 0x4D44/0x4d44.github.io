Inside Formula One Grand Prix Part II — The port

Chapter 10

The oracle

You cannot port a 1991 binary faithfully by reading it. You port it by running it, asking it questions, and freezing its answers into tests. This chapter describes the machinery the project built to do that, and the rules that stop a green test from lying.

Why a port needs an oracle

Big Race does not re-imagine Formula One Grand Prix. It runs the player's own copy of the v1.05 executable, GP.EXE, through a Rust "source runtime": each original routine is re-expressed in Rust with the same arithmetic, the same memory layout, the same flags and the same caller wiring. The bar is not "looks like the game". The bar is "writes the same bytes the game writes".

Reading the disassembly is necessary but nowhere near enough. The executable is about 600 KB of 16-bit real-mode code. Its data structures are reached through pointers computed at run time, its tables are rewritten after load, and its behaviour forks on values that no static read can predict. A port written from reading alone is a guess about all of that.

So the project's primary source of truth is the original program itself, running under emulation. We call it the oracle. Every claim about what the original does is either measured on the oracle or labelled as inference.

The trap

Early on, a naive coverage count scored any routine as "ported" if its address appeared in a comment. A survey on 2026-09-04 found the opposite was common: the main reason to cite a 15F2:XXXX address was to note that the routine was not reproduced. Four cases alone (A675, 3043, 2EB5, 8331, 1,475 bytes) counted as covered while two were listed as open work. Only explicit XXXX..YYYY ranges proved coverage, and they covered 51.3% of the 42,888-byte graphics segment. An annotation grep overstated coverage by roughly a factor of two.

The emulator and its recipes

The oracle is GP.EXE running under mdpc, a DOS PC emulator from the sibling mddosem project. A second mddosem tool, emuscru, drives it from a script. The two talk over a named control pipe, so a Python capture script, a shell script, or a recipe runner can all steer the same running emulator.

The recipes live in oracle/*.emu. They read like a tester's notes. The Practice recipe, for example:

  • launches the game from a private temporary copy of the player's install, at "pentium" speed with audio off, then switches the emulator to turbo;
  • waits for the title screen to stop changing, asserts a 320x200 video mode and checks a hash of that static screen, so a wrong install fails immediately;
  • presses Escape twice, clicks through the opening screens with mouse clicks at fixed coordinates, selects keyboard control, and taps Up repeatedly to clamp the menu cursor to its first item whatever state it started in;
  • enters Practice and parks in a live cockpit.

A second recipe, f1gp_v105_quick_race_suzuka_start.emu, reaches the Suzuka race start. Area folders under oracle/ (calibration, entrant initialisation, entrant rendering, entrant seeds, physics, pit annotation, racing line, session deadline, track annotation) each hold the method note for one differential comparison and, where needed, their own parking recipes such as park_quick_race.emu.

Animated cockpit frames deliberately carry no exact framebuffer assertion in the recipes. The cockpit's checksums change from frame to frame, so recipes assert the stable title screen and the selected menu state instead.

Parked, not rewound

Two limits of the emulator shaped every capture. First, the release build of mdpc has no time machine: its checkpoint-restore commands exist only in debug builds and answer "Time machine not available in release builds". Second, commands that write memory or set registers only work while the guest is paused. So the oracle is parked: a recipe navigates once to a live cockpit, leaves the emulator paused there, and every probe runs from that one park. Nothing is rewound.

Long runs start mdpc in the background with a named pipe and connect emuscru to it afterwards. The obvious alternative, emuscru's own keep-alive flag, dies with the command that started it. Every emulator call is wrapped in a timeout, because a hung call otherwise strands the capture.

Relocation and address spaces

Before you can set a breakpoint you need to know where the code will be. That is harder than it sounds, because a DOS program's segments are relocated when it loads, and the project's sources cite addresses in several different spaces.

The disassembly listing names the graphics code segment 15F2. At run time, in the observed session, that code lives at 1699, and the offset shifts too. The relocation rule is: listing 15F2:XXXX runs at 1699:(XXXX − 0xA70). It was verified on four independent breakpoints, for example 15F2:5BB0 → 1699:5140 and 15F2:46C0 → 1699:3C50. The capture scripts are written in runtime addresses with the listing address alongside in a comment, which keeps them readable against the disassembly.

Absolute segment values depend on the DOS load base, so the capture README tells you to re-derive them from the live registers before trusting a script. The differences between segments are believed invariant; the README labels that as inference.

The code base cites addresses in four forms. The architecture guide records how each maps to a file offset in the unpacked executable:

A bare hex number such as E0B1 might be a file offset rather than a segment offset. The track expander overlay, cited as 19ED:X, is not even consistent across the tree: three files use three different mappings, and the guide says to verify the bytes before relying on any of them.

Reading data straight from the file

Because the segments sit contiguously after the code, a data segment's initial contents can be read from the unpacked file without any emulator: file offset = 0x10000 + (SEG − 0x15F2) × 16 + OFF. The rule was checked against the live machine: scene data 381C:01C0 reads 0x20 in both places. It answers "what does this table hold before anything runs" in one line of Python.

It also produced one of the project's retracted claims. An earlier note used file values to argue that the pit-lane strip join 2EB5 and the wall routines at 3474 "could not work if they were called". Both tables they depend on are rewritten at run time. The wall-width table at scene offset 0xb6 is all zero in its first column in the file and populated live; the pit-record table at 0x1ac holds four null entries in the file and four live pointers into the track table at run time. Those pointers decode to Suzuka records 1049, 1050, 22 and 21: the pit entry and exit. The note was retracted and the rule became: the file gives you the value at load, never at any later moment.

Breakpoints, watchpoints and RAM dumps

Three instruments do most of the work. Each has sharp edges the project learnt the hard way.

Breakpoints

A breakpoint in mdpc halts the guest. The recipe runner's wait command then reports "hang detected", which is the breakpoint firing, not a fault. Recipes that read memory after a breakpoint must run with --continue-on-error, or they stop before their memory reads.

Breakpoints are expensive even when they never fire. While any breakpoint exists, the emulator drops to one interpreted instruction per iteration with its fast dynamic core bypassed. One exit breakpoint raised emulator CPU load to about 670%; clearing it brought load back to 34–35%. So captures arm breakpoints late, clear them as soon as possible, and clear every one before any live driving.

Smaller rules followed from specific failures:

  • mdpc reports a breakpoint set just after a CALL at call time, so "return markers" placed there are useless.
  • Clearing and re-setting a breakpoint while stopped on it can recapture the same instruction. A 512-frame wait never advanced until the capture first moved past the stop.
  • A menu breakpoint armed as 15F2:C047 reported 213F:0B77. Both resolve to physical 21F67. Match the physical address and check the code bytes.
  • STEP cannot advance interrupt-driven work: there is no timer tick while paused. Eight million instructions stepped while paused never processed a queued mouse click.
  • Setting DS through the emulator's register command leaves a stale segment cache. Eighteen authored polygon fills returned without drawing, even though the displayed registers and memory looked right. The fix is to reload DS through a real MOV DS,AX in the guest, and to require evidence that the input was read and output written.

Write watchpoints

The original sets most of its data structures through pointers it computes at run time. Static scans of the disassembly find the readers of a table, never its writer. Absolute, BP-relative, SS-prefixed and immediate-load scans all failed to find writers; one hunt set fourteen breakpoints on candidate "segment switch" sites and none fired, because the real writer used an ES loaded long before.

The answer is a write watchpoint, and mdpc has one, with conditions. It needs an mdpc built with debug assertions and an emu_probes feature. The executable must be passed as an argument, not only a control pipe. You arm a trigger on a linear address (TM_TRIGGER_WRITE_ADDR <linear> pause) and the emulator pauses when that byte is written. A companion query, TM_LAST_WRITE, names the instruction that last wrote an address, but its answer "No writes found" means "older than the history buffer", not "never written". So you arm the trigger before the event you care about.

RAM dumps

mdpc can dump all guest RAM with raw RAMDUMP <relative-path>. The path is relative to the emulator's working directory, so the emulator always runs from a scratch directory; otherwise it writes into the repository.

A before-and-after diff of two dumps answers a question disassembly struggles with: is this table copied from somewhere, or computed? The wall-width table at scene 0xb6 settled it this way. A full RAM diff found its bytes nowhere else in memory, so it is computed: out = source × 64 / (axis_x & 0x3f) from scene entries at 0xce onwards, verified on six live entries. Bisecting the menu recipe then located when it fills: during the menu phase, on the mode-select click, not at race start.

Censuses and profiles

mddosem's breakpoint list reports a hit count per breakpoint. That turns the emulator into a profiler. tools/oracle-capture/profile_routines.py parks the game in a live frame, sets breakpoints on a list of candidate routines, resumes a fixed number of times, and reads the counts once at the end. It clears every breakpoint on the way out, including on failure.

This mattered for planning. Ranking unported routines by size is misleading, because much of the largest uncovered code sits behind run-time gates. The two-frame profile compared a stationary car in the Suzuka pit lane with a moving car in a full 26-car field:

The shading overlay was the largest single block of uncovered bytes. It never ran in a practice frame, stationary or moving; it turned out to be an optional display mode the player toggles. Porting it on size alone would have been wasted effort.

Two rules came out of the profiling work. A non-zero count is decisive: the routine runs. A zero is provisional: the frame may simply not exercise it. And every negative needs a control in the same batch: "resumed 0 of 60 polls" looks identical to a misconfigured segment until a known-hot routine in the same run fires.

The trap

The driving recipe originally left the emulator in turbo. The three-lap session finished while the first probes were still running, and the game sat on the results screen, where the 3D scene still renders behind the menu panel. The profile looked alive and the control fired, but every number described a static post-race scene. The recipe now drops to normal speed before driving and prints the player's track record index, (word at 25B3:096F − 0x30) / 0x2E, before and after each profile. In the re-taken run it moved from 134 to 137.

The branch census

A census is the same idea aimed at branches instead of routines: put a breakpoint on each arm of a fork and count which arms real data takes. The polygon fill's selection logic forks three ways at 15F2:1495. Every earlier probe had sat on one arm. A census showed that 3 of 12 polygons in a Suzuka frame took code the port had never seen. The arms are symmetric in their output, so only the value of BX at the deciding test [bx],0x40 tells them apart; the census had to record the deciding value, not just the outcome.

Later captures made the census routine. The loader metadata capture counts seven complete phases, 18 marker calls, 125 stores and 412 visits on the natural path, and each authored variant is checked against the same call-and-store census. The route capture matched 1,067 complete source calls.

Frozen differential fixtures

A capture is slow, needs a working emulator and the player's data, and is not deterministic. A comparison should be none of those things. So the project separates them: capture once, then freeze the result into a Rust source file under src/original_*_fixture.rs. After that the comparison runs in an ordinary cargo test, offline, with no emulator present.

Each capture script under tools/oracle-capture/ stops at named routines and appends raw emulator responses to a file. An emitter parses that file and writes the fixture module. The draw emitter stores each canvas snapshot as a run-length-encoded XOR delta against the previous snapshot, which keeps a whole frame's drawing trace to about 102 KB of source.

When the toolchain was checked in, two emitters were re-run against their original captures and reproduced the committed fixtures byte for byte. One needed a "ground word" argument that appeared nowhere in the scripts; without it the emitted fixture differed on exactly one line. The argument now lives in the emitter's docstring.

From the port

For a while the whole capture toolchain, eleven shell scripts and five Python emitters, existed only in a session scratchpad under the system temp directory. It held knowledge recorded nowhere else: the canvas address, the relocation rule and the breakpoint addresses. The raw capture files it produced were lost that way and are now treated as gone. The scripts were rescued into the repository on 2026-09-04, and the fixtures they produced are the reason those comparisons still run.

What a good comparison looks like

The flagship road test, suzuka_frame_polygon_fills_object_order_and_pixels_match_the_original, does not diff two screenshots. It compares the original's sequence of fill events, then the pixels written by each fill, masking pixels that the original's object draws touched, over more than 100,000 pixels. When it fails, it names the event index that diverged. A whole-frame diff localises a defect only to one bounding box, which grows to the whole frame as soon as two defects are far apart.

The capture work also found that the original does not draw its road into video memory at A000:0000. It draws into an off-screen 320x164 canvas at 580C:1400, and the presenter copies only about 61% of the VGA page per frame. A whole-page read of video memory mixes the current frame with retained pixels from earlier ones. The canvas address is not a guess: the draw emitter reads it out of the game's own far pointer and prints it.

Tests that need the player's data

The repository never contains the original executable or game assets. Tests that need them are marked #[ignore] (317 of them at the time of writing) and read their inputs from environment variables such as MDF1GP_ORIGINAL_GAME_DIR. A hygiene test, src/test_source_hygiene.rs, fails any owned-asset test that would silently pass when its variable is unset, and any test that hard-codes a developer's path.

The captured-bytes register

The project's rule is simple: original data is read at run time from the player's own install, and never bundled. Frozen fixtures are an exception to that rule, so the exception has a register, wrk_docs/CAPTURED-ORIGINAL-BYTES.md, and nothing joins it without a row.

Every entry today is test-only. The fixtures are included inside #[cfg(test)] modules and compiled out of release builds. They include the Suzuka road drawing trace (102 KB of source), the edge builder captured moving and at rest, the road pass inputs, the object sort order, the track pattern tables, and a handful of tiny scalar oracles from isolated runs of single routines. In all, roughly 232 KB of source, none of it in a shipped binary.

The shade table shows how the rule works in practice. The renderer needs four 256-colour shade banks. They were once captured from the running game, and a 2026-09-05 capture matched all 1,024 bytes. But the product does not ship that capture. At startup, original_runtime_resource_preparation generates the banks from the player's own executable inputs and publishes them where the original keeps them. The captured copy survives only as a test oracle for the generator. The executable file cannot supply the table as a byte range, because the file holds zeros at that offset: the game builds it at run time too.

Adding to the register takes three things: a row with provenance and a route to eliminating the entry; a statement of whether it ships or is test-only; and, for anything that would ship, a reason it cannot be read or computed from the player's install. Sometimes the right answer is to derive instead of capture. Three status tables in the screen clipper turned out to be "all the screen corners an outcode spans"; deriving them removed three copies of original bytes from the repository.

One memory image, bridges at the boundaries

The central design decision of the port is where the game's state lives. The answer is: in one place, laid out exactly as the original lays it out.

The native host owns a single byte buffer spanning physical addresses 25B30 to 680C0. The portable core borrows it. Five segment views share those bytes, just as they overlap in the real machine:

  • DS:AB30 is the same byte as SS:0000;
  • SS:7B60 is 381C:0000;
  • 381C:FF70 is 4813:0000;
  • 4813:FF90 is 580C:0000.

A checked segment-and-offset range maps each view onto the same buffer. There is no emulated CPU. Each ported routine is ordinary Rust that reads and writes this image at the offsets the original uses.

Typed state lives for one call

Rust code likes typed structs, and the port uses them: entrant tables, order tables, RNG state. But none of them persists. Each is decoded from the image immediately before a routine runs, and its fields are published back only after the routine succeeds. No typed copy of the entrant table or the RNG is allowed to drift away from the bytes the next routine will read.

Where a helper needs separate mutable views of DS and SS, it works on temporary snapshots, and their whole overlapping region must agree before either is published. An error, or a disagreement, leaves the authoritative image untouched. The design explicitly rejected a three-way merge to reconcile divergent snapshots. A merge could hide a missing alias publication, and could not fix a stale read inside a helper; the fix belongs at the helper that owns the write.

The stack is part of the state

The native caller fixes BP at zero, and in this program the low BP-relative words are live game globals, not disposable stack. Some continuation helpers also leave the residue of original CALL and PUSH instructions, which private differential replays compare. The runtime places temporary source frames in a reserved window, SS:7000–SS:7B60, with a working stack pointer of 7B1C and a measured footprint of 0x60 bytes. The window ends at 7B60 because higher addresses alias the pit bank. A stack pointer of zero is unsafe for the same reason: wrapped stores at SS:FFFC land in the generated pit bank.

A focused test, native_game_outputs_ignore_reserved_stack_contents_and_location, poisons that private memory and moves the stack pointer by 0x100. Every game output, all of DS and all non-private SS must stay identical. Injecting a read of an unwritten stack word makes it fail.

Bridges at source boundaries

About 125 files named original_runtime_* are the bridges. Each connects the canonical image to one source routine or service: startup, the loader tail, the cold track load, the grid, the per-frame field update, race commands, qualifying, pause, replay, rendering, the clock and timer interrupt, and the serial link. Host state (sockets, threads, wall clocks, audio DSP) never enters the image. That is what lets a save file be a copy of the image, and what lets two machines in a linked race agree.

How it works

A bridge's job is narrow. It stages the inputs the original routine would find in memory, runs the ported routine against the canonical image, and publishes exactly the bytes the original writes. An acceptance test for a bridge checks two things: the routine's own outputs match an original capture, and every other byte of the image is unchanged.

Guards, not stubs

A port in progress is full of places that return an error because the real code is not there yet. The danger is that those places quietly become permanent, and a game that "works" is really running around holes.

The project draws a hard line. An error on a shipped path is either a guard (a bounded check on malformed input, a missing caller capability, an exhausted table walk, or a transactional rollback) or it is a defect. A stub that stands in for unported behaviour is not allowed on a shipped route. And a guard stays until its source contract and reachability have been checked. A passing short race does not classify a guard as unreachable.

The clean-room two-car simulation that bootstrapped the project, and its menu routes, were removed on 2026-09-10. Since then no shipped gameplay or rendering route bypasses the original runtime.

The boundary checklist and audits

The running record is wrk_docs/2026.09.12 - TSK - Original runtime boundary checklist.md. It is described as an open verification queue, not a count of missing functions. Each row names a source boundary by address and states what was ported and what proves it. A typical row: the session state machine at 0752:D331 now scans for the next candidate when its deadline expires and follows the original's three branches (no candidate, same identity, different identity), with focused regressions for the fifteen-second handoff and the long same-identity timeout.

Periodic audits sweep the tree. The 2026-09-17 inventory searched the gameplay, presentation, audio, replay, camera, pit, retirement, results, save and Championship paths and found no live missing production route among the Unsupported and Unported outcomes. What remained were bounded guards; two public error variants had no construction site at all and were kept only as compatibility markers. By the latest audit the checklist stood at 576 of 577 rows checked.

Acceptance rules

The quality guide sets a small number of rules that apply to every claim of "done". Each one exists because its opposite once produced a false green.

Every race ends naturally, with all 26 cars

Race acceptance needs all 26 entrants to reach a terminal state, finished or retired, through the original's own exit flags. The host must never force a retirement, teleport a car, or relax the terminal checks to get a run to finish.

The final-tree matrix runs all sixteen original circuits in dry and wet weather, with both idle and held-throttle control: 64 runs, all reaching the natural source terminal with all 26 entrants classified or retired. An earlier 2026-09-10 delivery run covered 32 of 32 dry and wet races. Held-throttle runs use a "source driver" that emits real keyboard make and break edges for steering, derived from live track geometry. A straight-input run is kept as a negative control: on wet corners, straight held throttle can strand a perfectly valid player car, which is why the terminal predicate stays strict and the input gets smarter instead.

A headless test runs one production-shaped race to a frame cap. Its finish requirement accepts only the source winner crossing the lap limit, all entrants terminal, and the source finish flags requesting exit.

Exact full-page pixel oracles

"The page shows the right title" is route evidence. "The capture is not empty" is route evidence. Neither is pixel parity. Pixel parity means a complete-page comparison against an authenticated original frame.

The race-start oracle compares the production renderer's presented VGA page against four owned captures of the original at Suzuka: stationary and three moving frames. Every page reports 0 of 64,000 mismatches. To prove the comparison can fail, a deliberate one-byte shift of the canvas was made: the stationary check then reported 9,980 mismatches, and was restored. The same standard now covers the outer Championship Results menu, Race Finishing Times, Driver Lap Times, Fastest Laps and all three populated Championship standings pages, outside the original's blinking cursor. The native renderer also reproduces the complete 55,338-byte active track table after the original's car-list unmark, across stationary and three moving frames.

Every regression test goes red once

A test written alongside its fix passes the first time whether or not it tests anything. So every new regression test must be made to fail once, by mutating the source position, the fixture or the assertion, then restored and rerun green. Journals record the mutation and the red result.

Mutation testing here is mostly deliberate and by hand: temporary mutants of the port, recorded as killed or, honestly, as survivors. Capture drivers go further. The route capture's Rust replay runs a 16-case corruption self-test, and the metadata capture checks 74 deliberate integrity mutations, including deleted equal-value stores, interleaved instruction order and truncated snapshots, all of which must be rejected. Two further rules came from accidents: mutation fixtures are copied, never hard-linked (a hard-linked mutation once altered a genuine capture), and an inert mutation must be explained before either verdict is believed.

Check provenance and pipeline

Two more rules guard the oracle itself. Check a fixture's provenance before treating agreement as identity: one frozen grandstand frame came from Phoenix practice, and its depth of 9282 nearly became "same object, verified" against a Suzuka object at 9281. And check that the test runs the same pipeline play runs: six apparent "renderer defects" were the test harness running less of the pipeline than the game.

Independent acceptance adds a second pair of eyes. For many units a separate session re-captured the original from scratch, recomputed the arithmetic, compared registers at entry, store, pre-return and actual return, and confirmed that the emulator process and its private staging directory were gone afterwards. Journals separate what was observed from what was inferred, and name any limit of the host that prevents a claim.

The quality programme

Above individual tests sits a written quality programme, authored as a machine-readable programme file and projected into a generated quality map. Its title is "Faithful Formula One Grand Prix v1.05 runtime", and it is still marked draft: the targets have not been formally confirmed.

It states four outcomes. The original runtime owns gameplay, rendering, audio, save and load, and menu-routed sessions. Every session type behaves correctly across the stated matrix. Presented pages match the authenticated source oracle where comparison is required. And no shipped route bypasses the original runtime. It also names four dealbreakers, including "a green claim depends on an unintegrated branch, an unreviewed mutation, or a test that does not exercise the production route".

Work is divided into four areas, each rated on a three-step scale. Weak means a material boundary or acceptance is unproven or provisional. Sound means the route is exercised with current evidence and known gaps are recorded. Strong means the full matrix and exact comparisons pass on the integrated tree and every remaining error is a validated guard.

Local gates

There is no hosted continuous integration. The gates are run by hand, locally, and recorded in journals. The Cargo package is big-race, with binaries big-race and track-author. The portable core in src/lib.rs is #![no_std]; the windowed application lives behind the default native feature.

GateWhat it runs

The full gate is the core gate, the native gate, core lint, smoke and the format checks. It runs when a change crosses a runtime boundary; otherwise focused tests for the touched area are enough. On one recorded integrated tree the core gate passed 1,529 library tests, 21 main-binary tests and 35 track-tool tests, and the native gate passed 401 with 64 ignored, all with zero failures.

Three practical rules keep results honest. Tests run with standard input closed, so none can hang on a read. Each worktree gets its own Cargo target directory: a shared one once served a neighbouring tree's test binary, complete with the wrong test count. And a test filter must be checked with -- --list before a green run is trusted, because a filter that matches nothing passes with zero tests.
