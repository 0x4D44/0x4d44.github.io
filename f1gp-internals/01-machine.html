Inside Formula One Grand Prix Part I — The original

Chapter 01

The machine

Formula One Grand Prix is a 16-bit DOS program that owns the whole PC while it runs. This chapter describes the machine it builds for itself: how the executable is packed and loaded, where code and data live, how a 300 Hz timer paces everything, and how the port keeps all of that in one faithful memory image.

A real-mode program

Geoff Crammond's game for MicroProse runs in x86 real mode. There is no protected mode, no flat address space and no operating system help once a race starts. Every address is a pair: a 16-bit segment and a 16-bit offset. The CPU multiplies the segment by 16 and adds the offset to get a 20-bit physical address. So 25B3:0D1B means physical byte 0x25B30 + 0x0D1B.

This matters for everything that follows. A table the game reads at DS:2984 sits in whatever segment the DS register holds at that moment. Two different segment:offset pairs can name the same physical byte. And a program loaded by DOS does not know its own segments until DOS tells it, so the executable carries a list of places to patch.

This site cites addresses the way the port's sources do. 0752:5C2F is a code address in the running game. DS:2984 and SS:05C8 are offsets into the data and stack segments. Where a citation is a file offset instead, the text says so, because the two are easy to confuse.

Packed and unpacked

The GP.EXE on the original disks is compressed with Microsoft EXEPACK. EXEPACK squeezes the program image and its relocation table, then appends a small stub. When DOS starts the program, the stub runs first, expands the image in memory, applies the relocations itself and jumps to the real entry point. The packed file's own MZ header therefore has no relocations; its entry point is the stub at offset 0x0010, and the stub's header carries an RB signature.

Game and mod folders often also hold an unpacked copy, usually named GP_UNPACKED.EXE, which is far easier to study. The port's research used one heavily. Every file offset quoted in the port's sources is an offset into such an unpacked image.

The port does its own unpacking. src/native_exepack.rs is a small, safe decoder. It checks the MZ signature, insists that the declared size matches the file and that there are no overlays, finds the EXEPACK header from the packed CS, checks the signature, decodes the sixteen groups of packed relocations and the image, and rebuilds an ordinary relocatable MZ file. A test reconstructs the owned game's unpacked file byte for byte when the owner's copy is available.

The trap

A game folder can contain both files, and they need not match. On 2026-09-12 the project found that an adjacent GP_UNPACKED.EXE could be a stale generic image with a different driver roster and different random-number state from the packed GP.EXE beside it. Comparisons against a fresh capture of the real game only agreed once the port unpacked GP.EXE itself.

The rule that came out of this is short: when both files exist, the packed GP.EXE is authoritative. The host decodes it with the native EXEPACK decoder and ignores the unpacked copy. Mod folders are the usual source of a stale unpacked file, so the same lesson applies to roster bytes: decode GP.EXE before comparing anything.

Loading at 0752

An MZ executable is written as if it will load at segment zero. Every instruction that needs an absolute segment, such as mov ax, seg data or a far call, holds a value relative to that imaginary zero. The header lists where those words are. DOS picks a real load segment, copies the image there, and adds the load segment to each listed word.

Under the reference setup the project used, the game's image starts at segment 0752. The port fixes that base. src/original_runtime_image.rs defines LOAD_SEGMENT = 0x0752 and loads the image exactly as DOS would: validate the header, validate every relocation target first, copy the bytes, then add 0x0752 to each relocated word inside the window being loaded. If any check fails, the destination is left untouched.

Relocation explains many strange-looking numbers in the port. The executable's code refers to the off-screen canvas segment as 50BA. Add 0752 and it becomes 580C, which is where the game actually draws. The VGA aperture at A000 is a hardware address, so it is never relocated.

Two details in that map surprise people.

First, the stack segment starts inside the data segment. 3066 − 25B3 = 0xAB3 paragraphs, so SS:0000 is DS:AB30. The last 0x54D0 bytes of the data segment and the first 0x54D0 bytes of the stack segment are the same memory. The game stores many ordinary variables at low SS offsets, so a write through SS changes what a read through DS sees.

Second, the "pit" bank at 381C has nothing to do with the programmable interval timer. The port's constant is called PIT_SEGMENT because the bank holds the pit-lane track data. One of the port's lessons records that the pit-lane join reads its anchor from a second 46-byte-stride record table in this scene bank, not from the main table at 4813.

The canvas and the screen

The game does not draw the 3D world straight into video memory. It draws into an off-screen canvas in the 580C bank, starting at 580C:1400. 0x1400 is 5,120 bytes, which is exactly 16 rows of 320 pixels, so the canvas's first row lines up with page row 16. When a frame is ready, a separate resident routine at 213F:31FA copies the pixels to the VGA page at A000.

The screen-pointer setup at 213F:25CB installs these pointers: the primary and lower destinations at A000:0000, the upper and saved-upper pointers at 580C:0000, and a copy of the upper segment in the scene record. The frame pacer repeats the same stores every frame.

The trap

Comparing the whole VGA page between two runs compares frame history, not the current frame, because parts of A000 hold whatever earlier frames left there. Early oracle work compared the wrong buffer. The rule became: the world is drawn to 580C:1400, so compare that. A related slip: the port's "lower" buffer is the whole 64 KiB A000 segment, not the 64,000-byte visible page, so it must be sliced before any size check.

Three ways to write an address

The port's sources mix runtime addresses and file offsets, and that caused real mistakes. The rules that hold are simple once written down. For a runtime address SSSS:X, the file offset in the unpacked executable is:

file = (SSSS − 0x752) × 16 + X + 0x1600

The 0x1600 is the size of the unpacked file's MZ header, and 0x752 undoes the load base. Three special cases fall out of the same formula:

There is a second naming habit in the sources. Some citations name a segment by its position in the image, before the load base is added. The resident that runs at 92C0 is also cited as 8B6E, because 0x8B6E + 0x0752 = 0x92C0 and its bytes begin at image offset 0x8B6E0. The menu overlays are cited the same way, as 605A and 6BE7. One journal notes that a service cited as 19ED:2D73 is resident 213F:2D73, which fits the same arithmetic, since 0x19ED + 0x0752 = 0x213F.

An honest gap

19ED:X citations are not consistent across the project's own sources. One lesson says the track-expander overlay is file X + 0x8B4D0, and says that rule checked out against four citations. The track-table module cites 19ED:5B8F as file 0x90B8F. The cockpit module treats 19ED:X as image-relative, at file 0x19ED0 + X + 0x1600. A disassembly note maps a listing of the same area to run-time linear 0x19ED0 + offset + 0x7520, so the loader entry 19ED:519F breaks at 9658:000F, not at 213F:519F. The project's own guidance is to check the bytes before relying on any 19ED mapping, and this site follows it.

A bare hex number such as E0B1 is the worst case, because it may be a file offset or a segment offset. Older labels in the port once confused file 1469F with runtime 0752:469F. The fix was procedural: resolve the code bank and read the caller's actual call bytes before porting anything by name.

The 300 Hz timer

The PC's programmable interval timer (PIT) is fed by a 1,193,182 Hz clock. Channel 0 divides that by a programmable count and raises interrupt 0 (IRQ 0) each time the count runs out. DOS leaves it at the slowest setting, about 18.2 Hz. The game speeds it up.

At boot, code in the startup overlay (cited as 605A:B76C..B81B) installs the game's interrupt handlers and programs channel 0 twice: first with a count of zero, then with the final count. The final divisor is 3977. 1,193,182 / 3977 = 300.02, so the game's timer interrupt fires just over 300 times a second.

The trap

Writing 0x00 to PIT port 0x43 only latches the counter for reading. Writing 0x36 programs channel 0's mode. An early reading that looked only at the latch sites concluded the game never reprogrammed the PIT, and so lost the tick rate. Both kinds of write have to be read.

Inside the interrupt

The handler lives in the separate resident at 92C0:033F. The port ports it as one call, original_runtime_timer::tick, and the host calls it once per elapsed PIT interrupt. Each interrupt does four things, in this order:

  1. Sound. A shared sound service runs the six-interrupt divider. Every sixth interrupt is a main tick, which advances the music sequencer through the XSOUND AdLib driver at 9438. The OPL register writes it produces come out in order, before the interrupt completes.
  2. Counters. It increments two 16-bit counters at SS:05D2 and SS:05C8. The second is the frame counter the main loop watches.
  3. BIOS accounting. It adds an increment from SS:05CC into an accumulator at SS:05CE.
  4. Completion. If that add carries (or the increment is zero), the handler chains to the saved BIOS timer handler. Otherwise it sends end-of-interrupt to the PIC and returns.

The accumulator is the classic way to speed up the timer without breaking DOS's time of day: only a fraction of the fast interrupts are passed on to the BIOS. (That this is its purpose is our reading of the mechanism; the sources state the carry test, not the intent.) There is also an alternate handler at 92C0:0373, selected when SS:0A26 is 0xFF. It uses SS:05C5 as a re-entrancy latch, runs the same accumulator split, and skips the sound service while SS:08EB is 0xFF.

Frame pacing

The game's frame rate is not tied to the timer directly. The Graphics menu stores a frame interval: the number of 300 Hz ticks each frame should take. The menu byte is zero-extended into SS:1230. An interval of 12, which the project's reference test scenario selects, gives 300 / 12 = 25 frames a second.

The pacer at 0752:C2A6..C2FB runs once per frame, after the world is drawn. In the ordinary case it:

  1. copies the current frame counter into DS:2C63, recording how many ticks the frame used;
  2. waits, with an unsigned comparison, until SS:05C8 reaches SS:1230;
  3. resets SS:05C8 to zero;
  4. installs the screen pointers (the same stores as 213F:25CB);
  5. calls the pixel copy at 213F:31FA.

A fast PC therefore waits. A slow PC finds the counter already past the target and carries straight on, so the game simply runs slower. In a linked two-machine race, the pacer takes a different branch: if SS:0A27 is non-zero it skips the snapshot, the wait and the reset, and jumps straight to the common pointer stores. Chapter 08 explains why a linked race paces itself elsewhere.

What the interval feeds

The interval is not only a wait. A one-off routine at 0752:7CAF..7D2F turns it into fixed-point timing words that the physics uses. From the interval r it computes:

  • a draw budget, 30 − r/2, clamped to 12..23, at DS:2225;
  • a full time step, (r × 65536) / 300, stored at DS:2C5D and copied to two more words;
  • the frame rate 300 / r at DS:2C61;
  • a low-rate marker at DS:2C5F: when the frame rate is below 12, the marker becomes 0xFF and two of the step words are halved.

The step is proportional to the interval. Our reading is that a lower frame rate therefore means larger physics steps rather than slower cars. The divides here use the game's divide-error rule, described next, so a zero or overflowing divisor cannot crash the setup.

When a divide fails

On x86, a DIV or IDIV whose divisor is zero, or whose quotient does not fit, raises interrupt 0. Under DOS that normally ends the program. Formula One Grand Prix replaces the vector at 0000:0000 with its own handler at 213F:2602. The handler sets a flag and returns. The flag is the byte at SS:00C0, and it is sticky: nothing clears it between faults.

After a risky divide, the game either tests the flag and takes a coded fallback, or carries on with a clamped value. In the physics, one path skips the IDIV and a later instruction replaces the quotient with zero. In the renderer, a bitmap-scale quotient is clamped to 0x8000 right after the divide, so any overflow simply becomes that ceiling.

From the port

On 2026-09-04 the port's race dropped back to the menu at Suzuka's first corner. The session loop treated any render error as "circuit unavailable", but the original never fails a frame. A sweep that rendered every Suzuka track record from three lateral positions, facing both ways, found 292 failures in three places the port rejected and the original survives: the bitmap-scale divide at 15F2:24AE, the anchor-centre divide at 15F2:2C27, and routed verge strips. Folding the overflow into the clamp, porting the renormalisation at 15F2:2A1D so off-screen points clip instead of erroring, and letting one strip drop for a segment took the sweep to zero.

The lesson generalises: render divides in this game degrade; they never error. A port that raises an error on a divide fault is less tolerant than the original. The flag also hides repeats. One pit-lane annotation call with a zero divisor faults 415 times. Checking only the final flag would miss dropped exceptions, so the project's tools pair every DIV with its handler call.

The resident dispatcher

A separate block of code sits between the main image and the sound driver. The sources cite it as the 8B6E resident; it runs at 92C0 and is 0x1780 bytes long. It holds the timer interrupt, the keyboard hook, the joystick reader, the palette fade engine and the serial link.

Its entry point, 92C0:0000, is a dispatcher. The caller puts a method number in AX and makes a far call. The dispatcher saves the registers, rejects anything above 10, doubles AX to index a table of eleven near addresses, calls the target, restores the registers and returns. The main game reaches it through small wrappers in the 213F segment.

Palette fades

The game's fades are one of the clearest examples of the dispatcher at work. The wrapper at 213F:002C starts a fade-in: it sets a retrace flag at SS:08E6, then calls AX=5. AX=5 records the source palette pointer (resource segment 8320, offset 7440), clears the black-fade flag at SS:08E2, copies the step count from SS:08DC to SS:08DA, and zeroes the colour cursor at SS:08E4. The wrapper at 213F:008C then calls AX=7 once per frame.

Each AX=7 call emits one batch of colours through BIOS INT 10h, function AX=1012h (set a block of DAC registers), optionally after waiting for vertical retrace. When a full 256-colour pass completes, it moves every component one step towards its target using a signed byte divide, and counts down the steps. AX=6, used when a race ends, sets the black flag instead of loading a new palette.

The trap

Because 213F:002C and 008C sit near the sound code, they were first taken for sound-driver calls. Following the AX value through the dispatcher showed they drive palette fades. The retrace wait inside a fade also lets separate timer interrupts arrive, which the port has to allow for.

Keyboard and joystick

The game does not read the keyboard through DOS. It hooks the BIOS keyboard intercept, INT 15h with AH=4Fh, which the BIOS calls with each raw scan code. The resident's hook (cited at 8B6E:0533..0563) keeps a bitmap of which keys are currently down, at SS:04CC. Make and break codes set and clear bits.

Once per frame, 0752:0005..00C5 turns that bitmap into commands. It reads the player's key bindings from tables in the data segment and writes active-low command bytes: a bit is 0 when its action is requested. The binding tables pack bitmap positions differently from raw scan codes, so a port has to use the game's own tables rather than a scan-code map. The joystick is read by the resident at 8B6E:06DA, reached through 213F:2A78.

One frame, start to finish

The race loop is long, but its order is fixed and the port follows it exactly. The project reconstructed it from the executable and wrote it down as the host's call order.

A few points in that order carry weight. Input is sampled before anything moves. The pre-physics services at 0752:DA48 run object scanning, display cycling, the session state machine, the finish scan and periodic classification. The physics tick at 0752:5C2F walks the cars in the order given by a table at 25B3:0C65. And the race clock at 0984 is advanced only after the frame is drawn.

Computed pointers

One property of the executable shaped the whole research method. The game fills many of its data structures through computed pointers: it loads a segment and offset into registers, often from another table, and writes through them. It rarely writes a table through a fixed address.

That defeats static search. Hunting for a scene table at offset 0xB6 in the 381C bank, the project scanned for absolute writes, immediate loads, BP-relative and SS-prefixed forms, and relocations. Every scan found only reads. Signature searches such as mov es,[ss:0xf4] also missed far-pointer loads like les di,[var] and writes through an ES loaded long before. The table's bytes were not even in the executable or in any data file; the game builds them at startup.

How we know

The working instrument was a write watchpoint in the mdpc emulator: stop the machine when a given physical address is written, then read the registers. The rule the project adopted: static scans find readers, never the writer, in this binary. Use a watchpoint.

Calibration

Before a session starts, the game measures its own car. The routine at 0752:A718..A820 sets up the first entrant and runs the real physics 360 times accelerating from rest and 360 times braking. It records the results as two tables of 360 words each, 720 bytes apiece: acceleration at DS:2357..2626, and braking at DS:2627..28F6, which the game stores backwards. The acceleration table starts at speed 0; the braking table starts at raw speed 64.

These tables come from the actual car setup, the generated track geometry and the racing-line data, all in the game's own units. The port therefore cannot substitute a formula or convert from some native car model. It runs the same 720 updates through the same ported physics.

From the port

Calibration also depends on the frame interval, because the physics step does. The executable's static default for SS:1230 differs from the value the project's reference scenario selects in the Graphics menu (12). Only when the port committed the same menu choice before calibration did both 720-byte tables, and the random-number state, match the real game.

The random number generator

The game has one main source of randomness: a five-byte shift register at DS:2984..2988, drawn by the far routine at 0752:04D7. A second copy of the routine at 0752:0509 serves another register at DS:08C3. Each draw combines two 16-bit words from the register, shifts every byte up one place and puts the new byte at the bottom:

ax = (s1 | s2 << 8) >> 4
bx = (s3 | s4 << 8) >> 1
al = al XOR bl
s4 = s3;  s3 = s2;  s2 = s1;  s1 = s0;  s0 = al

The routine returns all of AX; callers mask the bits they need.

Two properties matter more than the formula.

It is deterministic and global. The generator is never reseeded from the clock during play. But every system draws from the same register: the track loader uses it for trackside pattern run lengths, feature widths and colour picks; the session hand-off draws a pace value from it; the field's ranking depends on it. So the outcome of any one draw depends on every draw made before it. The project's lesson: the field's ranking is only as deterministic as the generator's history, so a port must reproduce every prior draw, in order.

Its starting point depends on the timer. At program entry, 213F:0C34..0C4F reads the PIT channel-0 counter, shifts it right twice, keeps the low byte, adds one, and draws that many values. The static starting bytes are fixed, but the number of warm-up draws depends on where the hardware timer happened to be. The port makes that an explicit input: its virtual PIT starts at phase zero, so the latch equals the programmed divisor, and a separate entry accepts any observed latch.

How we know

A byte-exact track table needs the register's contents at the moment the loader starts at 19ED:519F. The project captured the register from the real game at the first race frame (0752:EE52) and made the port's cold start reproduce the same six bytes at DS:2983..2988. The earlier attempt matched a stale unpacked executable instead, which is part of how the packed-file rule was found. Tests that vary one input also hold the generator still, restarting it before each call, so that noise cannot hide a sign error.

How the port represents the machine

Big Race does not emulate an x86 CPU. It ports the game's routines to Rust, one source-mapped boundary at a time. What keeps those pieces faithful is a single decision: the game's state lives in one physical memory image, laid out exactly as the original lays it out.

src/original_runtime_memory.rs defines that image. It spans physical 0x25B30 (the start of DS) to 0x680C0 (the end of the 580C view): 271,760 bytes. RuntimeMemory borrows one caller-owned buffer and hands out 64 KiB views of the five segments without copying. The first 0x1AB30 bytes, through the end of the stack segment, are loaded and relocated from the executable. The generated banks are zeroed and then filled by the game's own ported startup code; no captured memory is used as input.

Bridges at source boundaries

Every original_runtime_* module is a bridge: a Rust port of one source routine or a stretch of one, named by its address range, that reads and writes the canonical image exactly where the original does. original_runtime_frame_present is 0752:C2A6..C2FB. original_runtime_timer is 92C0:033F..0496. original_runtime_timing is 0752:7CAF..7D2F. The overlapping DS and SS views get special care: a helper that wants two separate 64 KiB views receives disposable copies, and its result is published only if the aliased 0x54D0 bytes agree.

Bridges are transactional. A routine runs against a staged copy of the image; on success the whole copy is published at once, and on any error nothing changes. That rule is enforced by tests that inject a late failure and check that no earlier write leaked out. Where the original would wait, the bridge instead returns a resumable "pending" state, so the host is never blocked.

What the host owns

Hardware is represented at the edges, not inside the image. The host owns the real clock, the audio device, the window, sockets and threads, and none of that ever enters canonical memory. Some examples:

  • The PIT. The native host computes due interrupts from elapsed wall time as elapsed × 14,318,180 / (12 × divisor), using an absolute phase so fractions never round away, and calls timer::tick once for each. Before each tick it advances the audio model to that PIT boundary, so OPL writes land at the right moment.
  • The frame pacer. FramePacer::poll takes an observed value of SS:05C8 and returns Pending or Ready. It never blocks and never invents ticks. It remembers the first counter snapshot across polls, just as the original captures it once before looping.
  • The BIOS. Chaining to the old timer handler becomes a ChainBios event the host counts. A palette batch becomes a value for the host to apply to its own colour table.
  • The divide fault. Each ported divide reproduces the sticky SS:00C0 flag and the original's fallback, rather than panicking.
How it works

Think of the canonical image as the game's RAM and the bridges as its CPU, one routine at a time. The host plays the part of the motherboard: it supplies timer interrupts, key scan codes and hardware status, and it takes away pixels, OPL writes and palette batches. Because the RAM is laid out exactly as the original's, any byte can be compared against a capture of the real game at the same moment. That comparison is how every chapter in Part I was checked.

Because host state never enters the image, saving a session is a copy of the canonical bytes. The same rule is why Big Race refuses to save during a live linked race: the modem, socket and threads that the race depends on cannot be restored from memory alone.
