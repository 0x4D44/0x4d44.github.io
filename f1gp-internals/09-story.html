Inside Formula One Grand Prix Part II — The port

Chapter 09

Twenty-four days

On 30 August 2026 the project began as a small, independent Rust racing game that borrowed F1GP's track files. On 23 September it was Big Race: a program that runs the player's own copy of the 1991 game through a Rust bridge, with all 26 cars, every menu, the saves, the Championship and the modem link. This chapter tells how it got from one to the other, including the wrong turns.

At a glance

The repository's history is the spine of this chapter. It holds 2,654 commits dated 30 August to 23 September 2026. Every number below was counted from that history, from the project's status log (STATE.md), from its 529 dated engineering journals, from its 96 design documents, and from its bug ledger of 103 records.

The version number is a useful clock. The project bumps the patch version once for each change that lands on the main branch. The first commit carries 0.1.0. The last carries 0.1.714. So 713 separate changes reached the trunk in twenty-four days. That is roughly one every 48 minutes, around the clock.

Who did the work

The author directed the project. AI coding agents wrote almost all of the code, tests and journals. The commit history says which agents did so, because commits carry Co-Authored-By trailers naming the model. We counted them. Of the 2,654 commits:

So the port is mostly the work of OpenAI Codex sessions. Claude sessions led two stretches. The first was the renderer deep dive and the long autonomous loop of 3 to 5 September. The second was the last feature day, 22 September, which added the enhanced renderer, vehicle sets and window scaling. The two families also reviewed each other's designs. The quality records name an "OpenAI Codex lead session" as the attester of the current quality assessment, and several design documents record a Claude model as a consulted reviewer.

The agents often worked in parallel. From 6 September a lead session briefed several "owner" agents, each in its own copy of the repository, and accepted their work only after rerunning the evidence itself. Later journals describe up to three workers per feature, plus independent adversarial reviewers. That parallelism is why a single day could land 290 commits.

Day one: a clean-room game

The first journal is titled "F1GP Rust vertical slice". Its objective was modest and careful: build one deterministic practice slice "in portable Rust" that loads user-supplied data, advances one car at a fixed tick, draws an indexed framebuffer, and compares "selected stable observations" with the original game running in the emulator.

The rules were set on the first page and never relaxed. The repository ships no original executable, assets or extracted data. The core library is no_std with no dependencies. Disk bytes are decoded field by field, little-endian, never cast to native structures. Simulation uses fixed-width integers with defined wrapping, and no floating point. The journal records the very first tests as seven unit tests, each one made to fail once by a deliberate mutation before it was trusted.

That first day moved fast. By its end the project had parsed all sixteen original F1CTxx.DAT track files, checked their checksums, and walked every section of every track. Phoenix gave 67 sections, 769 track-length units and 233 section commands, matching an independent count. On top of that it built its own game: a car model with "provisional integer trigonometry", a lap lifecycle, human input replay, track limits, a deterministic AI lap driver, a "portable human versus AI race", qualifying, a manual gearbox and a cockpit view with instruments. The journal for the duel race specifies an allocation-free DuelRace that owns two RaceSession values and one AiDriver.

Two things about this start matter for the rest of the story. First, almost everything was labelled provisional: "provisional track geometry", "provisional runoff grip", "provisional track limits". The geometry design kept "65,536 heading units and curvature-per-track-unit explicitly provisional". Second, the oracle was there from the first hour: "Add repeatable mdpc practice oracle" is the twelfth commit. The project always meant to check itself against the real game. It did not yet know how much of the real game it would end up running.

From the port

On 31 August the clean-room core was cross-compiled for SPARC and built on an emulated SPARCstation 2 running SunOS 4.1.4 with its own GCC 2.7.2.3. The journal records the old assembler's 2,048-byte statement limit and the extra leading underscore that SunOS a.out symbols need. It proved the core was genuinely portable. It also shows the project's early idea of itself: a new engine that could run anywhere.

Reading the original's own files

On 31 August the direction began to tilt. The clean-room game kept growing: two-car contact, damage and retirement, pit service, car setup, race flags, a 16-round Championship. But alongside it a second line of commits started reading the original's data directly: "Decode original LZW screen records", "Reconstruct original palette animation frames", "Render original menu fonts from adjacent GP.EXE", "Render the original cockpit from adjacent GP.EXE".

The cockpit journal shows the method that would carry the whole project. The native program decodes the player's packed executable in memory only. It checks exact fingerprints for the 256-entry racing palette and the 320×200 cockpit template. Then it composes the live world with that template using the original presenter's own row mask. The journal gives the layout: the palette sits at file offset 0x22DC3, the 64,000-byte template at 0x7D2E0, and the presenter copies full-width scene rows 0–102, then span-masked rows 103–163, and keeps the template for rows 164–199. Nothing from the executable is written to disk or bundled.

On 1 September the menus followed. Twenty-seven commits titled "Recreate the original …" rebuilt the language menu, Setup Options, Driver Select, Load-Save, Select Circuit, every controls page, the printer page and the link dialogs, each with its own journal. File operations such as Load Names and Save Names were made byte-exact. Then, late that day, one commit changed the project's centre of gravity: "Add exact indexed presenter and frame oracle".

The renderer, routine by routine

From 1 to 4 September the project ported the original 3D renderer one routine at a time. The commit subjects read like a table of contents for Chapter 05: projected edge clipping, the edge scan stream, the paired edge fill, the masked span fill, the edge descriptor ring, synthetic screen-boundary edges, the bitmap scanline decoder, the object transform, per-point projection, the object placement stage, the runtime track table, road cross-section points, the pattern machine the loader uses to decorate trackside, the per-segment road edge builder, the road pass and the draw-order sort.

Each routine got an oracle before it got a port. A small capture toolchain parked the original in the emulator at a breakpoint, read the inputs and outputs of one routine, and emitted a Rust fixture. The port then had to reproduce those outputs exactly. By 3 September, "Draw the original road on the native cockpit" put the original's own road geometry on screen, drawn by ported code.

On 4 September a nine-agent survey asked how graphics fidelity should be driven. It found a risk more urgent than either option it was asked about. The whole capture toolchain, eleven shell scripts and five Python emitters, existed only in a session's temporary scratch space. It was moved into the repository that day, and two emitters were re-run to reproduce their checked-in fixtures byte for byte. The survey also found three facts that shaped every later oracle:

  • The original does not draw the road to the VGA page at A000:0000. It draws to a 320×164 canvas at 580C:1400, and the presenter copies only about 61% of the page each frame. A whole-page diff therefore compares execution history, not one frame.
  • The release emulator could not rewind. So each probe had to run from a parked state and never restore it.
  • "Citation is not porting." Most comments naming an address recorded that the routine was not reproduced. A coverage count built on comments overstated progress by roughly a factor of two.

The wall that was a table

Also on 4 September, the renderer ran into something bigger than a missing routine. A design note that day is titled "the runtime-table blocker is architectural, not local". Four separate graphics subsystems had stopped at the same kind of obstacle: a table the original builds at run time, by code that no static technique could find. Walls needed a wall table in scene data. Pit-lane strips needed anchor records set at startup. The masked-row polygon fill needed a per-row mask table at 25B3:6364.

The trap

The mask table at 25B3:6364 is non-zero in the executable image. That looked like good news: the port already read the cockpit from the player's executable, so a static table would have been portable at once. A live read disproved it. The first 20 bytes, exactly the entries for rows 104 to 113 that the routine uses first, are overwritten at run time. Only the tail from row 114 matches the image. Reading the image would have shipped a wrong cockpit mask.

The note's conclusion was that this is "how F1GP builds its tables generally, not a quirk of the road renderer". The fix was a tool, not a port: an emulator write-watchpoint, which names the instruction that stores to an address. With it, the wall table builder was decoded the same day, then the marking loop, then the wall points, each against a byte-exact oracle. "Put walls on screen" landed that evening.

Forty-nine reviewers and one wrong claim

That night a 49-agent adversarial review examined the wall work. It returned 45 findings, four of which its own verifiers rejected. Four independent review angles converged on the same code defects, and all four held when re-derived from the binary: a verge halved on the wrong branch, an accumulator that rewound where the original nets to zero, a gap loop that never cleared its records, and a loop exit that was a trailing walk rather than a return.

The journal's more useful half was about method. The landing commit had claimed the sweep test was green "with walls live". It was not: every test call passed walls: None. A drop in a fill metric that the commit read as confirmation was geometry being lost. "The entire wall-drawing body could have been replaced with an unconditional decline and the suite would have stayed green." From then on the rule was: when a change adds a new path, break that path on purpose and confirm something goes red before citing any suite.

5 September: the long loop

STATE.md calls itself "the loop's memory". It was written so that each iteration of an autonomous agent loop could start with no conversation context, read the file, do one unit of work and update it. Its goal line reads: "Port F1GP.EXE (v1.05) fully to Rust. First milestone: an authentic Quick Race. The oracle is the original itself." Iterations 1 to 57 are dated 5 September; 58 to 61 are dated 6 September.

Iteration 1 built the oracle route. Quick Race goes straight to Suzuka with no circuit choice, so it made a clean target. After O.K. and a fixed wait, the race-start frame always hashes to the same value with the car stationary and the start lights lit. Three runs from independently staged copies gave identical frames. The frame itself was never committed; the recipe regenerates it from the player's install.

What followed was a slow climb, with setbacks recorded as carefully as gains.

The early numbers came from a narrower road-scene test, and they already taught the main lesson. Iteration 8 went from 26.62% to 51.06% "by removing a confound I introduced myself": the test had been told to skip the horizon panorama, which this stage does draw. Iteration 24 then built the whole-frame test through the public render path. It first reported 42.31%, with the cockpit rows at 13.83%. The live game also runs a palette remap and the original cockpit presenter; the test did not. Adding those two steps gave 77.81%.

The trap

Six times, a poor score was caused by the oracle running less of the pipeline than the game. The status log lists them: the skipped panorama, a shade diagnosis built on it, the cockpit rows, objects that were never queued, the cockpit presenter, and, sixth, the missing competitor cars. "Every time, the renderer was less wrong than the number implied." The lesson file keeps it as one line: check the test runs what play runs, before theorising about a residual.

Retractions are recorded in the headings themselves. Iteration 25 is marked "DIAGNOSIS RETRACTED by 26": it had blamed a draw-distance cap, based on a percentage that did not move, when in fact objects painted 1,446 pixels and no culled population existed. Iteration 34 "RETRACTS ITERATION 33": a grandstand wedge that seemed to reach column 0 was a single garbage polygon with points seventeen thousand pixels off-screen, which the original clips inside its fill and the provisional rasteriser could not.

Iteration 37 is marked PIVOT. Seven iterations had gone into one grandstand fill without moving the frame. The loop parked it and turned to the cars. The grid was read from the running original: the car array at 25B3:0D1B with a stride of 0xC0, the player at position 7, six cars visible ahead. Iteration 38, "THE GRID DRAWS", gave the first frame movement since iteration 24. Iteration 39 found each car's team at record offset +0x25, where every value appeared exactly twice: a grid of two-car teams. The loop's own verdict on that step: "the score is the weaker evidence here; the picture is the stronger".

Iteration 51 shows how parallel work collides. While the loop's branch ran, another agent landed "Draw cars through the ported car list, not a hand-rolled imitation" on the trunk. The trunk's version was correct: it resolves a car's mark through the order table, which the loop's shortcut got wrong. The loop took the trunk's code whole and dropped its own. The frame went from 79.22% to 78.46%, and the log says so plainly: this was the branch declining to carry a superseded mechanism forward.

Meanwhile the same day produced the 26-car entrant subsystem, "the 34-to-26 field cut", and a new audio path. The original drives an AdLib card, so the port wrote an independent OPL2 chip model and a parser for the original's music catalogue. "Play the engine through the real chip" landed that afternoon.

The physics tick, and the producers

Iteration 61, on 6 September, carries the heading "THE PHYSICS TICK IS LOCATED, and the address this project has carried for it was wrong". The live Quick Race update is at 0752:5C2F, called from 0752:EE85. It walks the car list through the spatial order table. Detailed player dynamics are at 0752:995C. The address the file had named for physics all along turned out to be track-building code. A delegated agent found it; the loop corroborated it by disassembly. Two independent runs then matched every before-and-after byte of all 26 cars across 80 grid updates and 32 moving updates. For the first time, car physics could be ported against a tick-by-tick oracle rather than invented. The full mechanism is in Chapter 03.

The same day the work changed shape. A lead session briefed two parallel owners, one for physics and one for rendering, each in a separate worktree. The lead reviewed their code and reran their evidence before committing. The first round landed the track-relative coordinate refresh (all 192 entrant bytes matching 76 calls in two captures), a shared cockpit presenter, and a corrected neutral-gear glyph. The frame reached 52,144 of 64,000 pixels, 81.475%. The journal is careful to say only 41 of those pixels were a product fix. The other 1,890 corrected the old measurement.

Nine "parallel deliveries" followed over 6 and 7 September. The pattern in the commit log is distinctive: "Brief …", "Record independent … evidence", "Implement …", "Accept …". Each unit was a producer: a piece of the original that creates state another piece consumes. Force resolution and motion integration. The grid initializer, with its random-number read order preserved. The runtime racing line. Pit-bank geometry. Startup calibration. Session deadline. Route annotation. Loader tail. Race length and reset. Classification text. The countdown. Startup camera and clock. By the evening of 7 September the log shows the field's per-car continuation being corrected branch by branch: steering, acceleration, contact.

This is also when the bug ledger began. Bug 1, raised and fixed on 6 September, was a bitmap selector that mishandled the minimum signed object angle. Bugs 4 to 11 came in one burst the same afternoon, all in the road scene: forward car ordering used on reversed passes, a missing vertical scale on front billboards, a road heading marker using an absolute angle instead of an accumulated sign. All eight were fixed that day.

8 September: one memory, one race

By 8 September the port had dozens of faithful producers, each proven against captures. They did not yet make a game. Each had its own typed inputs and outputs, and the glue between them was new code. The turning point is a design note titled "Original Quick Race memory ownership".

Its decision is short: "The playable Quick Race must use one authoritative original-engine state." The native program owns one byte buffer spanning physical addresses 25B30 to 680C0. The portable core borrows it. Static data comes from the player's unpacked executable. Track and entrant records are generated by the original startup routines. "Captured dynamic memory is only a test oracle." The note adds that this "does not introduce an emulated CPU". The ported routines are Rust functions. They simply read and write the same bytes, at the same segment-and-offset addresses, as the original.

The note is equally clear about what it rejected. Helpers that need separate DS and SS slices get temporary snapshots, and their overlapping outputs must agree before either is published. A consultant had proposed repairing divergent snapshots with a three-way merge. The note refuses: that "could conceal a missing alias publication", and any disagreement "needs a source-backed correction at the helper that owns the write". The same design fixes BP at zero, because "low BP-relative words are live game globals, not disposable CPU stack", and reserves a scratch stack region at SS:7000..7B60, since addresses above it alias the pit bank.

This is the moment the project's idea of itself flipped. It had set out to write an engine and check it against the original. It was now running the original's own routines, against the original's own memory layout, fed by the original's own startup code. The clean-room game still existed, but it was becoming a fallback. The remaining work was no longer "make ours look like theirs". It was "connect theirs, completely".

The rest of 8 September was connection work, 220 commits of it: grid initialization into shared memory, Quick Race choices and timing, the cold track loader from the player's own files, roster and entrant seeds, the full-field car loop, the keyboard scan and bindings, sound driver calls, retirements, marshals, the fastest-lap notice, Escape cleanup with its black fade. A milestone task defined that day asked for a playable Suzuka Quick Race in which "a passing helper replay or static captured frame alone does not satisfy this milestone".

9 September: full races everywhere

The busiest day of the project has 290 commits. Its headline evidence is in the milestone record. Strict startup-to-exit replays at v0.1.284 reached the original three-lap finish with idle input at frame 11,054 and held throttle at frame 14,862, "with every entrant finished or retired". Both exits delivered 116 sound-stop writes and 84 black-palette batches, exactly as the original's cleanup does. A live window run held the throttle for 40 seconds and showed moving Suzuka scenery, 62 mph, lap 1 of 3 and 26 runners.

Pause and resume landed "with live timer interrupts", then instant replay, pit requests, tyre choice, the pit-crew animation, rear and front cameras, trackside cameras, wet weather palettes. Bugs came in fast because real driving reached paths that no capture had. Changing a driving aid aborted the race at 213F:3CD1. Circuit index 7 aborted on scenery projection. Suzuka's first grid aborted on a polygon edge overflow. F5 after the player retired aborted the race. Each was raised, claimed, fixed and recorded, and the evening commits read "record full dry and wet races after scenery correction" and then "record all sixteen circuits in dry and wet races".

From the port

Bug 38 began as a playtester's report: at Suzuka's first-gear left-hander after the bridge, the grandstand flickered in and out. It was confirmed with 240 consecutive captured scene states driven by a recorded input. The original kept the grandstand in frames 193, 194, 212 and 216; the port dropped most of it at 194 and 212, and frame 212 differed at 19,724 of 32,000 upper-scene pixels. The fix made the visibility test match the original at 15F2:9877: start with mask 0x1c, AND in each projected visibility point's mask in source order, and draw as soon as the common mask clears. Across the 240 frames, exactly 49 changed, all 718,289 changed pixels now equalled the original, and no previously correct pixel moved.

Not every race finished. Bug 47 recorded a wet race on circuit 6 in which one AI car stayed stranded for 30,000 frames, off-track and nearly stationary. The record insists: "Do not force retirement or finish as a workaround." The eventual fix was in the AI's reverse-heading recovery, which had returned early instead of keeping the original's recovery turn when lateral recovery was active.

10 September: deleting the clean-room game

At 12:29 on 10 September, a commit titled "remove provisional runtime surfaces" deleted 19,136 lines and added 2,835 across 27 files. Its message: "Delete the unreachable simulation, duel, AI, session, replay, smoke, and provisional rendering entry points now that desktop play uses the original runtime routes." The file list is the day-one game: duel.rs (1,776 lines), duel_weekend.rs, ai.rs, session.rs, weekend.rs, championship.rs, replay.rs, track_render.rs, and 13,609 changed lines of native.rs, the old native front end. Two hours later the provisional procedural audio module followed.

The "Final original-engine delivery" journal records what replaced it. The native original-engine route now owned Practice, Qualifying, Non-Championship Race, Quick Race and Championship Season. The whole matrix of 16 circuits in dry and wet weather passed 32 of 32 runs with every one of the 26 entrants in a natural terminal state. The test count at that point was 1,350 library tests, 322 native binary tests and 29 track-author tests. The architecture guide now states the rule flatly: "No shipped gameplay or renderer route bypasses the original runtime."

The deletion was not the end of clean-room remnants, and later commits kept removing them as each was found. On 14 September, "remove inert clean-room setup controls" took out Wing and Final Drive controls that looked real but reached nothing (811 lines deleted). On 20 September, "Remove source-less native menu rendering" deleted another 2,548 lines. The same day as the big deletion, the authored Bahrain circuit reached raceable state: it is described below.

How it works

Why delete working code? Because two engines that both "work" invite drift. While the clean-room route stayed live, any failure in the original route could quietly fall back to the invented one, and a green test could be testing the wrong engine. After 10 September, a missing piece of the original shows up as an explicit error with a source address, not as a plausible substitute.

12–14 September: the boundary audits

With the original runtime owning every route, the question changed again. What happens when the bridge meets a path it has not ported? Early code answered with Unported(address) errors. Some of those were real gaps. Others were guards for malformed input that a valid game never produces. The project could not claim fidelity until it knew which was which.

On 12 September a task document, "Original runtime boundary checklist", set out to classify every one. 13 September, with 254 commits, is almost entirely that sweep: "Classify animation parser and startup view boundaries", "Classify original race command adapter boundaries", "Classify remaining source boundaries", and alongside them the genuine ports it turned up, such as the linked race setup, the pause poll phases and the sixteen-unit neighbour route. Dead markers were removed only after their reachability was checked: "a passing short race does not classify one as dead".

Physics corrections surfaced in the same sweep. "fix: use source car angle for final force rotation" and "fix: rotate final forces by saved body heading" closed bug 62, where the final force rotation had used steering trigonometry instead of the saved body heading. The curve speed scaling, obstacle axle selection and route target quotient were all brought back to the source that day.

Then came the final-tree race matrix. Every one of the 16 original circuits, dry and wet, was raced twice: once with idle input and once holding the throttle with steering from a "source-derived geometry driver". That driver reads live entrant and track fields, applies the source's steering arithmetic and deadband, and emits only keyboard make and break codes. It writes no game state. All 64 runs passed the unchanged terminal predicate, which requires the source exit flags, the finish state, the winner's lap and every entrant carrying either the finish bit or the retirement bit.

How we know

The matrix ran with output suppressed and stopped on the first non-zero exit. All 64 cases returned zero, so each one exercised its assertions rather than just hitting the frame cap. An earlier "held-throttle with no steering" schedule is kept as a negative control: on the second circuit (index 1) in the wet it validly leaves the player stranded, so it cannot serve as a completion oracle.

On 14 September two more proofs landed. The race-start comparison passed at the pixel level: the production renderer and the source presenter matched four owned source captures, one stationary and three moving, at 0 of 64,000 mismatches per page, on version 0.1.441. A deliberate one-byte canvas shift made the stationary case fail with 9,980 mismatches before being restored. And the "Final source boundary audit" mapped every production session route to the source runtime, including Weekend and Championship coordinators, Load Game dispatch by save format, and authored track startup.

The quality map records the result: the integrated audit "checks 576 of 577 checklist rows". The checklist has since grown to 579 rows, and it still has exactly one unchecked. That row is the broad lifecycle item covering save and load, Practice, Qualifying, Weekend, Championship, pause, replay, input, audio and results together. Many sub-slices of it are proven; the row stays open until the attended end-to-end sweep and the ceremony comparison are done.

15–20 September: results, standings, ceremony

The next front was everything that happens after the chequered flag. The original shows Race Finishing Times, Driver Lap Times, Fastest Lap Times, race points, Drivers and Constructors Championship tables, Seasons Results, and a trophy ceremony. Each was brought across from the original's menu resources: "parse original results menu resources", "render original results menu", "present original seasons results", "Original Championship tables follow source scroll cursor".

Each one also needed an exact oracle, and that proved harder than the code. A result page depends on a palette, on result data and on the page artwork. The status log for 16 September notes that exact result-page pixels "still lack a retained paired source page, RGB6 palette and result-data snapshot". Over the following days those pairs were captured, and by 18 September the integrated tree matched the three populated Championship standings pages exactly, outside the source's cursor, alongside the earlier exact result-page oracles. Gates recorded on 18 September put the core suite at 1,529 library tests, 21 main-binary tests and 35 track-author tests. The quality map's integrated gate adds the native binary suite at 401 passed and 64 ignored.

The same week closed road-rendering parity circuit by circuit. Journals dated 18 September record exact source road replays for Phoenix, circuit one and F1CT03 through F1CT16, across natural and authored stationary and moving variants. Some mirror comparisons stay open where the source capture covers only one sign, and the checklist says so rather than rounding up.

From the port

Bug 68: the port wrote a raw save file of exactly the right size, 26,736 bytes, with a valid checksum and header. The original game accepted it in the file selector, said GAME LOADED, and then rejected it as Invalid Data. Swapping payload ranges into a known-good save showed the fault was in the state, not the checksum. The cause was two words the original's save preparation seeds before copying: DS:096B = 0x4813 and DS:096D = 0x381C, the main and pit segments. With them written, the original loaded the port's save and reached the expected frame.

On 20 September the Championship work finished its terminal path: "follow source Championship ceremony script", "follow source CHAMP presenter timing", "complete source championship terminal state". On 21–22 September a Championship run was accepted offline with the source-authentic 26-driver field, and "fix: retain the 26-driver Championship field" closed the last gap there.

Bahrain and Madrid

Adding circuits the original never had was a test of the bridge as much as a feature. The design for Bahrain, approved on 9 September, set a strict first-playable contract: the standard 5.412 km layout, clockwise, fifteen named corners, dry daylight; the original cars, physics, sound and full 26-car grid; and "a parser success or a screenshot is not completion". Bahrain became the seventeenth catalogue entry, and the catalogue was extended so further tracks need not fit the original's sixteen slots. Geometry came from public map data, with every estimate labelled.

The first full race failed dramatically. Bug 50: the authored race "retires the entire field before a classified finish". After 98.81 seconds all 26 cars had retired, with no winner. The cars left their corridor and reversed along the main bank. The cause was the racing line: the authoring compiler now fits curvature in the source's own packed units, keeps midpoint headings, and validates the line and its seam before publishing the track file. Further bugs followed the same theme of units: scenery placed in world distances where the original expects road-width-relative offsets (bug 53), shade-table indices outside the valid range (bug 52), pit-entry records missing a route transition mode (bug 54).

Madrid (the authored package is called Madring) had two failures of its own, recorded on 12 September. Its pit centreline was reversed relative to the main route, which made the original loader reject the pit pointer before a race could start. And its hairpin was encoded as zero-radius chords, so the original speed pass left those records at a seeded speed and one AI car stuck in contact. The fixed package has 1,111 main records and 193 pit records. The full authored acceptance then ran for 284 seconds: the player pitted, was serviced, rejoined, finished three laps and exited, with all 26 entrants terminal. Both authored circuits passed their full lifecycle checks on 14 September.

Becoming Big Race

On 19 September a commit renamed the public product to Big Race: the package, the executable, the interface and the developer commands, while keeping reads of the old settings and save paths. The README now opens: "Big Race is an unofficial Rust host and source-runtime bridge for a player-owned copy of the original game." The same day brought Alt-Enter fullscreen and resizable windows, and hardening fixes for corrupt Championship saves and non-printable option text. Full-game recording to a VP9 and Opus video had arrived on 14 September.

The bug ledger in this period shifts from fidelity to robustness. Records 72 to 91 include an audio device reporting a zero sample rate that trapped the music callback in a huge resampling loop, a file selector that exited on a non-ASCII filename, a malformed Championship checkpoint that aborted the menu, an options save that could destroy the previous valid record if interrupted, and several test-harness defects, such as corpus tests that silently passed when their assets were absent and a full-frame oracle that accepted a truncated expected frame as a match.

Two machines: the link and the modem

The original supports a two-player race over a serial cable or a modem, described in Chapter 08. The port worked through that path from 12 September onwards: the linked pause controller, the linked race setup, the packet transmitter and its retry and acknowledgement. On 20 September the linked frame was extended through player input and the post-frame continuation, and a staged cold-startup owner was added for linked play.

On 21 September the project chose the most faithful route to a network game it could find. Rather than turning the original's modem into a socket, it vendored a modem engine from the mddosem emulator, complete with its DSP, and modelled the PC's 8250 UART as the original sees it. The original runtime drives a virtual modem. The modem's 16 kHz audio crosses TCP. The peer's modem feeds the peer's original runtime. Keeping mddosem's PCM wire format means the original GP.EXE, running under mddosem, can act as an independent interoperability oracle. The original's own modem command builders were ported, and a commit titled "Present the authentic modem line audio" plays the modem line sound to the player.

On 22 September automatic LAN discovery removed the need to type addresses. The original Wait For Call and Dial now find each other with typed UDP query and offer packets, then claim a TCP connection before any modem audio flows. Three adversarial reviews and a cross-family review shaped the design; an independent code review then found four lifecycle defects, all fixed.

From the port

Bug 101: on two real machines, version 0.1.704 sat on STARTING LINK with continuous modem noise, while the in-process test harness connected perfectly. A two-process harness reached carrier, which moved the fault past negotiation. Two causes emerged. The production bridge advanced its UART with timer cycles but never passed them to the linked transport, so the original's serial timeout saw no time pass and could wait forever. And independent workers substituted silence whenever a network packet missed one 10 ms tick, which corrupted the first linked packet. A bounded three-chunk playout buffer fixed the second; publishing the timer and modem-control observations fixed the first. The dialog now names the live link phase, so any future stall reports where it stopped.

22 September: beyond the original

The last big day turned to things the original never did. A Claude session led three features, each with a design revised under adversarial review before any code landed.

The enhanced renderer redraws the whole race scene at window resolution, as an option, "reading source state and never writing it". Its first design tapped camera-relative road points. Three reviewers and a Codex review all found that unrecoverable, so revision 2 taps the resolved screen-space draw commands instead. A 60-frame owned-asset race with the renderer on and off proves the original's memory stays byte-identical. At 1280×960 a full composition cost about 1.7 ms. Chapter 12 covers it in detail.

Vehicle sets put old bangers or monster trucks on the grid, kept strictly separate from the original. The first design patched the executable image. Reviewers showed that was a no-op: the per-circuit driving block is decoded from the track at startup, and the renderer re-copies shapes from live memory every frame. Revision 2 overlays the decoded driving block, within bounds taken from the original's fixed-point maths (engine at most 1.0, grip at least 0.6, below which the corner solver overflows), and re-points a host-side shape override after each copy. Tuning was done against laps completed: at first a banger on grid 5 stalled in its tall first gear at the first corner, and raising grip made things worse; shorter gears fixed it.

Window presentation now shows every screen at 4:3 with integer-scaled pixels at any window size. Reading the code found nine separate buffer-update sites, some screens stretched and others shown squashed with a repeated last row. Revision 3 of the design lets the presenter do the tall-pixel mapping in one place, which deleted the older stretch, padding and mouse-correction code.

The final commits on 23 September make Championships honour the Vehicles setting and write up the architecture and testing guides.

A playtester's report produced one of the neatest examples. Bug 67 fixed a lap counter that stayed stale after a winner crossed the line again on the cooldown lap. The fix was verified. Then bug 103 reported that the dash still showed "6 of 5" in the running game. The earlier test had checked that a display service was called, not what the dash showed. The real cause was that the source lifecycle stopped at the finished-car gate before a later crossing could advance the winner's lap byte. The new regression reproduces the frozen 6, then checks the rendered 7 in the pixels. The record's instruction is the lesson: "verify the visible dash pixels, not only a display-service call".

What is not claimed

The status log is explicit that "no defensible whole-game completion percentage is established". The quality map rates the four main areas as Sound rather than Strong, because some evidence is still missing:

  • The final attended sweep through the outer menus, results and standings, on the integrated tree.
  • An exact-pixel comparison of the Championship ceremony.
  • Some one-sign mirror comparisons on a few circuits.
  • One open bug (97), a strict lint failure in the driver-team menu.

The raw capture files are also deliberately kept out of the repository, because they hold far more original memory than the fixtures distil. The repository records which captured bytes it relies on in a registered exception list, and that list may not grow without a row.
