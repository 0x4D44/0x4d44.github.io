Inside Formula One Grand Prix Part I — The original

Chapter 02

Circuits in a file

Each of the sixteen circuits ships as one small file. It holds no 3D model of the track. It holds a list of instructions: go this far, bend this much, climb this much, put a wall here. At load time the game runs those instructions and builds the real track, one 46-byte record for every sixteen feet of tarmac. This chapter follows that process from the file's bytes to the track the cars drive on. It ends with the two circuits the port authored from scratch.

Sixteen files, one grammar

The stock circuits live in F1CT01.DAT to F1CT16.DAT, in calendar order. Phoenix is 01, Interlagos 02, Imola 03, Monte-Carlo 04, Montreal 05, Mexico City 06, Magny Cours 07, Silverstone 08, Hockenheim 09, Hungaroring 10, Spa-Francorchamps 11, Monza 12, Estoril 13, Barcelona 14, Suzuka 15 and Adelaide 16. All sixteen use the same format. The port's catalogue (src/circuit_catalog.rs) keeps these sixteen IDs exactly as they are. Its separate user-facing catalogue (src/track_catalog.rs) adds authored tracks after them.

Much of the port's evidence comes from Suzuka. The v1.05 Practice route loads F1CT15.DAT, not Phoenix, and the emulator captures of the running game were taken there. Suzuka's main track expands to 1,203 records. That number comes up often below.

The file format was documented long ago by the community ArgDocs reference, which the port's parsers credit (src/track.rs, src/track_sections.rs, src/track_shapes.rs). What ArgDocs could not give was the executable's side: what the loader actually does with each byte. The port recovered that by reading the loader's code and checking every result against tables captured from the running original.

The file envelope

A track file is a fixed front section followed by variable data, ending in a checksum.

  • Horizon, bytes 0x0000–0x0FFF. A 512 × 8 indexed image: the distant panorama drawn behind the circuit (4,096 bytes, row-major).
  • Offset table, bytes 0x1000–0x100F. Eight little-endian words. The first must be 0x1010, the base every other offset is relative to. Word 4 locates the checksum, word 5 the object settings, and word 6 the track data. Word 7, at 0x100E, is the number of 3D object shapes.
  • Shape table and shapes. At 0x1010 sits one four-byte pointer per shape, then the shapes themselves.
  • Object settings. Fixed 16-byte records between the object-data and track-data offsets. Each one describes how to place a shape beside the road.
  • Track data. A short header, then the section stream, the encoded racing line, 38 bytes of driving parameters, the pit-lane section stream and a loader tail.
  • Checksum, last four bytes. Two 16-bit words computed over every byte before them. One is a plain wrapping sum. The other is rotated left three bits before each byte is added. The checksum offset must point exactly four bytes from the end, or the parser rejects the file.
The trap

On 4 September the port found 738 bytes after Suzuka's first 0xffff terminator: the main stream used 1,432 of the 2,170 bytes. A delegated decode claimed the expander simply kept reading past the terminator for a second run. Resuming the section parser there produced five "sections", one command and then an unknown-command error. The bytes had a regular 12-byte stride in two circuits, and a 10-byte section record with a zero second byte misparses easily against zero-padded data. The team recorded the claim as half right and did not act on it. Later loader work settled what follows the terminator: the encoded racing line, 38 bytes of driving parameters, and then the pit stream.

The track header

The track data begins with a header of word values. The loader reads it word by word (OriginalTrackStart in src/original_track_table.rs):

WordMeaning to the loader
0Heading of the first record (a 16-bit angle; the full circle wraps at 65,536)
1Pitch of the first record
2, 3, 4Start position: X, height, Z
5Road half-width in world units
7Side and scenery flags, copied to DS:0174. Bit 0x02 picks the side of the pit entry, bit 0x08 the side of the exit; the same byte gates the outer ground fill
8Right (low byte) and left (high byte) verge widths that the first section ramps from
9Number of kerb colour entries that follow
10…Kerb colour list: selector 8 is a fixed kerb and takes one word; every other selector takes two

ArgDocs names some of these fields differently. The port's first parser, TrackFile in src/track.rs, follows ArgDocs. The loader port follows the executable. The kerb list becomes a four-row kerb colour table, and eight "height words" are copied into two banks of scene data (src/original_runtime_track_header.rs, file 902DC..9041B). The loader then enters the expander.

The section stream

The heart of the file is a flat stream of two kinds of record, read two bytes at a time.

  • A section is ten bytes. Byte 0 is its length in track units and byte 1 is zero. Then come a signed curvature word, a signed height word, a flags word, and one byte each for the right and left verge widths.
  • A command starts with a one-byte argument and then a command byte between 0x80 and 0xAC. A per-command number of 16-bit argument words follows: none for 0x83, one for 0x80, two for 0x85, five for the wall commands 0x8a/0x8b.
  • The terminator is the two bytes 0xff 0xff.

The rule that tells them apart is simple: if the second byte is zero, it is a section. So a section can never be longer than 255 units; a length of 256 would put a non-zero high byte where the parser looks for a command. The port's authoring tool splits long straights for exactly this reason. Commands attach to the section that follows them, and the one-byte argument usually says how many records ahead of the current position the command acts.

Suzuka's main stream holds 76 sections and 153 commands. The sections carry the shape; the commands carry nearly everything else: width changes, scenery, walls, pit-lane markers, draw distances and anchor points.

Curvature and height

A section's curvature is how much the heading turns per track unit. Its "height" field is the vertical equivalent: how much the pitch changes per unit. Neither is a position. The track's shape only exists once the loader integrates them, unit by unit, from the start pose in the header.

From the port

Before the loader was ported, the project's first renderer had to guess what the height field meant. On 30 August the team checked all sixteen stock files. Individual height values ranged from −88 to +182, yet sum(height × length) stayed between −11 and +21 on every circuit, and two circuits used only zero. A value that sums to almost nothing over a lap behaves like a rate of change, not an altitude, just as curvature must sum to one full turn. The design treated height as a pitch increment and was marked as falsifiable. The real loader later confirmed the model, and on 10 September the guessed renderer was retired in favour of the original code.

The track expander

The code that turns the stream into a track sits in an overlay whose code segment starts at file offset 0x90000 of the unpacked executable. In the game's runtime addressing, 19ED:X is file offset X + 0x8B4D0, so the expander's entry 19ED:519F is file 0x9066F. It fires once when a session's track is built, with ES:DI pointing at the output table.

The port found it by an unusual route. Cited addresses had drifted, so the team searched the whole 600 KB image for one distinctive instruction pair, CWD; IDIV, which the width-ramp command uses. One scan found it at 0x90a5c. From there the command dispatcher was easy to recognise: it subtracts 0x80 from the command byte and switches on the result in cl.

Two passes, one switch

The expander reads each stream twice. A single byte, DS:0238, says which pass is running. The code at file 9066F..9069B sets it to 0 for the first pass and 0x80 for the second, and it does this for both the main and the pit bank.

  • Pass 1 (DS:0238 = 0) walks every section and writes the geometry: heading, pitch, position, width, verges and the trackside pattern bytes. First-pass commands change state for the records that follow: road width (0x85), pattern channels (0x8e/0x8f, 0x94/0x95), lane flags (0x98/0x99), a marker bit (0x83 clears it, 0x84 sets it), a reversed half-step (0xa5), and the pit entry and exit (0x86/0x87).
  • Pass 2 (DS:0238 = 0x80) walks the stream again with a cursor over the finished records. It attaches everything that needs a finished record to point at: object placements (0x80), draw-distance seeds (0x81/0x82), walls (0x8a/0x8b), pit strip bits (0x88/0x89), flag runs (0x92, 0x93, 0xa8), height words (0x9a), far pointers (0x9b–0x9e), anchors (0x9f/0xa0) and pit joins (0xa1–0xa4).
The trap

Because the game builds a main bank and a pit bank, it was tempting to read DS:0238 as "main or pit". It is not. It selects the pass, and object placement (0x80) runs during the second pass of either bank. Getting this wrong puts pit-lane scenery in the wrong place or nowhere at all.

Two details show how literal the port had to be. 0xa8 marks six records by adding 46 to a pointer six times, with none of the end-of-table check that 0x92/0x93 use. It can write past the active records; only 16-bit wrap stops it. And the run loop behind 0x92/0x93 is a "subtract one, loop while not negative" pattern that tests for zero only on entry. An argument of 0xffff runs once, while 0x8000 runs 32,769 times. The port reproduces both rather than "fixing" them.

The anchors deserve a note. The pit-lane join renderer reads its anchor from a far pointer at [bp+0x160], a stack slot. For a long time the port could not find what wrote it. A histogram of the main stream found no 0x9f or 0xa0. The answer was that they live in the pit stream and point into the pit table in segment 381C, not the main table in 4813. On Suzuka they select pit records 13 and 178.

Integrating the geometry

For each section the first pass does the same small loop (19ED:7477). It turns heading and pitch by a half step into the first record, by full steps between records, and by a half step out. This puts each record's heading at its own centre, not at its start. At each record it advances the world position with the executable's own 1.14 fixed-point cosine table:

x      += (sin(heading) × 1024) >> 14
z      += (cos(heading) × 1024) >> 14
height += (sin(pitch)   × 1024) >> 14

So one record is 1,024 world units long at heading zero. ArgDocs gives the track unit as sixteen feet, 4.8768 m. The port's authoring reports use exactly that: "4.8768 m = 1024 world units per record".

Command 0xa5 changes the rhythm. The next section begins by undoing the pending half-step and applying a full one. The port's authoring tool learned a related lesson the hard way: because each section applies two rounded half-steps, an odd curvature or height value split across a section boundary shifts the geometry. The compiler now rejects such splits.

Curvature packed by pi/2

Each record also stores a curvature word at +0x14. It is not the section's curvature. After a record is filled, code at file 0x929c8 calls 0x90140, which writes into the previous record:

previous.curvature = (boundary_delta × 0x6488) >> 14

Here boundary_delta is how far the heading at the record boundary moved, and 0x6488 is a fixed multiplier held at DS:0890. Since 0x6488 / 16384 ≈ 1.5708, this scales the turn by π/2. A raw boundary turn of 256 packs to 402; 1,024 packs to 1,608; −1,024 to −1,609.

The trap

The port's first racing-line fitter treated +0x14 as a plain heading increment. It fitted radii that validated on synthetic test tracks, because those tracks were built with the same wrong assumption, and failed on every real circuit. The fix was to recover the raw turn with a signed ceiling of packed × 16384 / 0x6488, then check it by packing again. The team verified exact inversion for all 41,721 unwrapped raw increments.

Closing the lap

Integer integration drifts. After a full lap the last position rarely lands exactly on the first. The loader measures the error between record 0 and the record one past the last (19ED:5C59..5DB9). It then spreads that error over records 1 to N with one integer accumulator per axis. Each record adds the absolute error to its accumulator, and whenever the accumulator reaches the record count it moves one more unit of correction into the running total. The effect is a linear ramp, record i corrected by about i/N of the error, done without a division per record.

The pass assumes a closed loop. An open test track collapses toward its start, so the port's table fixtures must be closed loops. The pit bank uses the same accumulator, but closes onto a different target, as described below.

The 46-byte track record

The result is a table with one 46-byte record per track unit. Suzuka's 1,203 records fill 4813:0030 onwards. The road renderer, the physics, the AI and the scenery all read it. The table below lists what each field holds, as src/original_track_table.rs and the loader journals document it.

Verges ramp smoothly. At each section start the loader computes a per-record step from the previous section's verge byte to the new one, in 8.8 fixed point, and adds it every record. +0x28/+0x29 hold the high bytes.

The strip bytes have a second life. Over a routed run (a run of records whose +0x26 carries 0x20 or 0x10), +0x28 is rewritten as a weight. For a run of length L, position i gets i + 1 on even positions and L − i on odd ones, so neighbours pair up to sum to L. For L = 8 the run reads 1 7 3 5 5 3 7 1. The renderer uses the byte both as a blend input and as a record stride: it subtracts byte × 0x2e from its pointer to find a partner record. A first attempt fitted 2L − i to what looked like a run of eight; it was half of a sixteen-record run, and reading whole runs corrected it.

Draw distances are spread after closure (19ED:6547, 65A5). A forward pass walks the table count + 256 times, carrying the largest +0x16 seed of 0x3c or more and letting it decay by one per record. Even records take the carry when it beats their own value. A backward pass does the same for odd records with the +0x17 seeds. A non-zero seed below 0x3c freezes a record.

How we know

On 18 September the port read the whole Suzuka table from the running original in fourteen authenticated chunks: 1,203 records × 46 bytes. It compared the port's own table against it byte for byte. 55,332 of 55,338 bytes matched. The six differences were all +0x25 wall-shade bytes that the original's display pass rewrites before the capture pause takes effect. A second test, on four frames of a fresh capture, matched all 55,338 bytes once car marks were accounted for.

The trackside pattern machine

Kerbs, verge stripes and roadside features are not stored per record. The loader generates them while it expands the track, with a small state machine at 19ED:7164 that runs once per record.

It has eight channels, kinds 7 down to 0, with masks 0x80 down to 0x01. Each channel has a 44-byte definition in the executable's data segment, at DS:0514 for straights and DS:0674 for curves. A definition holds an initial gap, two runs and two gaps whose lengths are (rng & mask) + base, two colour-pick arguments, two repeat periods and the channel's own counters.

A channel runs only when the section's processed flag word enables its kind. The loader processes the raw section flags as ((flags | 0xc300) ^ 0x3000) & 0xff37. A channel then cycles: wait out the gap, start a run of random length, and while running OR its mask into four accumulators. When a run starts, kind 7 draws a random width for the lateral feature and kind 6 for the longitudinal one, in the range −61..61. A colour nibble is picked through the table at DS:07D4 and redrawn once if it did not change. At the end of each record the accumulators become the kerb, edge, run and verge bytes (+0x0a, +0x0b, +0x27, +0x2a) and are cleared.

The five-byte random number generator

Everything random in the pattern comes from one generator, 0752:04D7, over a five-byte register at DS:2984..2988. Each draw reads the register as two little-endian words, shifts them, XORs the low bytes, then shifts the whole register up one byte and puts the new byte at the bottom.

That last point cost the port time. The Suzuka pattern bytes only matched the running original once the team captured the register at the loader's entry. The same generator also serves a later feature pass. Resident code at 0752:053C initialises the longitudinal track features with a temporarily seeded register, then restores the caller's six RNG bytes. A later resident step replaces each main record's longitudinal feature width and shade nibble from the racing line or the RNG.

Walls and the 0xb6 table

Walls are not geometry in the file. They are marks on records. Commands 0x8a (lateral wall, bit 0x80) and 0x8b (longitudinal wall, bit 0x40) each carry five words: a colour byte and mode byte, an outer count, an initial width, a width step, and a packed pair of counts called the phase and the gap. They run in the second pass, from handler 19ED:5B8F (file 0x90b8f).

The marking loop has three nested counters. Each outer pass marks phase + 1 consecutive records, then skips gap − 1, so the pattern repeats every phase + gap records. Suzuka uses both shapes. Phase 1, gap 1 marks every record: its two sixteen-record runs at 38..53 and 1026..1041. Phase 1, gap 2 marks two records in every three: the alternating run at 1163..1202.

The wall bits in +0x1f are only ever OR-ed. The clearing helpers touch +0x0b, +0x27 and +0x22, never +0x1f, so every record the marking step reaches keeps its bit. With both commands ported, about 74 records per circuit carry wall bits.

Each marked record also gets a width, computed by dividing by the axis half-width bits (axis_x & 0x3f). The divisor comes from the record where the command was seen, not the record being marked. Suzuka proves it: record 53 ends the 38..53 run with its own half-width bits at 54, which would give 432 / 54 = 8, but the original wrote 7, which is what 56 yields.

When the mode byte has bit 0x20 set, the handler at file 0x91046 overwrites that width with a table index: 0x7c + (step & mode), where the step is 7 on the inner loop and 6 on the outer. A single command therefore writes two indices. With mode 0x23 Suzuka's lateral walls alternate 0x7f and 0x7e; with mode 0x25 its longitudinal walls alternate 0x81 and 0x80.

Those indices point into the wall colour tables in scene data at 0xb6..0xdd: five eight-entry byte tables, three outputs (0xb6, 0xbe, 0xc6) and two sources (0xce, 0xd6). The sources are static in the executable image. The builder at file 0x91072 computes each output entry as source × 64 / (axis_x & 0x3f), signed and truncating. The 0xbe table is the record's previous feature width minus half the 0xc6 value. The final value of each entry is whatever the last record with that index wrote, so the table depends on geometry, not just on the circuit number.

From the port

A full 128 MB memory diff could not find the 0xb6 table's bytes anywhere else, which proved it was computed, not copied. Bisecting the menu recipe showed it fills during the menu phase, on the mode-select click, when the expander runs. Where the width division hits a zero divisor, the original's IDIV faults, and because the game hooks INT 0 the fault just sets a flag and the entry keeps its old value. The port reproduces that instead of adding a guard the original lacks. The team calls that kind of added guard its "recurring defect class".

The trap

An early port of the wall pass advanced two records per iteration. It produced period 2 everywhere and looked plausible. The live capture of +0x1f rejected it at the alternating Suzuka run, because the oracle had been built before the port. A later 49-agent review of the wall work found four more real defects, including a gap loop that never cleared its records and an outer loop whose exit falls into a trailing walk rather than returning.

The racing line and its speeds

After the main table exists, a second encoded stream describes the line the computer cars follow. The materializer at 95FC:23C0 reads it block by block. Each block starts with a header word: the low 14 bits are a record count, bit 0x8000 means an explicit lateral word follows, and bit 0x4000 means the radius has an extra high word. Then come a turn word and a radius. A header of zero ends the stream.

  • With a zero radius, the turn word is a simple heading change applied at the start of the block.
  • With a non-zero radius, the line follows an arc. The radius is in eight-world-unit steps; positive puts the centre to the right of travel. The turn word then means forward advance, in four-unit steps.

For every record the block covers, the materializer writes two words: +0x18, the line's heading minus the track's heading, and +0x16, the line's lateral offset. The walk wraps from the end of the main table back to record zero.

Corner speeds and the 63-group limit

Before the line is built, every record's +0x2c speed word is seeded to 0xEE00, and +0x16/+0x18 are zeroed. The speed annotation pass (0752:70A0 and neighbours, src/original_track_annotation.rs) then rereads the line stream and looks for corners.

A block qualifies as a corner only if it has no extended-radius flag and a non-zero curvature, and if 0x145F30 / |curvature| comes out at 60 or more. Each qualifying block becomes a group: its radius and a computed corner speed are stored as a pair in a 64-slot table at DS:3053. The pass stores the speed across the corner's records, accelerating where the corner allows, then walks backwards from the corner's entry, braking, so the approach speeds fall towards the corner speed.

Slot 0 is preset, which leaves 63 usable groups. A 64th group would overwrite the globals that follow the table, and the original then loops forever. The port turns that into an explicit error.

The pass also reads one record past the end: the closing record. On Suzuka the line loop produces 1,203 records but the guidance consumes 1,204. The port initialises the closing record's line words before this pass so it never depends on stale data. The team found this by poisoning the following record to expose any captured-input dependency.

Scenery objects

Trackside objects are placed by command 0x80. Its argument byte says how many records ahead the object sits; its word is a byte offset into the object settings. Each setting is 16 bytes: a shape ID, a detail level, a palette word, a distance from the track, two angles, a height and a second ID.

The distance is not in world units. The record's lateral axis already includes the road width, and placement multiplies (axis >> 6) × distance >> 5. So a distance of 256 is one road half-width from the centre line. Along the track, one record is 1,024 world units.

The object's class is the setting's offset divided by 16, and classes 0 to 2 are special:

  • Classes 0 and 1 render a nested scene through 15F2:A675. The authoring notes call them the reserved camera placements; they publish the pointers at DS:01C4/DS:01C8.
  • Class 2 is a marshal post. It borrows setting 2 when the post is left of the road and setting 3 when it is right.
  • Classes 4 and 5 are pit objects whose palette comes from a team's car colours.

Ordinary scenery must therefore use settings from index 3 upwards. The shapes themselves are track-local 3D models. Each has a 32-byte header with ten-byte detail-level records (a depth threshold, a scale mask, an angle shift and an element-list offset), eight-byte points and two-byte vectors. Polygon colours are indices into a shade row, not palette bytes; flat objects have sixteen entries per row.

The pit lane

The pit lane is a second track. It has its own section stream after the racing line and driving parameters, and its own table of 46-byte records. The main bank is table A at 4813:0030; the pit bank is table B at 381C:D7AE.

How the pit bank is built

When the main first pass meets command 0x86, it snapshots its whole expansion state. Command 0x87 marks the exit. After the main bank is finished and closed, the loader restores the heading, pitch, flags, verges and pattern state from the 0x86 snapshot. It sets the pit half-width to 0x280 and the outer width to 0x2d0. It starts the pit at the main entry record's position, shifted sideways by the difference between the main width there and 0x280. Header bits 0x02 and 0x08 decide which side the entry and exit offsets fall on.

The pit stream then expands with the same code and the same two passes. Pit records get index words based at the saved count plus 0x2000. Command 0xa9 sets their draw distance. Instead of closing onto its own start, the pit bank closes onto the main exit record, offset sideways. Finally the loader copies the main exit record into the pit's last slot, so the lane rejoins the circuit exactly.

Joins, anchors and walls

Second-pass commands 0xa1–0xa4 publish four join pointers to scene data at 01AC and set a pit-side wall bit, 0x20 or 0x10, in +0x1f. Which bit depends on the side flags. On Suzuka the main joins select records 1049/1050 and 22/21. The anchors from 0x9f/0xa0, described above, give the renderer the pit records where the lane's join geometry is drawn from.

The service window

Commands 0x96 and 0x97 publish two pit record indices to DS:019C and DS:019E. Command 0x89 publishes a pattern anchor at DS:019A. A car's stop target is DS:019A + 1 + 3 × team: the teams' bays are three records apart. To actually stop, the car must be at least 0x400 sideways, at or past its bay record, and at least 0x1E0 into that record. Meanwhile the physics clamps the car's steering reference to the window from the first bound + 10 to the second bound − 10. The stock values show the pattern: Barcelona uses 52, 77 and 139 for 0x96, the 0x89 anchor and 0x97; Suzuka uses 95, 103 and 166.

The implicit outer boundary

A pit record with no wall bits is still not open ground. The ordinary collision path compares the car's lateral position plus 512 against width + ((width × strip) >> 5) + 80, where the strip is the verge strip byte. So a narrow strip byte is a wall in all but name. This matters, as the port found out below.

Horizon and ground

The first 4 KB of the file is the panorama: 512 columns by 8 rows of palette indices. The sky stage (15F2:7D2E..7DFD) fills the sky upwards from a colour-band table, then draws the panorama with its bottom row on the camera horizon. The column comes from the camera heading shifted right five bits and wrapped at 512, so one full turn of 65,536 heading units sweeps 2,048 columns, four times round the image. The horizon row itself is 0x50 + (sin(pitch) >> 6) with a fixed −0x400 camera pitch. The stage then paints the ground colour below.

A record can hide the panorama: the stage checks section flag 0x08 on the car's record. That is the same +0x26 bit that commands 0x83/0x84 control. (That these two are the same switch is our reading of two separate sources, not a traced call chain.)

Writing new circuits

Once the port could load every stock circuit exactly, the author asked for something the original never had: new circuits in the original format. The design (9 September 2026) set a strict bar. Bahrain had to be recognisable, use the existing cars and physics, and complete a three-lap race with a full grid and a real player pit stop. "A parser success or a screenshot is not completion."

The result is track-author, a second binary in the same Cargo package. It compiles a frozen source package into a complete DAT: envelope, main and pit section streams, racing line, the 38 named driving parameters, loader tail, authored shapes, settings, placements and checksum. It has no network access and reads no game assets. Its source data are open geometry, frozen with checksums: OpenStreetMap ways for Bahrain (ODbL) and the Madrid city Geoportal's MADRING dataset for Madrid. Widths and elevations are labelled estimates, since neither source provides them. Bahrain became catalogue entry 17 and Madrid entry 18.

What the pit lane taught

Bahrain's first complete file loaded on 10 September. It then failed, in turn, in almost every way the pit-lane mechanics above allow.

  • Mode bits. A car reached the pit entry record within the ±720 lateral gate and was refused. The compiler had written all pit sections with flags zero. The source rejects a pit record whose low +0x26 bits are zero. Lifecycle pointers alone do not enable the route. The fix was to author entry, through and exit modes 1, 3 and 2 and an outside suffix, modelled on Suzuka's layout.
  • The service window. With entry fixed, the car drove through without stopping. Bahrain's 96/128 window clamped the steering reference to pit records 106–118, entirely after the line's service patch at 87–98. Held steering decayed and the car returned to the lane centre. Moving the first bound to 52 put the bays inside the window.
  • The invisible wall. The car still could not reach its bay. The pit strip byte was 16, and through the implicit boundary formula that blocked the 1,024-unit move to the service gate. A strip of 96 (0x60) on the service side cleared it.
  • Missing parameters. An earlier probe spun for ten million work steps at the first pit record. The driving-parameter encoder had skipped the byte at DS:020D, shifting every later scale word. The corrected encoder names all 38 bytes at their decoded addresses.

Madrid added one more. Its pit centreline ran backwards relative to the source, so the loader got an exit pointer that did not precede the entry in the wrapped main bank, and refused to start. The compiler now rejects any such pair.

What the racing line taught

Bahrain's first line used only zero-radius blocks: straight chords with heading changes. It passed every geometric check. But zero-radius blocks never qualify as corners, so all 1,112 speed words stayed at the seed 0xEE00 and no corner-speed group was built. The computer cars had no idea where to brake.

The fix was to fit real arcs. The fitter finds same-sign curvature runs of at least 60 (recovered through the π/2 unpacking), seeds each radius from 0x145F30 × count / curvature sum, and replays each candidate through the port's shared materializer so every block sees the true incoming state. It must stay within the 63-group limit. The final Bahrain file produced 39 groups and 1,211 speed stores, and all fifteen named corners showed braking in the 16 records before them. On 10 September the final 12,060-byte file passed the full test: a three-lap race with the player serviced in the pits, and all 26 cars ending classified or retired.

Madrid's hairpin failed the same way two days later. It was encoded as chords, left at the seed speed, and one computer car stalled against it near record 250. The fitter now keeps short variable-radius corners while leaving room in the shared group table. Madrid then produced 35 groups and 929 speed stores, and passed its own full race with a pit stop.

From the port

The lesson the team wrote down is blunt: "a parser success or a screenshot is not completion". Each failure above passed some static check first: a clean load, a good geometric fit, a correct-looking cockpit view. Only a real car driving the real loop through a real pit stop exposed them. And every one was a fact about the original engine, not about the new circuits.
