## Engine contract (existing, reused verbatim)
`cruise-games-engines.js` exposes `window.CruiseGames`. Each game:
`new Game(canvas,{sfx,onState})`; methods `start()`, `reset()`, `destroy()`;
`onState(partialObj)` emitted only on discrete change (score/lives/msg/over).
`Base` already wires the RAF loop, pointer events (canvas-space via `_pt`),
rounded-rect + HUD helpers. Canvas is 640×920. The hub (`games.dc.html`)
mounts `K[CLASSES[screen]]`, forwards `sfx`/`onState`, and persists bests to
`localStorage["cg_best"]` per game key.

## The four games (each a small, self-contained engine)
1. **Leaning Tower of Pisa — `Pisa`** (overhang-**slice** stacker,
   Tower-Bloxx/"Stack" style — a genuinely different mechanic from Shipwright's
   balance physics; see revised D4). A tier slides side-to-side above the tower;
   tap to drop it. The part overhanging the tier below is **sliced off**, so the
   tower narrows as it rises; a dead-centre drop is a "perfect" (no trim, tiny
   width bonus + a nicer sound). Miss the stack entirely → over. The view scrolls
   down as the tower grows and gains a gentle **cosmetic** lean/sway with height
   (flavour only — it does not affect play). Best = tiers stacked. This shares
   almost no code with Builder (no centre-of-mass, tilt, or capsize physics).
2. **Colosseum Escape — `Colosseum`** (maze/dodge). You start in the arena sand;
   steer (drag-to-set-heading, reusing pointer) toward the exit gate while 2–3
   lions chase with simple seek AI. Reach the gate = win (advance a round, more
   lions); caught = over. Bloodless, cartoon. Best = rounds escaped.
3. **Barcelona Mosaic — `Mosaic`** (tile puzzle, a genuinely new mechanic). A
   small grid of tiles; tap a tile to cycle its colour; match the shown target
   pattern to complete, then a fresh (reachable) target appears. Best =
   **patterns solved** — higher-is-better, a single comparison direction (no
   "fewest taps", which would need the opposite comparison — see Δ3).
4. **Ports Quiz — `Quiz`** (trivia, canvas-rendered — D3). Multiple-choice
   questions drawn from the real itinerary (ports, foods, sights). Tap the
   answer rect; correct → streak++, wrong → over (or lives). Best = best streak.

## Muster-station card (Extras tab)
A new section mirroring the existing journal pattern **exactly** (Δ6): a short
plain-English drill explainer (what muster is; the 7-short-1-long horn =
assembly; life-jacket location; that the drill happens before sailing) plus
**editable fields** — muster station, deck, cabin — the family fills in from
their SeaPass, persisted on-device. We can't know their real assignment, so it
is user-entered (D5). **Safety wording is humble and accurate (ΔC6):** it defers
to the ship's crew and PA announcements, and states the general emergency signal
as "**seven or more** short blasts followed by one long" (the SOLAS general
alarm) — not a more-authoritative-than-the-ship "exactly seven". The card is a
memory aid, not a substitute for the official briefing. The inputs are **uncontrolled** — `defaultValue` +
`onInput` writing to an instance field `this.muster` and a `hm_muster`
`localStorage` key inside try/catch, never `value=` and never `setState`.
Reason: the app `forceUpdate`s every second (`tick`), so a controlled input
bound to a plain field would have its typed characters reverted within ~1 s.

## Decision log
- **D1** Don't rebuild phrasebook/currency/packing — already present & correct
  for the itinerary (cheapest code is code you don't write).
- **D2** No French phrases — no French port on this sailing.
- **D3** Quiz rendered on canvas (big tap rects) to keep **one** engine contract
  — no DOM special-case in the hub.
- **D4** (revised after review — Δ1) Pisa uses a **different mechanic** —
  overhang *slicing* (timing/precision), not Shipwright's centre-of-mass
  *balance*. That is what justifies a separate engine: it shares almost no logic
  with Builder (no CoM/tilt/capsize), so cloning was never the plan. The earlier
  "avoid a feature flag / duplication < wrong abstraction" rationale was a
  misread (data-theming isn't a flag, and Builder is a *stable* existing
  abstraction — cloning it would have been the expensive mistake). The honest
  reason for a separate engine is simply that the mechanics differ; Pisa is also
  *simpler* than Builder.
- **D5** Muster station is **user-entered** (can't know their real assignment),
  persisted like journal notes.
- **D6** **No node test harness** — repo has zero test infra; a stubbed-DOM
  runner would be overengineering. Verify behaviourally (headless Chrome) plus
  the quiz integrity self-check; keep game logic in small clear methods.
- **D7** All new game code stays in `cruise-games-engines.js` (no new JS file),
  so the SW `CORE` precache list is unchanged; only `VERSION` bumps.

## Residual risks
- **R1** Four canvas games is a lot of new code in one change; mitigated by a
  shared `Base`, keeping each engine minimal, `node --check`, and the
  behaviour-drive tests.
- **R2** Canvas-rendered quiz text wrapping/tap targets need care on narrow
  phones; mitigated by generous rects, short answer strings, and a word-wrap
  helper.
- **R3** VERSION bump forces a one-time re-cache for returning users (expected;
  scoped cleanup already protects sibling PWAs).
- **R4** A v2 precache immediately after deploy could momentarily capture
  CDN-stale bytes (this repo has documented CDN stickiness); network-first
  overwrites on the next online load, so it self-heals within one `max-age`
  window. Accepted rather than complicate the SW.
