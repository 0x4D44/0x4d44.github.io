# King's Cross live 3D model: design (draft for discussion)

Status: draft, 2026-11-07. Nothing is built. Labels: **[fact]** observed this session,
**[assumption]** needed but unchecked, **[guess]** my inference.

## Goal

A three.js model of King's Cross station at true scale, with trains that move where the
real trains are now. Live data arrives through a small relay running on Arthur's machine
for development. A recorded replay mode is the fallback, so the page still works on
GitHub Pages with no relay.

## Layout in this repo

- `kings-cross-src/` — source. Own `package.json` (vite, three), tests, and `relay/`.
  Its Vite `index.html` sits in `kings-cross-src/web/`, because `tests/responsive.test.mjs:184`
  treats any top-level dir with an `index.html` as a published document. [fact]
- `kings-cross/` — built output, served by Pages. Vite `outDir` writes straight here,
  `base: "./"`, so there is no copy step and no source/output drift.
- Precedent for a nested package: `cairn-run-rally` (`npm --prefix cairn-run-rally test`). [fact]
- Add the shared back pill to the built page (`<script defer src="/almanac-back.js">`).
  Vite drops it on rebuild, so put it in the source `index.html`.

### Live movement: Network Rail Open Data

- **Train Describer (TD)**, one ActiveMQ topic (`TD_ALL_SIG_AREA`) carrying two message classes. [fact, from the Open Rail Data wiki via search]
  - **C-class**: a train description (headcode) steps from one *berth* to another. This is
    the live "where is each train" signal. It reports berth-to-berth steps, not metres.
  - **S-class**: signalling equipment state (signal aspects, points) as a bitmap of up to
    2,048 bits per area. Each bit has to be matched to a signalling diagram to mean
    anything, and **not every TD area provides S-class at all**. [fact]
- **SMART** reference data maps berths to locations (STANOX). **CORPUS** converts location
  codes. Both need the "All Reference Data" subscription on the data feeds account. [fact]
- **Darwin** (National Rail) gives platform numbers, times and cancellations. It is a
  separate registration. [assumption] It's needed to show the platform a train is booked to,
  so a train appears at the right platform before its berth steps confirm it.

**Phase 0 result (SMART and CORPUS downloaded 2026-11-07 from Arthur's account; SMART
file dated 2026-10-19, CORPUS 2026-10-02).** Raw files live in `~/kx-data/`, outside git.

- **King's Cross is TD area `Y9`, not `KX`.** SMART has no rows at all for `KX` or `K2`;
  its only K-areas are `KG`, `KM`, `KN`. The wiki pages named `KX` and `K2` use other
  names, so ignore them for this area. [fact]
- **Y9 covers more than the station:** King's Cross (STANOX 54311, 58 rows), Belle Isle,
  Copenhagen Jn, York Way Jn, Holloway Jn, Finsbury Park, Harringay, Hornsey, Highbury
  Vale Jn, and the Moorgate branch (Drayton Park, Essex Road, Old Street, Moorgate). 262
  rows and 165 distinct berths in total. [fact]
- **Platform berths:** berth `1000`+N is platform N, for platforms 0-10. Arrival steps
  come in from berths `2034, 2036, 2040, 2042, 2046, 2048`, with a `BERTHOFFSET` of about
  +90 to +121. Departures leave to `1015, 1017, 1021, 1023, 1027, 1029` (for example
  platform 0 -> 1029, platforms 2-4 -> 1023, platforms 8-10 -> 1015). [fact] The unit and
  sign of `BERTHOFFSET` I read as metres along the line [guess].
- **Gaps:** SMART lists only berths that raise arrival and departure events. It does not
  list every berth in the throat, so the full berth list has to come from the recorder
  (phase 2). SMART stops at platform 10, while OSM has platform refs up to 13 plus A and B.
  Platform 11 and what OSM's 12, 13, A, B are need checking [guess: some are not
  King's Cross mainline platforms]. The rows are dated 27/03/2022. [fact]
- **Signal state (S-class) for Y9 exists.** Confirmed by the recorder, see "Live
  recording" below. Decoding it is still open work.
- **Do not commit the raw SMART or CORPUS files.** They are 7 MB each, and the licence
  terms on republishing are unchecked. A small derived berth-to-track map is the thing to
  commit, after the terms are checked.

## Scope decision (2026-11-07)

The model covers King's Cross station, its throat, and the approach north through Gasworks
and Copenhagen tunnels as far as the OSM extract goes (zone `KINGS_CROSS` plus the track
network in the extract). Y9 trains whose berths are not on that network (the Moorgate branch,
Hornsey, and so on) are counted but not drawn. The St Pancras and Underground platforms in
the extract are context only.

## The hard part: berth -> track

1. Build a routable graph from OSM (rail ways joined at switch nodes).
2. From SMART + the Y9 berth list (platform berths 1000-1010 and the approach and exit
   berths above, plus whatever else the recorder sees), assign each berth an anchor on
   that graph (a track section between two points).
3. A C-class step `A -> B` moves the train's progress target from berth A's anchor to berth
   B's. The renderer interpolates along the graph between them at a plausible speed, and
   caps at a sensible stop (buffer, or the next berth) if the next step is late.
4. Platform and route come from Darwin plus the platform ref, as a cross-check.

Failure modes to design for: a berth with no anchor (render a marker, log it), a step that
jumps over several berths (path-find through the graph), and a headcode that vanishes
(fade out, don't pop).

## Relay (dev, on Arthur's machine)

- Node process. Holds one STOMP connection to Network Rail (and later Darwin). Reads the
  login from the macOS keychain inside the process (item `kx-ntrod`). Never returns, logs
  or commits it.
- Filters to TD area `Y9` messages. Keeps current state (berth occupancy, signal bits) so a
  new browser gets a snapshot, then deltas.
- Browser protocol: Server-Sent Events (built into Node, so no dependency; the page only
  reads). `/events` sends `snapshot` then a `td` event per change. One event schema
  (`core`/`relay` `td.mjs`), shared by the relay, the recorder and the replay player, so the
  same code path runs live and from a recording. Built and tested; see
  `kings-cross-src/README.md`.
- Recorder: the relay can write the filtered stream to a file; replay plays it back in
  the browser with no relay. This is also the test fixture source.
- Public hosting is out of scope for now. The page must still load and show replay when
  the relay is absent (same stance as `worldviewer`'s inert live-ships toggle).

## Rendering (three.js, Vite + TypeScript)

- Pure, tested core (no DOM): OSM -> graph, berth anchors, interpolation, replay clock.
  Same split as `mdtrain2`/`mdsnake`: tested sim core, thin renderer.
- Station shell from OSM building outlines, extruded; train shed roof and concourse
  hand-modelled. Platforms from the platform ways.
- Trains: Class 800/801 (LNER Azuma), 802 (Hull Trains), 803 (Lumo), Class 43/other as
  needed, built from published dimensions. Liveries drawn procedurally, not photo
  textures (licences are uneven and flat colour reads better on a box-like model).
  CC0 texture sets for ballast, concrete and brick.

## Risks

- Berth anchors are the biggest unknown. If SMART lacks good KX rows, positions are only
  platform-level (still a decent product).
- OSM signals are incomplete (34 of 60 with refs), so aspects need a reviewed overlay.
- Feed terms: redistribution of the data to the public must be checked before any public
  relay. Dev use only until then.
- Bundle size on Pages: keep geometry as compact JSON/binary; Draco/meshopt only if needed.
- `CLAUDE.md` still says the repo has no `package.json` and no test suite, but both exist.
  Not changed here (we don't edit CLAUDE.md unprompted).
