# Plan to Build: a CAD drafting film that builds the apartment in 3D

Added `/plan-to-build/`, one self-contained `index.html` (about 185 KB), on The Drawing Office and The Built World shelves with a new `ill-plan` sprite icon. three.js r186 (with `RoundedBoxGeometry` and `RoomEnvironment`) and mp4-muxer 5.2.2 load from jsDelivr through an import map, so the page needs a network. three.js loads in the background: the 2D half plays at once and the 3D half joins when it arrives. If it never arrives the visitor is told, the 2D half still plays, and the render button says why and refuses before it opens the save dialog, rather than write a film with no second half.

**What it shows (3:12, 191.93 s).** An AutoCAD-style screen types real commands (LINE, OFFSET, COPY, INSERT, DIMLINEAR and about twenty more) while a crosshair snaps and clicks: grid lines, a 400 x 400 column copied to every crossing, 300 mm block walls with 150 mm insulation, doors and windows, furniture at real sizes, dimensions, room areas (7 rooms, 92.0 m2) and a 1:50 sheet. A selection window grabs the plan at 117.93 s, the screen dissolves into a three.js scene whose ground is the finished drawing, and the model builds from the same data: columns, block walls, insulation, lintels, windows and swinging doors, oak and tile floors, kitchen and bath, then 40 pieces of furniture dropping onto their drawn footprints. The interiors are filmed through a live section cut at 1.3 m (SECTIONPLANE, lifted again with ERASE). 18 chapters, one chip each.

**One timeline.** `renderFrame(ctx, W, H, t)` is a pure function of the clock. The player, the scrubber and the exporter all call it; the exporter steps t = i / 60, draws 2560 x 1440, hands each frame to a WebCodecs `VideoEncoder` and muxes with mp4-muxer, so the file is exact however slow the machine is.

**Review.** An independent reviewer (Opus, fresh context, reading the code, running nothing) returned 15 findings. Twelve are fixed outright. Each has a check that failed on the page as it was before the review and passes now (at the last baseline run, 32 of the 47 checks in the repaired sections failed there), except the corrected comment, which has none of its own:
- the blocking top-level `await import('three')`, now a background load;
- the Render button doubling as Cancel (a double-click, or Space while it had focus, cancelled the render: it now has a start guard and blurs after a click);
- one throwing frame leaving the canvas clipped and black, and a `?t=1:30` or `?t=90s` link causing it (the frame is reset, playback stops after one console error, and `?t=` takes `90`, `90s`, `1:30` and `1:30.5`, anything else opens at 0);
- no message when three.js fails to load, and the save dialog opening before the render found out;
- the play button keeping the keyboard focus, key repeat on Space, the big play button left over a keyboard seek, and a negative first time step;
- the timeline slider's arrow keys moving 10 ms (they now skip 2 s, Shift 10 s, PageUp and PageDown 10 s, Home and End, like the rest of the page: **a behaviour change**);
- accessibility: play button label, `aria-valuetext` on the timeline, `aria-current` on the chapter chip, a progressbar role and a live region for the render;
- first-draw stalls in the 3D half (10 spots took 165 to 906 ms the first time; the warm-up renders the half in idle slices and the slowest first draw is now 70 ms);
- a lost WebGL context (an export now refuses to write blank frames while it is lost, and the environment light is rebuilt when it comes back: 0 pixels differ before and after);
- a wrong comment about what the save dialog does to an existing file;
- a muxer error on the first chunk skipping the codec fallback, and no H.264 Baseline in the codec list (added; only its place in the list is checked here).

Three are fixed in part:
- **Memory without a save dialog (finding 1, High).** Firefox, Safari and Android Chrome have no `showSaveFilePicker`, so the muxer buffers the whole MP4. On those browsers the 24 and 40 Mbps options are now disabled (16 Mbps), and the finished file stays behind a "save the MP4 again" link instead of a URL revoked after a minute. The buffering is unchanged, so peak memory stays a few times the file (inference); a real fix is a streaming rewrite.
- **Fullscreen (finding 3).** A screen that is not 16:9 now letterboxes the film (`object-fit: contain`) instead of stretching it. iOS Safari has no `requestFullscreen`, so F and a double-click do nothing there, and the page cannot change that.
- **Full disk (finding 15).** The screen wake lock is now asked for again when the tab comes back. mp4-muxer still does not await its file writes, so a full disk fails late.

**Checked here (all headless, at the lowest process priority, every child process window hidden).**
- Catalogue entry, 14 checks: unique slug, URL, ISO date, tags on both axes, icon present, tagline 50 words, on two shelves, nothing unshelved.
- `tests/responsive.test.mjs` narrowed to this document: no sideways scroll and nothing under the back pill at 390 and 768 px. Screenshots of the controls at 1400 and 390 px, with the progress row and the "save the MP4 again" link showing, look right.
- Player, 31 checks: big play, play/pause, 18 chapter chips, scrub, arrow keys, speed 2x against 1x, end of film, restart, no console errors, and the same frame after seeking away.
- Review fixes, 64 checks: those fixes that can be seen headless (the wake lock and the Baseline encoder cannot), plus a slow three.js (held back 6 s: the drafting plays at once, the 3D appears when it lands), a blocked three.js, a browser without a save picker (double-click, Space, the "again" link, the 16 Mbps cap) and a muxer failure on the first chunk.
- Export, 69 checks (`window.__export`, a trusted click and an OPFS stand-in for the save dialog): H.264 High 2560 x 1440 60 fps, exact frame counts, moov before mdat, decoded frames against `renderFrame` at 35 to 44 dB, abort and cancel, VP9 and AV1 fallbacks, no console errors.
- The whole film through the real Render button (a trusted click, an OPFS stand-in for the save dialog), after the review fixes: 11,516 frames in 153 s (75 fps; the first run took 424 s with the box busy), 221.5 MiB at a 16 Mbps target (9.7 Mbps average: the software encoder undershoots), 3:12, H.264 High 2560 x 1440 60 fps, duration exactly frames / 60, every frame decodes.
- That file, 26 checks: ten spot frames from 0 s to 191.67 s, decoded by frame number, match `renderFrame` at the same t at 32.8 to 43.3 dB, and none matches a neighbouring frame better than its own (equal only where the picture is still: frames 0, 600 and 7075).
- 2D to 3D handoff: no visible offset between the 2D drawing and the ground texture at 1920 px; the difference image is edge antialiasing only.

**Not verified.** The native Save dialog (headless cannot show it), a real hardware encoder (headless Chrome 155 rejected every `prefer-hardware` config and used software), the H.264 Baseline fallback (only its place in the codec list), the no-save-dialog path at full length (it ran on clips of 1 and 6 s; the memory estimate for 192 s is inference), Firefox and Safari, a real phone. The check scripts live in the session scratchpad and are not committed.

**Gotchas.** Re-rendering the same t is repeatable to within 1/255 on a handful of pixels in the window openings (5 of 60 back-to-back renders at 640 px; none at 1280 px, none in the 2D half), so the checks allow that and nothing more. The clock advances per animation frame (at most 0.1 s of wall time each), so a starved machine plays slower rather than skipping. To check a finished MP4 frame by frame, decode by number: `ffmpeg -ss` returned frame i+1 for some i, which looked like two failed frames until the PSNR against the neighbours showed the file was right and the check was wrong. See `lessons_learnt.md` for that, the first-draw stalls, the Cancel button and the section-cut, H.264 level and shadow-map notes. Two unrelated defects in `tests/responsive.test.mjs` (a Windows cleanup that never stops Chrome, and a silent skip when `CHROME_PATH` is unset) are in `scratchpad.md`.
