# 2026.07.10 — JRN — span-of-control review fixes

Fixed the three confirmed findings from the pre-integration review of the
span-of-control document (the review ran as an adversarial multi-lens workflow
before the original integrate; no blockers, three should-fix + one nit).

## 1. Arc ordering — the Vision Deck could play out of sequence
`up-vision` is a strict `once` escalation gag: v1 (5 slides) → v7 (31) →
final (82). Bug: v1 set flag `up-vision`; **both** v7 and the finale gated on
that same flag, and v7 set no new flag. So the moment v1 was played, the finale
was eligible and the open weighted deck could draw the 82-slide premiere before
the 31-slide middle beat. Worse, the finale is `once`, so `engine.draw()`
(line 133, `if (c && isEligible(c))`) silently discards the copy v7 later queues
— collapsing 5→31→82 to 5→82→31.

Fix: v7's two choices now `setFlags: ["up-vision-tightened"]`, and the finale
`requiresFlags: ["up-vision-tightened"]`. Matches the pattern the other staged
arcs already use (abs-meridian-chair, down-greg-countered) — each stage unlocks
the next.

Root cause is the engine invariant, not this one arc: **`engine.draw()` plays a
queued follow-up only if it's still `isEligible()`, and `isEligible()` knows
nothing about arc order.** So a `once` follow-up target must be unlocked by the
very choice that queues it, or the open deck can draw it unbidden and the queued
copy is dropped. Encoded that as an oracle in `content.test.mjs` (repeatable
pool cards like the reorg pair are exempt — they share the engine's
`reorg_looms` flag and are deliberately unordered). Verified the oracle FAILS on
`origin/main`'s content (`up-vision-v7.left -> up-vision-final: must set one of
[up-vision], sets []`) and passes after the fix — a test that couldn't catch the
bug it's written for is worthless.

An audit of every follow-up in the deck found exactly these two `once` arcs;
only up-vision was broken.

## 2. Homily overlay could soft-lock a touch-only player
`.overlay` was `display:flex; align-items:center` with no `overflow-y`, and
`.homily-card` had no `max-height`. A flex item centred in a fixed container
overflows equally off BOTH edges with nothing to scroll — so on a short
(landscape phone) viewport the "Pin it up" button dropped off-screen and a touch
user, whose only dismiss path is that button, was stuck.

Fix: `align-items:flex-start` + `margin:auto` on the card (centres when it fits,
pins to a scrollable top when it doesn't) + `overflow-y:auto` +
`overscroll-behavior:contain`.

Drove the real overlay over CDP (Node's built-in WebSocket, no deps), forced the
longest homily (158 chars), and swept viewport heights old-CSS vs new-CSS on the
same DOM. Threshold: old CSS clips the card top from 280px down, button
off-screen at 240, fully **unreachable** at 200. New CSS: clean 200–360px.

## 3. viewport-fit=cover with no safe-area insets
index.html opts into `viewport-fit=cover` (content runs under the notch/status
bar) but nothing reclaimed the inset, so an installed (display:standalone) PWA on
a notched device had the status bar sitting on top of the header. Added
`env(safe-area-inset-*)` padding to `.chrome` (top+sides), `main` (bottom+sides,
for the home indicator), and the overlay. Shorthand precedes each `env()`
override so non-supporting browsers keep the original padding. Insets are 0 in a
normal browser tab, so no visual change there (verified by screenshot).

## Nit: modal focus
The overlay declares `role="dialog" aria-modal="true"` but never moved focus or
trapped it. Now: capture the focused element, `inert` the header + main, focus
the OK button, restore focus on close. `aria-modal` is only an AT hint, so
`inert` is what actually keeps Tab out of the background.
