# Exterior kit textures and binding contract

The library contains one shared **512 × 512** prop atlas, with matching colour,
normal and ORM PNG planes, plus **twelve 1024 × 1024 wall materials**. Each wall
has its own albedo, normal and ORM KTX2 file and all eleven mip levels. These are
original procedural images generated by `extkit_textures.py`; no photographic
texture, scraped artwork, manufacturer mark or external image is incorporated.

The twelve finishes are six painted-plaster colours (azul añil, turquesa,
amarillo ocre, terracota, verde menta and rosado), exposed tolete brick, damp
tolete brick, cement block with mortar, a baldosín band, streaked rough pañete,
and aged whitewash. The extra damp-brick finish resolves the brief's request for
twelve materials while its enumerated finishes total eleven. The six paint
finishes have separate peeling and damp patterns rather than identical damage
recoloured six times.

## Why the wall maps use compressed GPU formats

Thirty-six 1024-square maps alone would require about **201 MB** as RGBA8 with
mipmaps, exceeding the library's 40,000,000-byte GPU limit. The wall maps retain
BC texture blocks on the GPU:

| Plane | Vulkan format | GPU data | Colour space |
| --- | --- | --- | --- |
| Albedo | `VK_FORMAT_BC1_RGB_SRGB_BLOCK` (132) | 8 bytes per 4 × 4 block | sRGB |
| Normal | `VK_FORMAT_BC5_UNORM_BLOCK` (141) | 16 bytes per 4 × 4 block | Linear |
| ORM | `VK_FORMAT_BC1_RGB_UNORM_BLOCK` (131) | 8 bytes per 4 × 4 block | Linear |

Every mip is independently ZLIB-compressed inside a KTX2 container, using
standard supercompression scheme **3**. This is documented by the
[Khronos KTX 2.0.4 specification, §3.8 and Table 2](https://registry.khronos.org/KTX/specs/2.0/ktxspec.v2.html).
The data-format descriptors retain BC block dimensions, channel descriptions
and transfer functions as required by §3.10.3.1. The
[Khronos Data Format specification, §5.6](https://registry.khronos.org/DataFormat/specs/1.4/dataformat.1.4.html)
defines the BC1 and BC5 channels used here. This is native BC data; it is not a
Basis Universal texture or an embedded glTF texture.

Measured texture disk total is **6,083,057 bytes**. The exact sum of all wall mip
block data is **33,555,072 bytes**. Conservatively treating all three atlas PNG
planes as RGBA8 with complete mip chains adds **4,194,300 bytes**, for
**37,749,372 bytes** with **every wall and atlas texture simultaneously resident**.
This total does not assume streaming, selective residency, compressed PNG
memory, or omission of the wall library. The independent validator can use the
conventional infinite `4/3` mip estimate for the atlas, yielding four extra
bytes; both values remain below the cap.

Before BC encoding, normal X/Y values are quantised with maximum error
2/255 per channel and ORM occlusion/roughness values with maximum error 4/255.
This removes insignificant low-bit noise so the authored damage, mortar and
surface variation fit the disk budget. Albedo is not prequantised. Albedo mips
are filtered in linear light; normal mips are renormalised. The original
procedural source remains fully reproducible through the generator.

## Coordinates and sampling

The atlas uses sixteen 128-square cells and four-pixel gutters, with the same
bottom-origin UV rectangle convention as the substation2 library. The GLB UVs
already select the material's cell; do not apply the rectangle transform a
second time. `materials.json` supplies each cell in `atlas.tiles` and each named
material in `materials`. Multiply albedo by linear GLB vertex colour. The
neutral cloth, paint and pale leaf cells support the model's vertex tints.

The prop atlas normal map is a conventional RGB tangent-space normal. Wall
normal maps contain **X and Y only**. A future shader must reconstruct positive Z:

```glsl
vec2 xy = texture(normalTexture, uv).rg * 2.0 - 1.0;
vec3 tangentNormal = vec3(xy, sqrt(max(0.0, 1.0 - dot(xy, xy))));
```

ORM channels are **R = occlusion, G = roughness, B = metallic**. Wall metallic
values are zero. All wall textures repeat in both axes and represent a 2 × 2 m
patch. The KTX2 orientation metadata is `rd` (right, down); orient it consistently
with the project's texture-loader path. The offline Blender reviewer decodes
the actual shipped BC mip bytes to RGB and reconstructs the normal Z channel.
It does not render higher-quality uncompressed source art.

The generator uses periodic fields and mirrors the final outer BC block's
selectors from the opposite edge. This makes opposite edge pixels identical
**after independent BC block decoding**, including normals and ORM. The change
occupies only the outer four-pixel strip. Mips of four pixels or smaller use
constant averages; normal maps use a neutral normal. Independent Node decoding checks all **396 wall mip images** for
matching opposite edges. The contact sheet displays each albedo as a 2 × 2
repeat so repetition and boundary continuity are visible.

## Writable board and Spanish text

`extkit_chalk` is a blank dark cell. A later integration can copy that cell and
draw a menu into it; the library does not bake a menu or modify game code.
There are **no strings drawn on the shipped texture planes** and no logos.
`drawnStrings` is therefore an empty array. The development preview captions
use Colombian Spanish, including **añil, pañete, baldosín, óxido, plástico,
oclusión** and **pintado**. The accents and enye have been checked visually.

## Independent inspection and what remains unverified

`extkit_texture_codec.mjs` independently parses the KTX2 header, descriptor,
metadata and mip index, inflates each mip using Node 22's `node:zlib`, verifies
block byte lengths, rejects overlapping/trailing data, decodes BC1/BC5 pixels
and measures seams. It uses neither Pillow nor the Python writer. The asset
tests exercise corrupt-input cases and their per-test mutations.

**Runtime integration is untested.** The current game does not load any extkit
asset. No claim is made that its existing `GLTFLoader`, `TextureLoader` or
`KTX2Loader` path can load these wall files without changes. A future integration
needs a ZLIB-to-native-BC upload path, BC1/sRGB and BC5 device support, positive-Z
normal reconstruction, and a deliberate fallback for devices without those
formats. See the
[Khronos KTX Developer Guide format support tables](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXDeveloperGuide.md)
for the relevant API feature checks. Neither native GPU upload nor device
compatibility was exercised in this offline library task; the preview is a CPU
decode used for asset review, not a runtime performance test.
