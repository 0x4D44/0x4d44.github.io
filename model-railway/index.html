A six-year embedded project · 2013 – 2018

Nine Arduinos, two radios, and a whole railway.

This is a hand-built control system for a model railway: a fleet of cooperating Arduino microcontrollers that drive points, read track-circuit occupancy, calculate signal aspects, and beam DCC packets to locomotives over a 2.4 GHz radio. Everything is written in C, single-developer (the commit log shows only “MD”), and shipped to bare-metal AVR chips with hand-tuned fuse bits and a VBScript build pipeline. Below: how it’s wired, how it talks, how it evolved.

§ 01 · the system

Two networks, one railway.

The system splits cleanly into two communication fabrics. A wired I²C bus, mastered by the Mainboard, runs the trackside infrastructure — points, track circuits, signals, the mimic-diagram control panel. A wireless NRF24L01 star, centred on the DCC Booster, carries train commands from handheld controllers. The Repeater bridges them so the wireless side can listen in on layout state. Hover any node.

§ 02b · the handset that never turns off

A 2 MHz cold boot, then nothing but leakage.

The handset is a study in milking battery life out of an AVR. It boots slowly on purpose so it can survive the voltage sag of a cold start, climbs to full speed only once a boost converter has the rail at 3.3 V, and never actually has an “off” switch. Idle handsets enter SLEEP_MODE_PWR_DOWN with the brown-out detector and every peripheral disabled — quiescent draw drops below the natural self-discharge of the NiMH cells, so leaving it on a shelf for a week costs less than the battery losing charge by sitting there. Hover any phase of the timeline.

Cold boot @ 2 MHz

fuse: CKDIV8BOD: 1.8 VF_CPU: 2 MHz

Fuses are set so the handset starts at 2 MHz — the boost converter isn’t on yet, so the chip is running directly off the raw battery (~2.6 V NiMH). That’s below the safe operating area for any speed above ~4 MHz. The brown-out detector is armed at 1.8 V; if the cells are too flat the chip never makes it out of reset.

The fuse triplet

low_fuses0x6F
high_fuses0xDF
extended0x06
  • CKDIV8 divides the 16 MHz crystal by 8 → chip boots at 2 MHz
  • SUT0 ext-crystal with 4.1 ms start-up (safe because BOD covers us)
  • SPIEN SPI programming enabled
  • BODLEVEL0 brown-out detector trips at 1.8 V
  • boot-reset vector disabled — we don’t need bootloader on every reset

The very first line of setup() reverses CKDIV8 in software: CLKPR = 0x80; CLKPR = 0x00; — unlock, then write divider = 1. By the time the OLED initialises, the boost converter is running and the CPU is at 16 MHz.

ATmega328P safe operating area

Drag the supply-voltage slider — the highlighted band shows the maximum clock the chip can be run at and stay inside spec. The dashed marks show the handset’s two operating points.

Vcc = 2.60 V max clock = ~5 MHz

The punchline. A NiMH cell self-discharges at roughly 1–2 % per week (low-discharge variants). In SLEEP_MODE_PWR_DOWN with BOD switched off in software (MCUCR = bit(BODS) | bit(BODSE); MCUCR = bit(BODS); — a strict four-clock-cycle window the code respects in-line) the ATmega328P draws well under a microamp. Multiplied out, the handset bleeds the battery slower than the battery bleeds itself. So the handset has no power switch. It just sleeps.

§ 02c · the level crossing

Four states, two LEDs, one yodalarm.

The level crossing is the smallest module and the most self-contained. A single Arduino Micro running the Mozzi audio-DSP library to synthesise the UK “yodalarm” alternating tones, four GPIO pins driving amber+red LEDs on PORTD, and a state machine with four states. Click START to run the whole sequence; click any state in the timeline to jump there.

t = 0.0 s
AMBER — 2.0 s
TRANSITION — 1.5 s
RED FLASH — sustained

Implementation

  • Master state machine — four states: IDLE → AMBER → TRANSITION → REDFLASH. All timing uses mozziMicros() not millis() so the audio engine stays sample-accurate.
  • Charlieplexed reds — the two red LEDs share lines and can’t physically be on simultaneously. To simulate “both on” the code flips between them every tick of updateControl() (128 Hz) — fast enough that your eye merges it. That’s the gR1R2 variable.
  • Direct port writes — pin updates use PORTD = 0xC0 + (PORTD & 0x0F) instead of digitalWrite. digitalWrite takes ~5 µs; the audio sample budget is ~61 µs.
  • Two-oscillator yodalarm — each output sample is aSin.next() + (bSin.next()>>4): dominant tone plus a 3×-harmonic mixed in 16× quieter (~–10 dB). The pair alternates between 800 Hz and 1 kHz every 250 ms.
  • 16,384 Hz audio rate — updateAudio() must return within 61 µs on every call. Comments in the source remind future-MD: “do any calculation we can in updateControl(), not here.”
  • Pinned to Arduino 1.0.5 — Mozzi’s pin-mapping macros didn’t survive the 1.0.6 toolchain bump. The source file opens with a triple-banged warning to that effect.

§ 03 · the DCC protocol

A 58 μs heartbeat, encoded in the rails.

Each locomotive carries a tiny decoder that listens for its address on the track. The Booster generates the DCC waveform with a Timer2 compare-match interrupt: a ‘1’ bit is one half-cycle of 58 μs; a ‘0’ bit is at least 100 μs. The whole signalling vocabulary — speed, lights, sound, emergency stop — is bit-banged on top of that. Click a bit type to see the waveform.

PREAMBLE≥14 ones lets every decoder sync to the bitstream.
ADDR BYTEIdentifies which locomotive should obey.
INSTRUCTIONSpeed, direction, function-group, or feature expansion.
ERROR BYTEXOR of address ⊕ instruction. Decoder must verify.
END BITA single ‘1’ closes the packet. 5 ms idle until next.

Why an IDLE between every packet? The NMRA standard requires ≥5 ms between consecutive packets to the same decoder. For three years that didn’t matter — until April 2018, when Hornby’s TTS sound decoder refused to work without it. V2.2 of the Booster added the IDLE separator. The April-2018 entries also added DCC functions F5–F20, then immediately fixed F13–F20 a few weeks later in V2.4.

§ 04 · signalling logic

Aspects propagate upstream.

The Mainboard recomputes signal aspects on every loop iteration. The trick is that each signal’s aspect depends on the next signal downstream — a green only stays green if the next signal isn’t red. So the code walks the layout backwards, calling sigPrevAspect() on every signal in reverse order. Eight signal types are supported: 2/3/4-aspect colour-light, semaphore home/distant, and feathers (route indicators). Toggle the inputs below — the signals update exactly as the firmware computes them.

§ 05 · evolution

Six years of “MD did this”.

Every source file opens with a dated changelog. Reconstructed below from those comments — every entry is signed by the same developer initials, “MD”. The shape is unmistakable: explosive activity in 2015, consolidation across 2016, a long quiet patch, then a single targeted return in spring 2018 to chase Hornby decoder bugs.

§ 06 · assessment

What it gets right — and where it shows its age.

Genuinely good

  • Header documentation is exceptional. Every file opens with architecture, build instructions, datasheet references, even the I²C-spec quote about reserved address ranges.
  • Hardware-aware design. Throwing points uses a relay (for direction) plus FET (for current) with explicit settle and recharge delays so the supply capacitor doesn’t brown out.
  • Defensive embedded patterns: watchdog timers, brown-out detection, setMasterRC() sticky-error semantics, I²C return-code mapping, sleep modes that respect handset state.
  • Memory-conscious. Strings live in flash via PROGMEM; lookup tables are byte-packed (bus, unit-index, position folded into a single byte) to fit in 2 KB of SRAM.
  • Protocol design is real engineering — Booster ↔ Handset packets are versioned (V1 ➜ V2), use NRF24 ack-payloads, retries, and pipe-per-handset addressing.
  • Single developer, one consistent voice. The ACL_, MD_, xi/xo prefix conventions are followed across every firmware. It’s easy to read.

Could be improved

  • The build system is a VBScript that automates Arduino 1.0.6 via SendKeys. It opens the IDE, sends Ctrl-W, Ctrl-O, the path, Enter, Ctrl-R. Reproducible only on one specific Windows PC at c:\apps\arduino-1.0.6.
  • Code lives twice. Each module ships a tmp/<Name>.c source and a copy at <Name>.ino — the build script copies one over the other every time. A symlink or build target would do the same job without divergence risk.
  • goto MD_EXIT_POINT everywhere. Used as a poor-man’s try/finally. Functional, but precludes RAII and makes refactoring tricky. C++ on AVR could replace it with scoped guards.
  • No version control history in-tree. Changelogs live as comment blocks at the top of each file. Useful, but no diff, no branches, no blame.
  • Pinned to Arduino 1.0.6 and old library forks (custom MDWire, MDLiquidCrystal_I2C). Updating the toolchain is a project unto itself; LevelCrossing specifically requires Arduino 1.0.5 because of Mozzi.
  • No tests. Reasonable for a one-person hobby project — but with eight firmwares talking over two networks, a packet-format unit test would have caught the V1/V2 LOCOINFO break-glass moment in advance.
  • Static layout maps. Point/TC/signal tables are hand-edited C arrays compiled into each binary. Bringing up a new layout means recompiling Mainboard. EEPROM-resident or external-config storage would be a natural next step.

§ 07 · curiosities

Things you only find by reading.

01

It starts up at 2 MHz, on purpose

The Handset’s fuses set CKDIV8. The chip boots at 2 MHz (safe at the 1.8 V brown-out floor), and the very first thing setup() does is reset the clock prescaler to 1 — back to 16 MHz, now that the supply is stable. Cold-boot timidity, deliberate.

02

The “FORCE” mode

By default routes only move points that aren’t already correct. Press FORCE on the panel and the Mainboard will re-throw every single point in the route anyway — useful when you’re not sure a Conrad motor actually moved (because there’s no position feedback at all).

03

Two I²C masters do not get along

For most of 2015 the ControlPanel was a master too — the comments call this “clashes on the bus”. Jan 2016 demoted it to slave and life got quieter. The header note still lectures future readers about this.

04

Hornby TTS broke things three years later

For three years the Booster sent DCC packets back-to-back. Then in April 2018 someone tried a Hornby TTS sound decoder and discovered it strictly requires the NMRA-mandated 5 ms gap. An IDLE packet between every command fixed it. Standards-compliance has a half-life.

05

The “A” chip trick

The PCA9554 only has 3 address bits → 8 devices. The PCA9554A variant uses a different fixed prefix — same chip, different address range. The Mainboard uses both flavours back-to-back: 0x20–0x27 for points, 0x38–0x3F for track circuits. Sixteen expanders on one bus.

06

Yodalarm by Mozzi

LevelCrossing uses the Mozzi audio-DSP library to synthesise the alternating 800 Hz / 660 Hz tones of a British level-crossing warning — at the cost of being pinned to Arduino IDE 1.0.5 specifically. Every other module is on 1.0.6.

07

BC1A: the elephant in the room

The booster H-bridge isn’t Arduino at all — it’s the MERG BC1A, a classic enthusiast-club design (PCB schematics ship in 00-Info/Merg BC1A/). The Arduino just drives its input pins. Re-use over re-invention.

08

The handset’s case has a part number

Every detail has a home. The handset enclosure spec is committed to the repo as a single-line file: Case.txt → Hammond 1553DYLBKBAT. (The “BAT” suffix means it’s the version with the battery compartment.)

One more thing: the ToDo.txt describes a “fully autonomous control” system — Inputs: track occupancy and signal aspects. Outputs: train control + route setting. A wireless interface from this Overall Control System back to the Booster. That’s what the TouchScreen on the Arduino DUE was the front-end for. The most recent code in the tree is the four-week April-2018 sprint fixing Hornby decoders, so the autonomous OCS didn’t quite happen — but the wires are all in place for someone to pick it up.
