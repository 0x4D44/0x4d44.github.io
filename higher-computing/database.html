The purser's office · Database Design and Development (DDD)

The squadron's records

DDD is one of the two options. You answer either Section 2 (Database, 25 marks) or Section 3 (Web, 25 marks) in the question paper, and either Task 2 (Database, 15 marks) or Task 3 (Web, 15 marks) in the assignment. In 2025, 66% of candidates chose Database. At Higher, every database has at least three linked tables.

⚓ Ship's log: our database

The squadron's database links cadets, their squadrons and the ships they are posted to for sea training. It has four tables: Squadron, Cadet, Ship and Posting. The same data is loaded into the live SQL playground in Chapter 6, so every query on this page can be run for real.

1 · Analysis: end-user and functional requirements DDD · identify

Before designing a database, find out what it must do. At Higher this is split into two lists:

End-user requirements

The tasks the users expect to carry out with the database, written from their point of view. "The training officer needs to see which cadets are posted to HMS Redstone."

Functional requirements

The processes the system must perform and the data it must hold: the tables, fields and queries. "A query to display firstname, surname and startDate from Cadet and Posting where shipCode = 'RED'."

⚠ From the 2025 course report

Written answers have "significantly improved" since candidates started phrasing functional requirements as "a query to …", for example "a query to display the average flying hours for each squadron". Use that pattern.

Whose requirement is it?

"I want to find every cadet whose surname begins with Mac."
A query to display firstname and surname from Cadet where surname LIKE "Mac%".
The Ship table must store shipCode, shipName, rate, guns, launched and homePort.
"The squadron leader needs to know how many cadets each squadron has."

2 · Entities, relationships and ERDs DDD · three or more entities, cardinality

These words have precise meanings, so learn them exactly:

Entity
A person, place, thing, event or concept that data is stored about: Cadet, Ship.
Entity occurrence
One specific instance of an entity: Cadet C104 Mhairi Campbell. One occurrence is one row of a table.
Attribute
A characteristic of an entity, such as surname or flyingHours. Each attribute becomes a field.
Primary key
An attribute (or attributes) that uniquely identifies one entity occurrence. Underlined on an ERD.
Foreign key
An attribute in one table that is the primary key of another table, so it links the two. Marked with an asterisk (*).
Relationship
A natural association between entities, named with a verb: a Squadron has Cadets.
Cardinality
How many occurrences of one entity relate to one occurrence of the other: one-to-one, one-to-many or many-to-many.

Entity-relationship diagram

An ERD shows each entity as a rectangle. Each relationship is a named line, and crow's feet mark the "many" end. Read every relationship in both directions.

An ERD can also show every entity's attributes, as ovals joined to the entity. The primary key is underlined and a foreign key has an asterisk (*). This is the full design of the squadron database:

One-to-one

In a one-to-one relationship, each occurrence of one entity is linked to exactly one occurrence of the other, and the other way round. Each squadron is commanded by one, and only one, commanding officer, and each commanding officer commands one, and only one, squadron.

Resolving a many-to-many relationship

A cadet can be posted to many ships, and a ship takes many cadets. That is many-to-many, and a relational database cannot implement it directly: there is no single place to put the foreign key. The fix is to add a new linking entity, here Posting, which turns one M:N relationship into two one-to-many relationships. Each Posting row records one cadet on one ship.

Entity-occurrence diagram: untangle the rigging

Each tall oval is an entity and each label is one occurrence. Lines link related occurrences. Press the buttons to change the view.

⚠ From the 2025 course report

"Only a few candidates" could explain how a new entity lets a many-to-many relationship exist. In the assignment, only some explained the need for the extra entity by referring to removing the many-to-many relationship. Say it in those words: "A Posting entity is needed because Cadet and Ship have a many-to-many relationship, which can't be implemented directly. Posting resolves it into two one-to-many relationships."

Compound keys

A compound key is a primary key made from two or more attributes, where each of those attributes is a primary key in its own right in another table. In Posting, the primary key is cadetID + shipCode. Neither on its own is unique (Mhairi has two postings, and Redstone has many cadets), but together they identify exactly one posting. Each part is also a foreign key.

Note the boundary this design sets: a cadet can be posted to each ship at most once. If repeat voyages were needed, startDate would have to join the key (cadetID + shipCode + startDate). Strictly, SQA would call that a composite key rather than a compound one, because startDate is not a primary key in its own right.

Attribute types at Higher

Text, Number, Date, Time and Boolean. A size is normally given only for text: the maximum number of characters.

The four validation checks

Presence check: the field can't be left empty. Restricted choice: the value must come from a fixed list. Field length: a set or maximum number of characters. Range: a number or date between limits.

A foreign key value must also match an existing primary key in the linked table (Cadet.squadronNo must be a real squadron). That is referential integrity, enforced by the relationship itself rather than by one of the four validation checks.

Why is cadetID text, not a number?

It contains a letter (C104), and you never do arithmetic on it. The same goes for phone numbers and postcodes: an identifier made of digits is usually still text, because a number type would drop leading zeros.

4 · Designing a query DDD · exemplify a design

Before writing SQL, plan the query in a design table. SQA uses these headings:

Design: "Show the firstname, surname and ship name of every cadet posted to a Portsmouth ship, in surname order."
Field(s) and calculation(s)firstname, surname, shipName
Table(s) and queryCadet, Posting, Ship
Search criteriahomePort = "Portsmouth"
Grouping(none)
Sort ordersurname ASC

Notice what is not written under search criteria: the joins (Cadet.cadetID = Posting.cadetID and Posting.shipCode = Ship.shipCode). In the design, the joins are implied by listing the tables. In the SQL they must appear in the WHERE clause. Forgetting one is an easy way to get far too many rows.

The calculations and grouping rows are used once you know aggregate functions and GROUP BY. There is a full example of them in the next chapter.

5 · SQL at Higher DDD · SELECT, UPDATE, INSERT, DELETE; wildcards, aggregates, alias, GROUP BY, ORDER BY

You already know SELECT, INSERT, UPDATE and DELETE from National 5, and equi-joins between two tables. Higher adds three or more tables, wildcards, aggregate functions, computed values with aliases and GROUP BY.

Joining three tables

List every table in FROM, then add one join condition in WHERE for every link between them. Three tables need two joins.

SELECT firstname, surname, shipName, startDate
FROM Cadet, Posting, Ship
WHERE Cadet.cadetID = Posting.cadetID
  AND Posting.shipCode = Ship.shipCode
  AND shipName = "HMS Redstone";

Wildcards with LIKE

The % wildcard matches any number of characters, including none. The _ wildcard matches exactly one character. Wildcards only work with LIKE, never with =.

CriteriaMatches
surname LIKE "Mac%"starts with Mac: MacLeod, MacDonald
surname LIKE "%son"ends in son: Paterson, Robertson, Henderson
surname LIKE "%ar%"contains "ar" anywhere: Stewart, Barr, Marshall
firstname LIKE "_a%"second letter a: Callum, Hamish, Zara
startDate LIKE "2026-07-%"any date in July 2026. Our dates are stored as YYYY-MM-DD so that they sort correctly. SQA examples use DD/MM/YYYY, where the same search would be LIKE "%/07/%".

Aggregate functions

COUNT, SUM, AVG, MIN and MAX each turn a set of rows into one value. SUM and AVG work only on numbers. COUNT(*) counts rows.

SELECT MIN(guns) AS [Fewest guns], MAX(guns) AS [Most guns], ROUND(AVG(guns), 1) AS [Average guns]
FROM Ship;
⚠ Two rules examiners test
  • An aggregate cannot go in a WHERE clause. WHERE flyingHours > AVG(flyingHours) is illegal. Instead, save one query that works out the average, then use its result in a second query (Mission 10 below).
  • Don't mix aggregate and non-aggregate fields without GROUP BY. SELECT shipName, MAX(guns) FROM Ship; is wrong at Higher, even though some database programs (including the SQLite engine in our playground) let it run.

Computed values and aliases

A computed value is calculated when the query runs and is never stored in the database. An alias (AS) gives a column a readable heading that lasts only for that query.

SELECT shipName, guns, guns / 2 AS [Guns per broadside]
FROM Ship
ORDER BY guns DESC;

GROUP BY

GROUP BY gathers rows that share a value into groups, and the aggregate then runs once per group. This is how you get "for each …" answers. When both are used, GROUP BY always comes before ORDER BY.

Using the result of one query in another

Because an aggregate can't go in a WHERE clause, a question like "which cadets have more hours than the average?" takes two queries. Query 1 works out the average and is saved. Query 2 then uses the saved query as if it were a table. In Microsoft Access you simply save Query 1 under a name. In SQL the same thing is written CREATE VIEW:

CREATE VIEW [Find Average] AS
SELECT AVG(flyingHours) AS [Average Hours] FROM Cadet;

SELECT firstname, surname, flyingHours
FROM Cadet, [Find Average]
WHERE flyingHours > [Average Hours];

You will not be asked to write CREATE VIEW in the exam, but you may be asked to design or explain the two-query approach.

UPDATE, INSERT and DELETE

-- 1805 Squadron's Cadets with at least 10 flying hours are promoted to Cpl
-- and credited with 2 hours for the promotion flight
UPDATE Cadet
SET rank = "Cpl", flyingHours = flyingHours + 2
WHERE squadronNo = 1805 AND flyingHours >= 10 AND rank = "Cadet";

INSERT INTO Posting (cadetID, shipCode, startDate, nights, role, reportTime)
VALUES ("C109", "OBS", "2026-09-12", 4, "Rigging", "07:45");

DELETE FROM Posting
WHERE startDate < "2026-07-01";
⚠ From the 2025 course report

Some candidates found "the syntax to increment a field value challenging". The pattern is SET field = field + amount. Without a WHERE clause, an UPDATE or DELETE changes every row in the table.

SQLite vs the exam

Our engine is SQLite. It accepts SQA-style [square bracket] aliases and double-quoted strings, and it treats LIKE as case-insensitive, as Microsoft Access does. Differences: = is case-sensitive on text, and SQLite won't stop you mixing aggregate and non-aggregate fields without GROUP BY. The playground warns you when you do that.

7 · Testing and evaluating SQL DDD · testing; fitness for purpose, accuracy of output

Testing that SQL works correctly

  1. Work out the expected output by hand from the data before running the query.
  2. Run the query and compare the actual output with the expected output: the same rows, the same columns and the right order.
  3. Test the criteria on their boundaries. If the requirement says "at least 20 hours", is a cadet with exactly 20 included? Then you need >=, not >.
  4. Check that an UPDATE or DELETE affected only the intended rows. Run a SELECT with the same WHERE clause first.
⚠ From the 2025 assignment

Several candidates used > where the task said "at least". With the given data it produced the right output, so it looked correct, but it would fail if the data changed. "Candidates should ensure that their code will work for all values, not just the given set of data."

Evaluating a database solution

Fitness for purpose

Does the solution meet every end-user and functional requirement? If a requirement can't be met, say which one and what data or structure is missing: "The profit can't be calculated because the Ship table has no cost field. A cost attribute would need to be added to Ship."

Accuracy of output

Are the results correct and complete? Right rows, right calculated values, right order and readable headings. A query missing a join produces far too many rows (every cadet paired with every ship), and that is inaccurate.

⚠ Be specific

In 2025, answers like "missing join", "missing GROUP BY" or "missing table" were "not specific enough for marks". Say which join (Cadet.cadetID = Posting.cadetID), which field to group by, and which table to add.
