The gun deck · Software Design and Development (SDD)

Building programs that don't sink

SDD is the biggest part of Higher Computing Science. It fills most of Section 1 of the exam (about 41–45 of its 55 marks) and the whole of Task 1 of the assignment (25 marks). Every chapter here follows the order a real project follows: analyse, design, implement, test, evaluate.

⚓ Ship's log: why a gun deck?

On a ship of the line, a broadside only works if every gun crew follows the same drill in the same order: sponge, load, ram, run out, aim, fire. A program is the same. It is a drill written down so precisely that a machine can follow it. Our examples all come from 1805 (Blockhaven) Squadron, a crew of Air Cadets posted aboard HMS Redstone, a 104-gun first-rate built entirely out of blocks.

Code on this page

Exam questions show code in SQA reference language (SET … TO …, END IF and so on). You may answer in any language, and you are marked on understanding, not syntax. Each example has two tabs: Python, the language most Scottish schools use, and Reference, which is how the question paper will show it.

1 · Development methodologies SDD · describe & compare

A development methodology is the overall plan a team follows to build software. At Higher you must describe and compare two of them.

The iterative development process

You met this at National 5. A project moves through fixed phases in order:

analysis → design → implementation → testing → documentation → evaluation

It is called iterative because when a later phase finds a problem, the team goes back to an earlier phase and repeats it. SQA's course notes say it is "often called the waterfall model". It is a predictive method: the team tries to plan the whole project in detail at the start.

Agile methodologies

Agile development splits the project into short cycles called sprints, often one to four weeks long. In every sprint a small cross-functional team plans, designs, codes and tests one working piece of the product, then shows it to the client. The client's feedback shapes the next sprint. Agile is adaptive: it expects requirements to change and is built to cope with that.

Two shipyards build the same frigate

Press Launch. Halfway through, the Admiralty asks for an extra gun deck. Watch how each yard copes with the change.

How they compare

SQA compares the two methods under six headings. Learn these headings: they are exactly what "compare" questions ask about.

HeadingIterative (waterfall)Agile
Client interactionHeavily involved at the start (analysis) and at the end (evaluation), with little contact in between.Involved throughout. Gives constant feedback on prototypes, and that feedback is acted on quickly.
TeamworkSeparate teams of analysts, programmers, testers and documenters work mostly alone, handing work on at each phase.Small cross-functional teams work closely together. Fast face-to-face communication keeps the project moving.
DocumentationA detailed specification is written at the start. A lot of time goes on design documents, commentary and test plans.Documentation is kept to a minimum. Anything written must help the project move forward.
Measuring progressProgress is measured against a strict plan and the deadlines set at the start.Progress is measured by the time taken to produce prototypes or working components at the end of each sprint. Agile focuses on delivering software as quickly as possible.
Predictive vs adaptivePredictive: it plans the future in detail, so a mistake in the early analysis is hard to recover from.Adaptive: it changes quickly when the project's needs change. An adaptive team has difficulty saying exactly what it will do next week, but can report which features it plans for next month.
TestingA separate testing phase happens after implementation is finished.There is no separate testing phase. Testing happens during every sprint, alongside the coding.
⚠ Exam lookout

A "compare" question needs both sides of the same heading. For example: "In agile the client gives feedback throughout development, whereas in iterative development the client is mainly involved at the start and the end." Describing agile on its own scores nothing for the comparison. The 2025 course report notes that many candidates could explain why agile suited a given client. To do that, link the client's situation (changing needs, wanting to see progress) to a feature of agile.

3 · Design: structure diagrams, pseudocode and wireframes SDD · read, exemplify, implement

Before any code is written, the solution is planned. At Higher you must be able to read designs written as structure diagrams or pseudocode. You must also produce a design that shows three things:

  • Top level design: the main steps of the program, which usually become its sub-programs.
  • Data flow: which data goes IN to each step and which comes OUT. This becomes the parameters.
  • Refinements: each main step broken down into smaller, more detailed steps.

⚠ Exam lookout: data flow

Only pass in the data a step actually needs, and only pass out what it creates or changes. In 2025 some candidates added unnecessary parameters to their data flow, and that makes the code less efficient. Ask yourself two questions for every step: "Does this step read it?" (IN) and "Does this step produce it?" (OUT).

User-interface design: wireframes

A wireframe is a simple sketch of a screen. It shows where each input and output will appear, with no colours or real content. For a text-based program, the wireframe shows the prompts the user will see and where the results will be displayed.

4 · Data types and structures SDD · parallel arrays, records, arrays of records

From National 5 you know the basic data types: character, string, integer, real and Boolean. You also know the 1D array, a numbered list of values that all have the same type. Higher adds three ways of organising related data.

Parallel 1D arrays

Each attribute gets its own array. The same index in every array refers to the same cadet. names[3], flights[3] and hours[3] all describe Mhairi.

Records

A record groups several values of different types under one name. Each value is a field. A record is like a Minecraft chest that holds a sword, some bread and a map together. One chest, one cadet.

Arrays of records

An array of records is a numbered row of chests. cadets[3].hours means "open chest 3 and take out the hours field". Each cadet's data travels together, so it can't drift out of line.

The crafting table

Drag the slider (or use the arrow keys) to pick an index. Then press Craft to turn three parallel arrays into one array of records.

from dataclasses import dataclass

# --- parallel 1D arrays: one array per attribute ---
names   = ["Ross", "Ailsa", "Callum", "Mhairi"]
flights = ["A",    "B",     "A",      "C"]
hours   = [12,     31,      7,        31]
print(names[1], hours[1])          # Ailsa 31

# --- a record type: one "chest" per cadet ---
@dataclass
class Cadet:
    name: str
    flight: str
    hours: int

# --- an array of records ---
cadets = [Cadet("", "", 0) for _ in range(8)]   # 8 empty records
cadets[0] = Cadet("Ross", "A", 12)
cadets[0].hours = cadets[0].hours + 2             # Ross flies 2 more hours
print(cadets[0].name, cadets[0].hours)           # Ross 14
DECLARE names INITIALLY ["Ross", "Ailsa", "Callum", "Mhairi"]
DECLARE flights INITIALLY ["A", "B", "A", "C"]
DECLARE hours INITIALLY [12, 31, 7, 31]
SEND names[1] & " " & hours[1] TO DISPLAY

RECORD Cadet IS {STRING name, STRING flight, INTEGER hours}

DECLARE cadets AS ARRAY OF Cadet INITIALLY [ Cadet("", "", 0) ] * 8
SET cadets[0] TO Cadet("Ross", "A", 12)
SET cadets[0].hours TO cadets[0].hours + 2
SEND cadets[0].name & " " & cadets[0].hours TO DISPLAY

Reading the Python: @dataclass is the usual way to write a record in Python: it lists the fields and their types, and Python builds Cadet("Ross", "A", 12) for you. [Cadet("", "", 0) for _ in range(8)] is a short way to make a list of 8 separate empty records; it does the same job as a fixed loop that appends one empty record 8 times. You only need to read these, not memorise them.

Why choose parallel arrays?

They are simple to declare, and each attribute can be processed on its own, for example adding up all the hours. Their weakness is that the arrays must be kept in step by hand. Sort one and forget the others, and Ross gets Mhairi's flying hours.

Why choose an array of records?

All the data about one item is stored together. That is easier to read, harder to get out of line, and one record can be passed to a sub-program as a single parameter. SQA usually rewards an array of records when a question asks for the "most suitable data structure" for mixed data.

5 · Sub-programs, parameters and scope SDD · functions, procedures, parameter passing, local/global

A sub-program (or subroutine) is a named block of code that does one job. It is defined by its name and its arguments: the data that goes in and comes out. There are two kinds:

Procedure

Carries out a task, such as displaying a report or writing a file. It does not return a value to the code that called it.

display_results(cadets, top_pos, count)

Function

Carries out a task and returns a single value, so it is used inside an expression or assignment.

top_pos = find_max_position(cadets)

Formal and actual parameters

The variables listed in a sub-program's definition are its formal parameters. The values or variables supplied when the sub-program is called are the actual parameters. When the call happens, each actual parameter is matched by position to a formal parameter.

def count_flight(cadets, flight):        # formal parameters: cadets, flight
    count = 0                              # local variable
    for cadet in cadets:
        if cadet.flight == flight:
            count = count + 1
    return count

b_total = count_flight(squadron, "B")      # actual parameters: squadron, "B"
FUNCTION countFlight(ARRAY OF Cadet cadets, STRING flight) RETURNS INTEGER
    DECLARE count INITIALLY 0
    FOR EACH cadet FROM cadets DO
        IF cadet.flight = flight THEN
            SET count TO count + 1
        END IF
    END FOR EACH
    RETURN count
END FUNCTION

SET bTotal TO countFlight(squadron, "B")

Scope: local and global variables

The scope of a variable is the part of the program where it can be used.

  • A local variable is declared inside a sub-program. It exists only while that sub-program runs and cannot be seen from outside. count above is local.
  • A global variable is declared in the main program, outside every sub-program, and can be accessed from anywhere.

Good practice is to use local variables and parameter passing, and to avoid globals. Each sub-program then has clear inputs and outputs. It can be tested on its own and reused. Two sub-programs can each have a local variable called count without interfering with each other. A global, by contrast, can be changed by any line of the program, which makes errors very hard to trace.

Where these turn up

  • Substring: make a username from the first three letters of a surname, or take the area code from a postcode.
  • ord/chr: simple ciphers, such as shifting every letter along the alphabet, or checking that a character lies between "A" and "Z".
  • int: turn a calculated average into a whole number, or turn 3.7 hours into 3 complete hours.
  • Modulus: test for even numbers (n % 2 == 0), find what is left over (130 shot shared among 8 guns leaves 130 % 8 = 2 spare), or make values wrap round, like a clock.
# A Caesar shift of 3, like a ship's cipher: A→D, Z→C
def shift_letter(ch):
    position = ord(ch) - ord("A")          # 0..25
    new_position = (position + 3) % 26     # modulus wraps Z round to C
    return chr(new_position + ord("A"))

print(shift_letter("Z"))   # C
FUNCTION shiftLetter(CHARACTER ch) RETURNS CHARACTER
    DECLARE position INITIALLY ord(ch) - ord("A")
    DECLARE newPosition INITIALLY (position + 3) MOD 26
    RETURN chr(newPosition + ord("A"))
END FUNCTION

7 · File handling SDD · sequential CSV and txt: open, create, read, write, close

A sequential file is read or written in order, from the first line to the last, like a ship's log read page by page. Higher uses two kinds:

  • .txt: plain text, often one value per line.
  • .csv (comma-separated values): each line is one record, and the fields are separated by commas. For example Ailsa,B,31.

There are five operations to know:

OperationWhat it doesPython
OpenConnect to an existing file so it can be read (or added to).f = open("cadets.csv", "r")
CreateMake a new, empty file. In Python, opening with "w" creates the file, or wipes it if it already exists.f = open("report.txt", "w")
ReadGet the next line from the file.line = f.readline() or for line in f:
WriteSend text to the file.f.write("Ross,A,12\n")
CloseFinish with the file. Closing saves any buffered data and frees the file for other programs.f.close()

Reading the log, line by line

Step through to see a file pointer move down cadets.csv. Each line is split at the commas and stored in the next record.

def get_cadet_data():
    cadets = []
    file = open("cadets.csv", "r")
    for line in file:
        fields = line.strip().split(",")      # "Ailsa,B,31\n" → ["Ailsa","B","31"]
        cadets.append(Cadet(fields[0], fields[1], int(fields[2])))
    file.close()
    return cadets

def write_report(cadets, top_pos):
    file = open("report.txt", "w")            # creates the file
    file.write("Top cadet: " + cadets[top_pos].name + "\n")
    file.close()

Remember

Every value read from a file arrives as a string. Convert numbers with int() or float() before doing arithmetic. Otherwise "31" + "7" gives "317".

8 · Standard algorithms SDD · linear search, find min/max, count occurrences

Three algorithms appear in nearly every Higher paper and assignment. You must be able to write each one from memory, using a 1D array or an array of records.

Linear search

Check each item in turn until the target is found, or until the end of the array is reached. The efficient version uses a conditional loop that stops as soon as the item is found. A fixed loop would carry on checking pointlessly.

def linear_search(cadets, target):
    found = False
    position = -1
    index = 0
    while index < len(cadets) and not found:
        if cadets[index].name == target:
            found = True
            position = index
        index = index + 1
    return position                 # -1 means "not found"
FUNCTION linearSearch(ARRAY OF Cadet cadets, STRING target) RETURNS INTEGER
    DECLARE found INITIALLY false
    DECLARE position INITIALLY -1
    DECLARE index INITIALLY 0
    WHILE index < length(cadets) AND found = false DO
        IF cadets[index].name = target THEN
            SET found TO true
            SET position TO index
        END IF
        SET index TO index + 1
    END WHILE
    RETURN position
END FUNCTION

Find maximum and minimum

Assume the first item is the biggest so far. Then compare every other item with it, replacing it whenever a bigger one turns up. For the minimum, flip the > to <. Exam questions often ask for the position of the maximum. Store the index, and you can then get every field of the winning record.

def find_max_position(cadets):
    max_pos = 0
    for index in range(1, len(cadets)):
        if cadets[index].hours > cadets[max_pos].hours:
            max_pos = index
    return max_pos
FUNCTION findMaxPosition(ARRAY OF Cadet cadets) RETURNS INTEGER
    DECLARE maxPos INITIALLY 0
    FOR index FROM 1 TO length(cadets) - 1 DO
        IF cadets[index].hours > cadets[maxPos].hours THEN
            SET maxPos TO index
        END IF
    END FOR
    RETURN maxPos
END FUNCTION

Exam questions often use parallel arrays instead of records. The algorithm is identical: only the way you reach the data changes. cadets[index].hours becomes hours[index], and the winning name is names[maxPos].

DECLARE maxPos INITIALLY 0
FOR index FROM 1 TO 7 DO

    END IF
END FOR
SEND names[maxPos] & " flew the most: " & hours[maxPos] & " hours" TO DISPLAY

⚠ A common slip

Never start the maximum at 0. If every value is negative (temperatures in the Arctic, say), the maximum will wrongly come out as 0. Starting the minimum at 0 goes wrong for positive data in the same way. Always start with the first element of the array.

Count occurrences

Set a counter to zero. Go through every item and add one each time an item matches. A fixed loop is correct here, because every item must be checked.

def count_flight(cadets, flight):
    count = 0
    for index in range(len(cadets)):
        if cadets[index].flight == flight:
            count = count + 1
    return count
FUNCTION countFlight(ARRAY OF Cadet cadets, STRING flight) RETURNS INTEGER
    DECLARE count INITIALLY 0
    FOR index FROM 0 TO length(cadets) - 1 DO
        IF cadets[index].flight = flight THEN
            SET count TO count + 1
        END IF
    END FOR
    RETURN count
END FUNCTION

9 · Testing and debugging SDD · test plans, error types, debugging techniques

A comprehensive final test plan

A test plan lists the tests you will run, the data you will use and the result you expect, all written before testing starts. It is comprehensive when it shows that every functional requirement has been met, using a full range of test data:

  • Normal: sensible data that should be accepted. Flying hours of 12.
  • Extreme: data on the boundaries of what is allowed. 0 and 100 if the valid range is 0–100.
  • Exceptional: data that should be rejected. −5, 101 or "twelve".

✈ Flight log: the pre-flight checklist

Before every flight, an Air Cadet and their pilot work through a written checklist: every item planned in advance, each with the result it should give ("fuel: full", "flaps: move freely"), ticked off one by one. A test plan is the same idea for software: planned before testing begins, with an expected result for every test.

Three kinds of error

Syntax error

The code breaks the grammar of the language, so it cannot be translated at all. Examples: a missing bracket, a misspelt keyword like whlie, or a missing colon in Python.

Execution (run-time) error

The code translates, but crashes while running because it asks for something impossible. Examples: dividing by zero, using an array index that doesn't exist, or opening a file that isn't there.

Logic error

The program runs to the end, but gives the wrong answer. Examples: < instead of >, starting a loop at 1 instead of 0, or AND instead of OR.

10 · Evaluation SDD · fitness for purpose, efficiency, usability, maintainability, robustness

Evaluation is an objective review of the finished software. Is it any good, and how do you know? You judge it under five headings.
