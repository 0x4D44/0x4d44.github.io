The Locked Room

How to run code you do not fully trust on a Linux machine, and what each control stops. It runs from a single system call (prctl) to a Firecracker microVM, and it states the limits of each control.

If you read one thing

Run untrusted code with several locks, because each lock stops different attacks. Use a non-root user with no capabilities, no_new_privs, a seccomp allowlist (a list of the syscalls you permit), Landlock for files, and cgroup limits for memory and process count. If the code is hostile, put it behind a stronger boundary: gVisor or a microVM such as Firecracker. For untrusted code, set JAIL_REQUIRE_ABI=6 in the launcher so it refuses old kernels. Section 16 shows no_new_privs, Landlock, rlimits and a no-fork seccomp filter in one small program (it does not drop the user or capabilities). Section 18 lets you score your own setup.

01 · Threat modelThe shared-kernel problem

A normal Linux container behaves differently from a small virtual machine. It is an ordinary process, or a tree of processes, that the kernel has been told to show a limited view of the system. Namespaces give it a private view of mounts, PIDs (process IDs) and the network, and cgroups cap how much it may use. Capabilities and an LSM (Linux Security Module) narrow what it may do. But every one of its system calls still lands in the same kernel that runs the host and every other tenant. A single memory-corruption bug in any reachable kernel path turns "root in the container" into "root on the machine".

That view splits the field into four goals. You make fewer kernel paths reachable and constrain each reachable path more tightly. You also limit the damage if the process is subverted anyway. When the stakes justify it, you put a different kernel or a hypervisor (software that runs virtual machines) between the workload and the host.

LanguageMemory-safe code and a small dependency tree: fewer bugs to exploit in the first place (section 14).
Rlimits / cgroupsBound CPU, memory, processes, I/O, so a bug cannot become a denial of service.
seccompAllowlist of syscalls (and some arguments): shrinks the kernel attack surface the process can touch.
Landlock / LSMWhich files, sockets and objects the allowed syscalls may act on.

NamespacesWhat the process can see: its own mounts, PIDs, network, users. Not a security boundary alone.
Host kernelShared. Every layer above exists because of this one. A kernel bug can bypass all of them.
HypervisorOptional: a guest kernel (Kata, Firecracker) or a user-space kernel (gVisor) so the host kernel is no longer directly exposed.

Design principles that recur

  • Default deny: an allowlist fails closed when a new syscall, flag or kernel feature appears; a denylist fails open.
  • Least privilege, applied late: do the privileged setup (open sockets, read config, create cgroups), then restrict, then run untrusted work. Restrictions only tighten: seccomp filters and Landlock rulesets can only be added to, never removed.
  • Defence in depth, with independent failure modes: a seccomp filter and a Landlock ruleset fail for different reasons, so if one has a hole, the other may still hold.
  • Remove code as well as restricting it: a syscall that is compiled out cannot be reached by a filter bug; a dependency never added cannot be compromised.
  • Assume the sandbox is the last line of defence. It limits the damage from a bug you did not find. You still have to fix the bugs you know about.
What this page does not cover

This page leaves out network-level controls (firewalls, service meshes), identity and secrets management, and Windows or macOS sandboxing, and it does not replace patching. Several of the worst container escapes were plain kernel or runtime bugs that no policy would have blocked (section 17).

03 · Syscall filteringseccomp: the syscall allowlist

Reference: seccomp(2) and the kernel's Seccomp BPF documentation

Every interaction between a process and the kernel goes through a system call. The seccomp ("secure computing") feature lets a process install a filter that the kernel runs on every syscall entry, before the syscall does anything. The filter is a small classic BPF program (BPF stands for Berkeley Packet Filter). It is not eBPF (extended BPF): it has no maps, no helpers, no loops and no pointers, and it inspects a fixed record to return a verdict.

What the filter sees

struct seccomp_data {
    int   nr;                      // syscall number
    __u32 arch;                    // AUDIT_ARCH_* (which ABI)
    __u64 instruction_pointer;
    __u64 args[6];                 // raw register values, never dereferenced
};

The filter sees only those fields, so it can say "openat is allowed" or "socket's first argument must be AF_UNIX". It cannot say "openat may open only under /data". The path is a pointer into user memory, which the filter cannot read, and reading it would be racy anyway (see below). That job belongs to Landlock or an LSM.

Verdicts and precedence

Filters stack, children inherit them, and they survive execve, so if several filters are installed, all of them run and the most restrictive result wins:

2KILL_THREADKills the calling thread only. A surviving process in a half-dead state is rarely what you want.

5USER_NOTIFSuspends the caller and asks a supervisor process (5.0+). Flexible: runtimes use it to let a supervisor perform mknod or mount on a workload's behalf. See the warning below.

Two filters are installed, one by the container runtime and one by the application. Pick what each returns for the same syscall and see what the kernel does.

The five ways seccomp policies go wrong

  1. Forgetting the architecture: a filter that checks syscall numbers without checking arch can be bypassed through another ABI: 32-bit int 0x80 on x86-64 uses a different numbering. On x86-64 the x32 ABI sets bit 30 (0x40000000) in the number. Always check arch first and kill on a mismatch; reject numbers with the x32 bit. libseccomp does this for you.
  2. Denylisting: blocking "dangerous" calls fails open the day Linux adds a new one (io_uring_*, clone3, pidfd_*, landlock_*, mount_setattr were all new within a few years), so start from allow-nothing.
  3. Trying to judge pointers: suppose a USER_NOTIF or ptrace supervisor reads a path from the tracee's memory and then lets the call proceed. That has a time-of-check/time-of-use (TOCTOU) race, because another thread can rewrite the buffer between the check and the use. The kernel documentation is explicit that SECCOMP_USER_NOTIF_FLAG_CONTINUE must not be used to implement a security policy.
  4. clone3 and friends. clone3 passes its flags in a struct in memory, so a filter cannot see them. The usual fix is to return ENOSYS, which makes glibc fall back to clone, whose flags are in a register and can be filtered, and container runtimes do exactly this.
  5. Operations that are not syscalls. io_uring lets a process queue reads, writes, connects and more through shared rings. The kernel runs these operations without going through the syscall path, so a syscall filter never sees them. Block io_uring_setup/enter/register, or set the sysctl kernel.io_uring_disabled (6.6+: 0 allow, 1 only a configured group, 2 disable for all). Google has reported that most of the kernel exploits submitted to its kCTF bug-bounty program in 2022 targeted io_uring. It restricted the interface on several of its own platforms.

Building a profile you can trust

  1. Record, then restrict: run the workload under realistic load. Put the filter in LOG mode (SECCOMP_RET_LOG writes to the audit log), or use strace -f -c, or count syscalls with bpftrace: 
    bpftrace -e 'tracepoint:raw_syscalls:sys_enter /comm == "myapp"/ { @[args->id] = count(); }'
  2. Cover the unhappy paths: startup, shutdown, error handling, log rotation, DNS failures and signal handling all call syscalls that the happy path never does. A profile built from one test run often causes production SIGSYS crashes.
  3. Prefer ERRNO in production for optional calls, KILL_PROCESS for never-legitimate ones. Libraries probe for features and handle ENOSYS/EPERM gracefully; they do not handle being killed.
  4. Re-record on every runtime change: a new libc, a new Go or Rust release, or a new library can start using different syscalls (clone3, faccessat2, statx, rseq).
  5. Go and the JVM need extra care, because Go starts many threads and uses clone with several flags, sigaltstack, futex, epoll and madvise. A filter that forbids clone therefore breaks it. Record the profile with a real build and allow thread-style clone only. The JVM also maps writable-and-executable memory for its JIT, so it cannot run with MemoryDenyWriteExecute. It reads /proc/self and /sys/fs/cgroup at start-up, so test both under load and after launch.
  6. Tooling: The libseccomp library is written in C and has Python, Go and Rust bindings. The Rust seccompiler crate was written for Firecracker. Systemd ships named sets of syscalls, which you can list with systemd-analyze syscall-filter. In Kubernetes, the Security Profiles Operator can record profiles for you.
seccomp is not "eBPF seccomp"

seccomp uses classic BPF, a deliberately tiny instruction set the kernel can verify trivially. Extending seccomp to eBPF has been proposed several times but has not been merged. Everything in section 10 about eBPF's verifier and JIT does not apply to seccomp filters.

04 · Filesystem and network fencingLandlock: the filesystem fence

Reference: Landlock userspace API

seccomp decides which calls you may make, and Landlock decides what they may touch. It is a Linux Security Module with one unusual property: any unprivileged process can restrict itself. It needs no root, no admin-written policy and no setuid helper. An application can say "from now on I may read /usr and write only to /var/app/scratch". The kernel then enforces that on it and all its descendants, forever.

The three syscalls

  1. landlock_create_ruleset(): declare which access rights this ruleset handles. Anything handled is denied unless a rule allows it; anything not handled is left alone.
  2. landlock_add_rule(): allow specific rights beneath a directory (an O_PATH file descriptor), or on a single file, or (ABI 4+) on a TCP port.
  3. landlock_restrict_self(): enforce the ruleset, which requires no_new_privs (or CAP_SYS_ADMIN) and cannot be undone.

The call sequence is in the complete example in section 16, which was compiled and run for this page.

Access rights by ABI version

Landlock grows by ABI version, and a program asks the kernel which version it supports. The program then masks out the rights the kernel does not know about ("best-effort" mode), so old kernels give weaker sandboxing rather than failing.

Rules that surprise people

  • Within one ruleset, rules union: an access is allowed if a rule on the file or any ancestor directory grants that right.
  • Across stacked rulesets, rules intersect: each restrict_self adds a layer (up to 16); an access must be allowed by every layer. A child can narrow the policy it inherited but never widen it.
  • Not retroactive: file descriptors opened before restrict_self keep working. That is a feature (open what you need, then lock down) and a hazard (do not leak a directory fd into the sandbox).
  • Mount topology is frozen: a Landlocked process cannot mount, unmount or pivot_root.
  • Gaps: the original ABIs (application binary interface versions) have no right for chmod, chown, stat or utime-style metadata operations. The network side covers TCP only, not UDP or raw sockets. Landlock does not mediate connecting to a pathname Unix socket at all on ABIs 1 to 8, whatever filesystem rules you wrote. For example, connect() to /var/run/docker.sock or a D-Bus or systemd socket succeeds if the file's own permissions allow it. ABI 6 scoping covers only abstract sockets, and a proposed ABI 9 right (see the table) targets this. Until then, deny socket(AF_UNIX) in seccomp, or run in a mount namespace where such sockets do not exist. Pair Landlock with seccomp to cover what it does not.
  • It must be on: check cat /sys/kernel/security/lsm for landlock (kernel built with CONFIG_SECURITY_LANDLOCK, and listed in lsm=), so probe the ABI at runtime instead of assuming.

A time limit

No rlimit bounds wall-clock time, and RLIMIT_CPU counts CPU seconds only, so a process that sleeps or waits on a pipe never trips it. Run a watchdog outside the sandbox: start the job in its own cgroup, set a timer, and when it fires write 1 to cgroup.kill. With systemd, set RuntimeMaxSec= on the unit. Without either, timeout --kill-after=5 30 ./job is the minimum, but it signals only the command it started. On GNU coreutils 9.4 we saw background children keep running after the timeout fired, and a child that starts a new session will always escape it. To stop everything, write 1 to cgroup.kill or set RuntimeMaxSec on a systemd unit.

What limits do not cover

No cgroup controller shapes network bandwidth, so use tc or eBPF-based tools. Disk space needs filesystem quotas (XFS project quotas, a size-limited tmpfs) and inode limits. Shared kernel resources such as the dentry cache or kernel keyrings can still be a cross-tenant side channel. Memory limits also do not stop a cache- or timing-based side channel.

07 · PrivilegePrivileges, capabilities and namespaces

References: capabilities(7) · kernel sysctls · Docker security

Capabilities: slicing up root

Since Linux 2.2, "root" is a bundle of about forty separate capabilities. A hardened workload runs as an unprivileged UID (user ID) and has an empty capability set (--cap-drop=ALL). It adds back only what it can justify, which is commonly nothing, or NET_BIND_SERVICE to bind port 80. Be wary of:

  • CAP_SYS_ADMIN: the broadest capability, which covers mount, namespaces, many ioctls, BPF and cgroup manipulation, so granting it to a container largely voids the sandbox.
  • CAP_NET_RAW: raw sockets and packet crafting, which Docker grants by default; most services do not need it (and it has enabled ARP and DNS spoofing between containers on a bridge).
  • CAP_SYS_PTRACE, CAP_DAC_READ_SEARCH, CAP_SYS_MODULE, CAP_SYS_RAWIO, CAP_BPF/CAP_PERFMON: direct routes to other processes' memory, arbitrary files or kernel code.

Docker's default set has 14 capabilities: CHOWN, DAC_OVERRIDE, FSETID, FOWNER, MKNOD, NET_RAW, SETGID, SETUID, SETFCAP, SETPCAP, NET_BIND_SERVICE, SYS_CHROOT, KILL, AUDIT_WRITE. Docker chose this list for compatibility, so a hardened service can usually drop more.

no_new_privs: privileges can only shrink

prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) promises that execve will never grant more privilege than the caller already has. The kernel ignores setuid and setgid bits, file capabilities and automatic LSM domain transitions. It is inherited and cannot be unset, and it also lets an unprivileged process install a seccomp filter or a Landlock ruleset safely. Without it, the sandbox could be used to trick a setuid program, because the filter might make a privileged binary misbehave. Containers set it with --security-opt no-new-privileges / allowPrivilegeEscalation: false.

Other one-way switches worth knowing

  • PR_SET_MDWE (6.3+): refuse to create memory that is both writable and executable, or to make writable memory executable later. It is the process-level equivalent of systemd's MemoryDenyWriteExecute, and it breaks JITs.
  • securebits (PR_SET_SECUREBITS with SECBIT_NOROOT and the _LOCKED variants): stop UID 0 from automatically regaining capabilities on exec.
  • hidepid=2 on /proc: hide other users' processes from ps and /proc (a PID namespace does this more thoroughly).
  • memfd_create with MFD_NOEXEC_SEAL (6.3+): memory files that can never be executed, closing a route that fileless malware uses.

User namespaces: useful, and a larger attack surface

A user namespace maps UID 0 inside to an unprivileged UID outside. It is how rootless containers work: root in the container has no authority over the host. But it also lets any unprivileged process obtain a full capability set inside its own namespace. That exposes large amounts of root-only kernel code to an attacker: netfilter, filesystem mounting and the network stack. Many local-privilege-escalation bugs were reachable by unprivileged users via that door, such as the nf_tables flaw CVE-2024-1086. Some also have other routes, for example for processes that already hold CAP_NET_ADMIN.

  • Do use user namespaces to remove host root from the container. Examples are rootless Docker/Podman, Kubernetes hostUsers: false and Docker's --userns-remap. A runtime or container escape then lands as an unprivileged host user.
  • Do not allow sandboxed code itself to create new user namespaces unless it needs to. Deny unshare/clone(CLONE_NEWUSER) with seccomp, and where you do not need the feature, set user.max_user_namespaces=0. Some distributions have their own alternatives, such as Debian's kernel.unprivileged_userns_clone and Ubuntu 24.04's AppArmor restriction on unprivileged user namespaces.

08 · Docker, Podman, KubernetesHardening containers

References: Docker seccomp · Pod Security Standards · Kubernetes seccomp tutorial

A container runtime (runc, crun) is mostly a launcher. It performs the steps above in the right order from a JSON config, which follows the OCI (Open Container Initiative) runtime spec. Defaults are tuned for compatibility, so hardening is the work of removing what your workload does not need.

Things that void the sandbox

  • --privileged: all capabilities, all devices, no seccomp, no AppArmor, so it gives you almost none of a container's protection.
  • Mounting /var/run/docker.sock: whoever can talk to it can start a privileged container: root on the host, by design.
  • --pid=host, --net=host, --ipc=host, host-path bind mounts of /, /proc, /sys or /etc; --device of raw disks; --cap-add SYS_ADMIN; --security-opt seccomp=unconfined.
  • Running as root inside, with the runtime itself running as root on the host. A runtime bug then yields host root: see CVE-2019-5736 and CVE-2024-21626 in section 17.

Rootless and minimal

  • Rootless Docker/Podman: the daemon and containers run as an unprivileged user with a user namespace, using slirp4netns/pasta for networking, so a runtime escape lands as that user.
  • Minimal images: scratch or "distroless" images that hold the application binary, CA (certificate authority) certificates and nothing else. They have no shell, no package manager and no curl for an attacker to reuse, and you should pin them by digest rather than by tag.
  • Immutable hosts: container-focused operating systems ship a small read-only root and an update mechanism instead of a package manager. Examples are Flatcar, Bottlerocket, Talos and Fedora CoreOS (section 13).

10 · Programmable kerneleBPF: surface, enforcer and sensor

References: BPF LSM · unprivileged_bpf_disabled · Tetragon

eBPF lets privileged users load small verified programs into the running kernel, and it matters to hardening in three opposite ways.

1. As attack surface

The eBPF verifier is a large static analyser and the JIT compiles its output to native code. Bugs in either have repeatedly produced local privilege escalation (for example CVE-2021-3490 and CVE-2022-23222). So:

  • Set kernel.unprivileged_bpf_disabled to 1 (locked off until reboot) or 2 (disabled, admin may change it).
  • Set net.core.bpf_jit_harden=2.
  • Deny the bpf syscall to workloads by seccomp, and do not give them CAP_BPF, CAP_PERFMON or CAP_SYS_ADMIN.
  • Where eBPF is unused, compile it out (CONFIG_BPF_SYSCALL=n).

2. As an enforcer

  • BPF LSM (5.7, CONFIG_BPF_LSM and lsm=…,bpf): attach a program to any LSM hook; return a negative errno to deny. Because LSM hooks run after the kernel has copied and resolved its arguments, they avoid the time-of-check/time-of-use races that plague tracing-based enforcement. A sketch (not compiled here) that denies process creation, but not thread creation, for one cgroup: 
    SEC("lsm/task_alloc")
int BPF_PROG(deny_fork, struct task_struct *task, unsigned long clone_flags)
{
    const unsigned long CLONE_THREAD = 0x00010000;
    if (bpf_get_current_cgroup_id() == jail_cgroup_id && !(clone_flags & CLONE_THREAD))
        return -1;   /* -EPERM */
    return 0;
}
  • cgroup BPF: cgroup/connect4, cgroup/sock_create and friends give per-container egress policy; the CGROUP_DEVICE program is how v2 enforces device access.
  • Practicalities: BPF LSM programs are normally built with libbpf against the kernel's BTF (BPF Type Format, CONFIG_DEBUG_INFO_BTF). You build them as CO-RE (compile once, run everywhere) objects. A CO-RE object adapts at load time to the kernel it runs on, so one build works across kernel versions. You attach them with bpftool prog loadall … autoattach. The bpf LSM must also appear in the boot-time lsm= list.
  • Network: Cilium uses XDP and tc programs to enforce Kubernetes network policy. XDP (eXpress Data Path) runs a program as a packet arrives at the network driver. The tc (traffic control) tool is the Linux packet scheduler, which can run a program on packets as they enter or leave an interface. Both act on the packet path itself, so the policy applies before the packet reaches the workload.

3. As a sensor, and sometimes an enforcer

  • Falco and Tracee watch syscalls and kernel events and raise alerts on rule matches: detection, mostly after the fact.
  • Tetragon (Cilium) can enforce in-kernel: a TracingPolicy can send SIGKILL to the offender or override a call's return value. KubeArmor enforces through LSMs.
  • The TOCTOU caveat: monitors that hook syscall entry (tracepoints, kprobes) see the user-space arguments before the kernel copies them. A second thread can change them afterwards, so what was checked is not what the kernel acts on. Prefer enforcing at LSM hooks, and treat syscall-entry hooks as detection.
Which to pick

Use seccomp for "this process never needs that syscall". Use Landlock for "this process only needs those files". Use BPF LSM or Tetragon for fleet-wide policy you want to change without touching the application. Use detection tooling (Falco) to learn when any of it is being tested.

12 · Changing the boundaryA different kernel: gVisor, Kata, Firecracker

References: Firecracker design · Firecracker jailer · gVisor security model · Kata Containers

Everything so far shrinks and polices access to the host kernel, while the next tier stops sharing it in one of two ways. You can put a user-space kernel in between (gVisor), or give the workload its own guest kernel behind a hypervisor, as Kata, Firecracker and ordinary VMs do.

gVisor

gVisor's Sentry is a Linux-compatible kernel written in Go that runs as an ordinary unprivileged process. The application's syscalls are intercepted (by default through a seccomp-based "systrap" platform; a KVM platform also exists, and older releases offered a ptrace platform) and implemented by the Sentry. The Sentry itself is confined by seccomp to a small fraction of host syscalls. A kernel bug the application tries to exploit is a bug in Sentry's Go code, in user space, rather than in the host kernel.

  • Strengths: it has a far smaller host-kernel surface than a plain container. It is written mostly in Go, a memory-safe language (with some unsafe and assembly). It starts in container-like time (hundreds of milliseconds, not VM boot time). It is OCI-compatible as the runsc runtime, and RuntimeClass is easy to use in Kubernetes.
  • Costs: syscall-heavy and I/O-heavy workloads are slower; not every syscall, /proc file or ioctl is implemented, so some software fails; networking uses a user-space stack.

Kata Containers

Kata runs each pod inside a lightweight VM with its own guest kernel, while presenting the standard container interface (containerd shim v2, RuntimeClass). It can use QEMU, Cloud Hypervisor or Firecracker as the hypervisor. The workload sees a normal container; the host sees a VM.

Firecracker and microVMs

Firecracker is an open-source virtual machine monitor from AWS (it runs Lambda and Fargate) written in Rust on top of KVM. Its design is itself a hardening lesson: delete what you do not need.

  • Minimal device model: no BIOS, no USB, no GPU, no legacy emulation, and (by default) no PCI bus: devices sit on a simple MMIO (memory-mapped I/O) transport. Roughly, it offers virtio network, block and vsock devices, a serial console, a minimal keyboard controller for reset and a balloon. Newer versions add a few more, such as memory hot-plug and persistent-memory devices, and recent releases also offer an optional virtio-PCI transport. Check the current device matrix in the Firecracker docs before relying on a specific list. Historically the biggest source of hypervisor escapes has been emulated hardware (for example VENOM, CVE-2015-3456, in QEMU's virtual floppy controller).
  • Fast and small: the project's NSDI 2020 paper and README give these targets. A microVM boots to init in about 125 ms and adds under 5 MiB of VMM (virtual machine monitor) memory overhead. So a VM per request or per function becomes affordable.
  • A VMM that is itself sandboxed: the jailer puts the Firecracker process in a chroot (a changed filesystem root) with its own namespaces and cgroups. It drops privileges and applies a seccomp filter that differs per thread type (API, VMM and vCPU threads), so it uses every layer described on this page.
  • Rate limiters on network and block devices bound how much a noisy guest can hurt its neighbours.
  • vsock gives host-guest communication without a network, but it is still host attack surface: the host-side code that parses what the guest sends has had bugs. The same applies to virtio-fs and any other shared-folder device, which hand the guest a path into the host file system. Share as little as you can, read-only where possible.
  • Snapshots allow millisecond starts by resuming a saved memory image, but cloned snapshots duplicate guest state, including random-number-generator state. Entropy must be refreshed on resume (for example through the VM Generation ID mechanism) or two guests may generate identical "random" values.
# boot args typical of a Firecracker guest
console=ttyS0 reboot=k panic=1 pci=off nomodules   # pci=off matches the default MMIO transport
# the guest's init can be the workload itself: no shell, no sshd
init=/app

Similar projects: Cloud Hypervisor (Rust, Intel/Linux Foundation), crosvm (ChromeOS), libkrun, and QEMU's stripped microvm machine type. In crosvm, each virtual device runs in its own minijail-sandboxed process, and libkrun is a VMM as a library. Podman's krun runtime uses it to run an OCI container inside a microVM.

The costs

  • A VM is a stronger boundary, but it cannot guarantee safety. Escapes from the hypervisor and the VMM (virtual machine monitor) do exist. We still prefer a VM because its interface is much smaller. The guest can reach only a few emulated devices and VM exits (the points where the guest hands control to the host). A container, by contrast, can reach about 370 syscalls plus every driver, filesystem and network protocol.
  • Hardware side channels cross VMs: Spectre-class, L1TF and MDS attacks work across a hypervisor, so multi-tenant hosts use microcode updates, disabled SMT or core scheduling, and per-tenant host pinning.
  • Overhead: each guest costs a kernel's worth of memory and loses page-cache sharing with the host, and memory ballooning and dax/virtio-fs help only partly.
  • Confidential VMs (AMD SEV-SNP, Intel TDX) encrypt guest memory, so even a compromised host or hypervisor cannot read it. They protect the guest from the host, which is the opposite direction to everything else on this page. They do not remove the need to harden the guest.
  • KVM is itself kernel code: the host kernel still processes VM exits, so the attack surface shrinks but does not vanish.

WebAssembly as a sandbox

A Wasm (WebAssembly) module runs in a runtime (Wasmtime, WasmEdge, V8), and the runtime enforces memory isolation by construction. The module reaches the outside world only through capabilities the host passes in, such as WASI (WebAssembly System Interface) preopened directories and sockets. There is no ambient authority to remove: the default is nothing. The runtime is native code and can have bugs, so serious deployments run the runtime inside seccomp and Landlock, which is the same layering one level up.

13 · SubtractionCut-down Linux and unikernels

References: KSPP recommended settings · kernel-hardening-checker

The most reliable way to prevent exploitation of code is not to have the code. Every compiled-in driver, filesystem, network protocol and syscall is attack surface for every local user. A guest kernel in a microVM is a particularly good place to subtract aggressively, because it only has to support one workload.

Building a minimal kernel

  1. Start from nothing. make tinyconfig (or allnoconfig) and add only what boots and runs the workload. Or start from a distribution config and trim with make localmodconfig / localyesconfig, which keeps only modules currently loaded on a reference machine.
  2. Remove loadable modules (CONFIG_MODULES=n) for a fixed-function appliance: no module-autoload attack surface, no modprobe tricks, and the module-loading syscalls vanish.
  3. Remove syscall families you will not use: under CONFIG_EXPERT many are individually switchable.
  4. Turn on the self-protection options the kernel offers (list below).
  5. Check your work with kernel-hardening-checker, which compares a config and command line against KSPP and other recommendations.

Cut-down userland

  • Static, single-binary workloads: run a statically linked Rust or Go binary (or musl-linked C) as /init of a microVM. There is no shell, no package manager, no sshd and no libc to patch separately. An attacker with code execution has little to pivot with.
  • Container-optimised hosts: Flatcar and Fedora CoreOS are immutable and auto-updating. Bottlerocket (from AWS) is Rust-heavy, with SELinux enforcing, a read-only root and no default shell. Talos Linux has no SSH or shell at all and is managed by an API, and Google's Container-Optimized OS is another.
  • Small distributions: Alpine (musl, BusyBox), Wolfi/Chainguard images (built for minimal CVE exposure), Nix-built minimal closures, Buildroot and Yocto for embedded images.

Why it helps: a tiny code base; no /bin/sh for an exploit payload to run; no process creation; nothing to configure wrongly. Limits:

  • One address space: there is no privilege separation inside the guest: a memory bug in any library is a compromise of the whole guest. The isolation unit is the VM, so the hypervisor is your only boundary.
  • Exploit mitigations vary and have often lagged Linux (ASLR, stack protectors, W^X, guard pages): check each project.
  • Debugging, observability and patching are harder; you rebuild and redeploy the image.
  • Seccomp, Landlock and LSMs do not exist in the guest; there is nothing inside to enforce them. The policy is the set of things the image does not contain.

Putting it together: take a unikernel or tiny-init static binary and run it in a Firecracker microVM. Launch it with a jailer that gives the VMM a seccomp filter and cgroup limits. This is the "minimal everything" corner of the design space, at the right-hand end of section 15.

14 · Choosing the codeLanguage choice and dependency diet

References: RustSec · cargo-deny · cargo-vet · RLBox

All the sandboxing above assumes the workload will eventually be subverted. The other half of the strategy is making that less likely. Do this by making whole classes of bug impossible to express and by shrinking the amount of code you trust.

Memory safety removes the biggest class

Microsoft (MSRC, 2019) and the Chromium project (memory safety) have each reported that roughly 70% of their serious security bugs were memory-safety issues. These include use-after-free, buffer overflow and out-of-bounds read. Google's Android team reported that the share of memory-safety vulnerabilities fell sharply as new code moved to Rust, and the vulnerabilities that remain are mostly in new memory-unsafe code. Memory-safe languages remove that class by construction in safe code:

Language familyWhat it preventsWhat remains

A language does not replace a sandbox

Rust prevents a buffer overflow but does not stop a path-traversal bug, a command injection, a logic flaw or a malicious dependency from reading ~/.ssh/id_ed25519. A crate is not a security boundary. Every dependency runs with the full authority of the process, including build.rs scripts and procedural macros at build time. That is why you need both language safety and process sandboxing.

Shrinking the attack surface inside a Rust program

  1. Forbid your own unsafe: put #![forbid(unsafe_code)] at the top of crates that do not need it, and quarantine necessary unsafe in one small, heavily tested module. Enable unsafe_op_in_unsafe_fn and clippy's undocumented_unsafe_blocks.
  2. Measure the dependency graph: cargo tree lists it, cargo tree -d shows duplicates, and cargo tree -e features -i <crate> explains why a crate is pulled in. Run cargo geiger to count unsafe in your tree. A few dozen vetted crates is a different risk from a few hundred.
  3. Turn features off: most large crates default to many features, each pulling more crates: tokio = { version = "1", default-features = false, features = ["rt", "net"] }. Likewise prefer the standard library, or a small single-purpose crate, to a framework for one function.
  4. Prune the unused. cargo machete (or cargo udeps) finds declared-but-unused dependencies.
  5. Prefer pure Rust to C bindings where mature. For example, rustls instead of a binding to OpenSSL removes OpenSSL's large C protocol code, its certificate-parsing code and its CVE stream from the process. There is one caveat. The crypto back ends of rustls, ring and aws-lc-rs, still contain C and assembly primitives. You get a much smaller C footprint, but not zero C. Every *-sys crate is C attack surface despite its Rust name.
  6. Audit your dependencies.
    • cargo audit checks the lockfile against the RustSec advisory database (known-vulnerable and unmaintained crates).
    • cargo deny enforces policy in CI: allowed licences, banned crates, allowed registries and sources, duplicate-version limits, advisories.
    • cargo vet records that a human reviewed a specific crate version, and can import audits published by organisations you trust, so review effort is shared.
    • cargo crev is a web-of-trust code-review system, but few people publish reviews with it, so you may find none for your dependencies.
  7. Make builds reproducible and pinned: commit Cargo.lock; build with --locked; consider cargo vendor so a build needs no network and what you reviewed is what you compile. Check lockfile diffs in code review, since a new transitive dependency appears there first. Beware typosquats (look-alike package names) and compromised maintainers. The 2022 rustdecimal crate impersonated rust_decimal, and the 2024 xz backdoor (CVE-2024-3094) was a build-time script injection, the same risk class as build.rs.
  8. Treat build scripts and proc macros as code execution: review build.rs in new dependencies. Build in a sandbox without secrets or network, such as a throwaway container or microVM with your own launcher from section 16.
  9. Prefer provenance: provenance means a record of where a package came from and who built it. Where your registry supports it, publish and consume crates built by CI (continuous integration) with Trusted Publishing.
    • Trusted Publishing uses short-lived OIDC (OpenID Connect) credentials instead of long-lived API tokens. The CI system proves its identity to the registry, so no secret token sits around to be stolen.
    • Enable 2FA (two-factor authentication) for every maintainer. A stolen password alone then cannot publish a new release.
    • Have cargo vet record your policy as well as one-off reviews. The policy states which audits you trust and which exemptions you carry.
  10. Embed an SBOM. cargo auditable stores the dependency list in the binary so scanners can tell later what is deployed.
  11. Fail closed at run time: in the release profile, set panic = "abort" (no unwinding surprises; pair with a supervisor that restarts). Set overflow-checks = true so arithmetic overflow becomes a panic rather than a silent wrap. Use lto (link-time optimisation) and codegen-units = 1 for dead-code elimination. Use cargo clippy lints against unwrap/expect/indexing in request paths, and fuzz parsers with cargo fuzz. Run cargo miri over code that contains unsafe.
  12. Pass capabilities, not paths: libraries such as cap-std make filesystem access go through an explicit directory handle, so a function that was never handed /etc cannot open it. This is the in-process analogue of Landlock.
  13. Sandbox the Rust process itself: the landlock crate wraps the three syscalls with best-effort ABI handling; seccompiler compiles a filter in-process; caps/rustix expose capabilities and prctl safely.
  14. Sandbox the library as well as the process. When one dependency is the risk (a C codec, a parser), isolate it. RLBox with wasm2c, as Firefox does, compiles the library to WebAssembly and then to C that can only touch its own linear memory. So a bug in it cannot read the rest of the process. The cheaper cousin is running that one dependency in a helper process (next item).
  15. Split by process, not by crate: if one part parses untrusted input such as images, archives or documents, run it as a separate, more tightly sandboxed child. The child talks to the main process over a pipe or socket, the way Chromium's renderers and OpenSSH's privilege-separated child do. A bug in the parser then compromises a process that has no network, no files and no secrets.

Hardening C and C++ when you cannot move

  • Compile with -fstack-protector-strong -D_FORTIFY_SOURCE=3 -fPIE -pie -Wl,-z,relro,-z,now -fcf-protection and -ftrivial-auto-var-init=zero (clang 16 and later, GCC 12 and later).   • Use a hardened allocator (scudo, GrapheneOS's hardened_malloc) and run tests under AddressSanitizer/UBSan and a fuzzer.
  • Isolate the parsers: the sandbox launchers of section 11 are the main tool.

16 · SynthesisPutting it together: a launch sequence

Order matters because no restriction can be undone, and later steps need the rights earlier steps would take away.

  1. Set up while privileged: open sockets, files and devices the workload needs; create the cgroup and set pids.max, memory.max, cpu.max.
  2. Isolate the view: create new user, mount, pid, net, ipc, uts and cgroup namespaces. Use pivot_root to move into a minimal, read-only root, and mount a small tmpfs for scratch with nosuid,nodev,noexec.
  3. Drop privilege: switch to an unprivileged UID/GID; clear every capability set (permitted, effective, inheritable, bounding, ambient).
  4. Set no_new_privs and rlimits (NOFILE, CORE=0, FSIZE, ...).
  5. Apply Landlock (Landlock uses its own three syscalls. jail.c does not block them, but an allowlist filter would, so apply Landlock before such a filter). An allowlist filter must also permit everything the dynamic loader and execve need, such as mmap, mprotect and openat, so build it from a trace of the real program).
  6. Apply seccomp last (so the filter does not have to allow everything earlier steps used), with TSYNC if the process is already multi-threaded.
  7. execve the workload, since Landlock domains and seccomp filters survive exec.

The program below does steps 4 to 7 for real, and in order it:

  • sets an rlimit (resource limit) on open files and turns off core dumps, and closes inherited file descriptors;
  • sets no_new_privs;
  • adds a Landlock ruleset: read and execute under system directories only, no TCP, and (on ABI 6 and later) no signals or abstract Unix sockets to processes outside the sandbox;
  • adds a seccomp filter that checks the architecture, rejects x32, forbids fork, vfork and non-thread clone, and answers clone3 with ENOSYS;
  • runs the workload with execve and a clean environment (only PATH), so secrets and LD_* variables do not leak in.

The launcher refuses to run if Landlock is missing. By default it still runs on an older Landlock ABI, with TCP open below ABI 4 and signals unscoped below ABI 6. For untrusted code, set JAIL_REQUIRE_ABI=6 so it refuses to run unless the kernel can enforce everything shown. Run it as an unprivileged user, not as root. Building it needs kernel headers from 5.13 or later and glibc 2.31 or later (for close_range), and the filter compiles on x86-64 only. It sets only the file-descriptor and core-dump limits, and it leaves descriptors 0 to 2 as it found them: a directory descriptor passed on stdin would bypass Landlock, so give it ordinary pipes.

It deliberately does not call PR_SET_DUMPABLE. execve resets that flag for an ordinary binary, so setting it first protects nothing.

We built and ran it for this page on a 6.18 kernel (x86-64):

  • echo ran, a shell inside it failed with "Cannot fork", and a thread started but fork() failed.
  • A write to /tmp failed with "Permission denied", and /proc became unreadable.
  • A TCP connect failed with "Permission denied". A signal to a process outside the sandbox failed with "Operation not permitted".
  • A binary outside the allowed directories failed at execve.

The sandbox is tight on purpose. /proc and most of /dev are not readable, so ls / and any program that reads /proc/self will fail. The program grants only /dev/null (read and write) and /dev/urandom (read), and a real profile adds exactly what the workload needs. Its seccomp filter is also a denylist for process creation, which is acceptable for one narrow rule but not a replacement for the allowlist that section 3 recommends. The calls to deny next are unshare, setns, bpf, io_uring_setup, userfaultfd and socket with AF_UNIX.

// is accepted (no TCP rules below ABI 4, no scoping below ABI 6): set JAIL_REQUIRE_ABI=6 for untrusted code.
// Run it as an unprivileged user.
// Build: gcc -O2 -Wall -o jail jail.c      Run: ./jail /bin/echo hello

/* Our own copy of the attribute struct and the rights added after ABI 1, so the build does not
   depend on how new the installed kernel headers are (older headers lack the "scoped" field). */
#define LL_FS_REFER      (1ULL << 13)   /* ABI 2 */
#define LL_FS_TRUNCATE   (1ULL << 14)   /* ABI 3 */
#define LL_FS_IOCTL_DEV  (1ULL << 15)   /* ABI 5 */
#define LL_NET_BIND_TCP    (1ULL << 0)  /* ABI 4 */
#define LL_NET_CONNECT_TCP (1ULL << 1)
struct ll_attr { __u64 handled_access_fs, handled_access_net, scoped; };
#define LL_SCOPE_ABSTRACT_UNIX_SOCKET (1ULL << 0)
#define LL_SCOPE_SIGNAL               (1ULL << 1)

static void die(const char *m) { perror(m); exit(1); }

/* ---- Landlock: read+exec under /usr /bin /lib /lib64 /etc, nothing else ---- */
static int landlock(void) {
    struct ll_attr ra = { 0 };
    int abi = syscall(SYS_landlock_create_ruleset, NULL, 0, LANDLOCK_CREATE_RULESET_VERSION);
    if (abi < 1) { fprintf(stderr, "landlock unavailable (%d)\n", abi); return -1; }
    /* Landlock must be present. To insist on a minimum ABI (4 = TCP rules,
       6 = signal and abstract-socket scoping), set JAIL_REQUIRE_ABI=N. */
    const char *req = getenv("JAIL_REQUIRE_ABI");
    if (req) {
        char *end; long need = strtol(req, &end, 10);
        if (*req == 0 || *end || need < 1 || need > 99) { fprintf(stderr, "bad JAIL_REQUIRE_ABI\n"); return -1; }
        if (abi < need) { fprintf(stderr, "landlock ABI %d < required %ld\n", abi, need); return -1; }
    }
    fprintf(stderr, "landlock ABI %d\n", abi);
    __u64 ro = LANDLOCK_ACCESS_FS_EXECUTE | LANDLOCK_ACCESS_FS_READ_FILE | LANDLOCK_ACCESS_FS_READ_DIR;
    __u64 all = ro | LANDLOCK_ACCESS_FS_WRITE_FILE | LANDLOCK_ACCESS_FS_REMOVE_DIR |
        LANDLOCK_ACCESS_FS_REMOVE_FILE | LANDLOCK_ACCESS_FS_MAKE_CHAR | LANDLOCK_ACCESS_FS_MAKE_DIR |
        LANDLOCK_ACCESS_FS_MAKE_REG | LANDLOCK_ACCESS_FS_MAKE_SOCK | LANDLOCK_ACCESS_FS_MAKE_FIFO |
        LANDLOCK_ACCESS_FS_MAKE_BLOCK | LANDLOCK_ACCESS_FS_MAKE_SYM;
    if (abi >= 2) all |= LL_FS_REFER;
    if (abi >= 3) all |= LL_FS_TRUNCATE;
    if (abi >= 5) all |= LL_FS_IOCTL_DEV;   /* no ioctl on device files opened later */
    ra.handled_access_fs = all;             /* handle everything => deny everything by default */
    /* ABI 4+: handle TCP bind/connect and add no rules => no TCP at all. */
    if (abi >= 4) ra.handled_access_net = LL_NET_BIND_TCP | LL_NET_CONNECT_TCP;
    /* ABI 6+: no abstract Unix sockets, and no signals to processes outside this domain. */
    if (abi >= 6) ra.scoped = LL_SCOPE_ABSTRACT_UNIX_SOCKET | LL_SCOPE_SIGNAL;
    /* Pass only the fields this kernel knows: it rejects non-zero bytes beyond its own struct size (E2BIG). */
    size_t sz = abi >= 6 ? sizeof ra : abi >= 4 ? offsetof(struct ll_attr, scoped) : offsetof(struct ll_attr, handled_access_net);
    int rs = syscall(SYS_landlock_create_ruleset, &ra, sz, 0);
    if (rs < 0) die("landlock_create_ruleset");
    /* /etc is granted wholesale for the demo; a real profile lists single files. */
    const char *dirs[] = { "/usr", "/bin", "/lib", "/lib64", "/etc" };
    for (unsigned i = 0; i < sizeof dirs / sizeof *dirs; i++) {
        struct landlock_path_beneath_attr pb = { .allowed_access = ro };
        pb.parent_fd = open(dirs[i], O_PATH | O_CLOEXEC);
        if (pb.parent_fd < 0) continue;     /* path absent on this distro: skip */
        if (syscall(SYS_landlock_add_rule, rs, LANDLOCK_RULE_PATH_BENEATH, &pb, 0)) die("add_rule");
        close(pb.parent_fd);
    }
    /* Single devices that ordinary programs expect: shell redirects, randomness. */
    static const struct { const char *path; int write; } devs[] = { { "/dev/null", 1 }, { "/dev/urandom", 0 } };
    for (unsigned i = 0; i < sizeof devs / sizeof *devs; i++) {
        struct landlock_path_beneath_attr pb = { .allowed_access = LANDLOCK_ACCESS_FS_READ_FILE };
        if (devs[i].write) pb.allowed_access |= LANDLOCK_ACCESS_FS_WRITE_FILE | (all & LL_FS_TRUNCATE);
        pb.parent_fd = open(devs[i].path, O_PATH | O_CLOEXEC);
        if (pb.parent_fd < 0) continue;
        if (syscall(SYS_landlock_add_rule, rs, LANDLOCK_RULE_PATH_BENEATH, &pb, 0)) die("add_rule dev");
        close(pb.parent_fd);
    }
    if (syscall(SYS_landlock_restrict_self, rs, 0)) die("landlock_restrict_self");
    close(rs);
    return 0;
}

/* ---- seccomp: arch check, then DENY the process-creating calls ----------- */
#define OFF(f) offsetof(struct seccomp_data, f)
static void seccomp_nofork(void) {
    struct sock_filter f[] = {
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS, OFF(arch)),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_X86_64, 1, 0),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),          /* wrong ABI */
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS, OFF(nr)),
        BPF_JUMP(BPF_JMP | BPF_JGE | BPF_K, 0x40000000, 0, 1),        /* x32 bit set */
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_fork, 0, 1),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_vfork, 0, 1),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_clone3, 0, 1),        /* args are in memory: cannot inspect */
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | ENOSYS),        /* ENOSYS => libc falls back to clone */
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_clone, 0, 3),
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS, OFF(args[0])),             /* low 32 bits of flags */
        BPF_JUMP(BPF_JMP | BPF_JSET | BPF_K, CLONE_THREAD, 1, 0),     /* thread: allow */
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    };
    struct sock_fprog p = { .len = sizeof f / sizeof *f, .filter = f };
    if (syscall(SYS_seccomp, SECCOMP_SET_MODE_FILTER, SECCOMP_FILTER_FLAG_TSYNC, &p)) die("seccomp");
}

int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s prog [args]\n", argv[0]); return 2; }
    struct rlimit nofile = { 64, 64 }, core = { 0, 0 };
    if (setrlimit(RLIMIT_NOFILE, &nofile) || setrlimit(RLIMIT_CORE, &core)) die("setrlimit");
    /* Close every inherited descriptor above stderr: Landlock does not revoke fds
       that are already open, so a leaked directory fd would be a hole in the fence. */
    if (syscall(SYS_close_range, 3, ~0U, 0)) die("close_range");
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)) die("no_new_privs");
    if (landlock() < 0) return 1;           /* refuse to run */
    seccomp_nofork();                       /* dies on failure */
    /* Note: /proc and /dev are not granted, so the child cannot read /proc/self either. */
    /* Run with a clean environment so secrets and LD_* variables do not leak in. */
    char *env[] = { "PATH=/usr/bin:/bin", NULL };
    execve(argv[1], argv + 1, env);         /* exec is still allowed: it replaces, not creates */
    die("execve");
}
What this launcher does NOT stop
  • Unix sockets: it does not block connect() to pathname sockets. A process that can reach systemd --user, D-Bus or dockerd can ask that service to start a process for it. Fix: deny socket(AF_UNIX) in seccomp, or hide those sockets with a mount namespace.
  • Network beyond TCP: TCP is blocked on ABI 4 and later, but UDP, raw and netlink sockets are not. Filter the socket arguments, or use a network namespace.
  • Same-user neighbours: Landlock denies ptrace of processes outside the sandbox on every ABI, and on ABI 6 and later its scoping also blocks signals and abstract sockets to them. We tested both. Yama and a PID namespace add a second layer. Set dev.tty.legacy_tiocsti=0 (kernel 6.2 and later) and use setsid to stop keystroke injection through a shared terminal.
  • execve is allowed: anything in the readable directories can run, including a shell or an interpreter.
  • The /etc grant is too wide: a real profile names the exact files the workload needs.
  • No time limit: a busy loop runs forever, so add a watchdog (section 5).
Where this example stops

It runs on x86-64 only. It skips steps 1 to 3, because it expects the caller to be unprivileged. It grants /etc as a whole, so in real use you should list single files. It also lets every syscall through except process creation. We wrote it as a small demonstration, so it is a weaker filter than a production profile. A real allowlist, built as in section 3, is much tighter. With libseccomp you would call seccomp_init(SCMP_ACT_ERRNO(EPERM)) and add rules for the allowed syscalls. The library then handles the architecture checks for you.

CVE-2022-0847		A pipe-buffer flag bug let an unprivileged process overwrite page-cache pages of read-only files (kernel 5.8 and later).Patching, or a VM. The public exploit used splice, so a profile that denied it would have broken that exploit, but the bug is reachable by other means.
Leaky Vessels
CVE-2024-21626		A file descriptor into the host cgroup directory leaked into the container, allowing a path escape through the working directory.Patched runc. A runtime bug that none of the in-container policies would see; a VM boundary or rootless runtime limits the result.
nf_tables
CVE-2024-1086		A use-after-free in netfilter, reachable through unprivileged user namespaces; exploited for root and listed as exploited in the wild.Denying new user namespaces; seccomp that blocks the netlink families; not loading nf_tables at all; a kernel without netfilter (section 13).
io_uring bugs
(a recurring class)		Many local privilege escalations in a fast-moving interface that bypasses syscall filters.Seccomp denial of io_uring_*, kernel.io_uring_disabled=2, CONFIG_IO_URING=n.
NVIDIA Container Toolkit
CVE-2024-0132, CVE-2025-23266		Container-escape flaws in the GPU container integration: a file-system TOCTOU (time-of-check to time-of-use race), and later an LD_PRELOAD injection through an OCI hook run on the host.Patched toolkit. Host-side runtime hooks run outside the container's policy, so seccomp and capability drops inside it cannot help. If you pass a GPU through to a microVM, the device and its driver become part of the attack surface, so check what the guest can reach.
runc masked-path races
(CVE-2025-31133, CVE-2025-52565, CVE-2025-52881)		Races and bind-mount tricks in how runc masks and protects procfs paths allowed a container to write to host-sensitive files.Patched runc; user namespaces (rootless) and an enforcing LSM; not running untrusted images with custom mount configurations. Another reminder that the runtime is attack surface.
xz backdoor
CVE-2024-3094		A maintainer-level compromise injected a backdoor through release tarballs and build scripts into a library that sshd loaded on some distributions.Dependency diet; building from the source repo rather than release tarballs; reproducible builds; and a sandbox on sshd (systemd units with hardening reduce what a backdoor can reach). A language cannot prevent this.

The pattern: you mitigate runtime bugs and kernel memory bugs only by patching or by a harder boundary. You remove capability-gated bugs by dropping capabilities, using seccomp and denying user namespaces. You address supply-chain compromises with a smaller trusted base and by sandboxing what you did trust.

Test the sandbox

Before you rely on a setup, try to break out of it. Run amicontained inside a container to list its capabilities, seccomp mode and namespaces. Use kube-bench to check a Kubernetes node against the CIS benchmark, and try the escapes in section 17 against your own profile. Check that fork, socket and a write outside the allowed paths fail the way you expect, and that the failure is the one you chose (EPERM, not a crash). Container image signing, for example with cosign, shows who built an image. cargo vet records who reviewed a crate. Neither proves the code is safe.
